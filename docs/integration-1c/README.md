# SimplyAddinConnect — інструкція для 1С-розробника

Ти отримав ZIP-файл `SimplyAddinConnectWin.zip` — нативну зовнішню компоненту для
**1С:Підприємство** (Windows). Цей розділ пояснює **спільні механізми**, однакові для будь-якого
драйвера всередині компоненти: як підключити DLL, як читати результати, як ловити події, як
тестувати без обладнання. Специфіку конкретного драйвера (методи, параметри, приклади) шукай в
окремому файлі — див. [каталог драйверів](#каталог-драйверів) нижче.

> Це документація для **прикладного 1С-розробника**, який користується готовою компонентою.
> Внутрішня будова (C++) — у [docs/architecture/](../architecture/README.md).

---

## 1. Що це і як постачається

**SimplyAddinConnect** — одна нативна DLL (окремо x86 і x64), яка реєструє **кілька компонент**,
кожна доступна в 1С під власним іменем. Драйвери обладнання — одні з них.

ZIP містить:

| Файл | Призначення |
|---|---|
| `manifest.xml` | опис компоненти для 1С (перелік бінарників за архітектурою) |
| `SimplyAddinConnectWin_x86.dll` | компонента для 32-бітної 1С |
| `SimplyAddinConnectWin_x64.dll` | компонента для 64-бітної 1С |
| *(опційно)* `cm-pkcs12_x86/_x64.dll` | провайдери крипто (лише для UAPKI-збірки; 1С їх **не** розпаковує) |

1С сама вибере потрібний бінарник за архітектурою свого процесу — окремо думати про x86/x64 не треба.

## 2. Підключення компоненти в 1С

### 2.1. Завантажити DLL і створити об'єкт

Компонента підключається як зовнішня нативна компонента, далі створюється об'єкт потрібного класу
за символьним іменем:

```bsl
// Асинхронне підключення (рекомендовано для тонкого/веб-клієнта)
&НаКлиенте
Асинх Процедура ПодключитьКомпоненту(Команда)
    // Розташування: адреса тимчасового сховища зі свіжим ZIP, або ім'я макета конфігурації
    ДвоичныеДанные = Новый ДвоичныеДанные("D:\dist\SimplyAddinConnectWin.zip");
    Расположение    = ПоместитьВоВременноеХранилище(ДвоичныеДанные, УникальныйИдентификатор);

    СимвольноеИмя = "MyDriver";     // будь-яке стабільне ім'я
    Подключено = Ждать ПодключитьВнешнююКомпонентуАсинх(
        Расположение, СимвольноеИмя, ТипВнешнейКомпоненты.Native);

    Если Подключено Тогда
        Сообщить("Компонента підключена як " + СимвольноеИмя);
    КонецЕсли;
КонецПроцедуры
```

Потім створюється об'єкт конкретної **компоненти-класу** (ім'я класу — у файлі драйвера):

```bsl
// "AddIn.<символьне ім'я>.<ім'я класу компоненти>"
ОбъектДрайвера = Новый("AddIn." + СимвольноеИмя + ".ECRPrivatJSON");
```

Синхронний варіант (товстий клієнт) — `ПодключитьВнешнююКомпоненту(Расположение, СимвольноеИмя,
ТипВнешнейКомпоненты.Native)` без `Асинх`/`Ждать`.

> **Async-підключення приймає лише ім'я макета або АДРЕСУ тимчасового сховища — НЕ сирий шлях до
> файлу.** Тому файл спершу читають у `ДвоичныеДанные` і кладуть у сховище (`ПоместитьВоВременноеХранилище`),
> як у прикладі вище; передача рядка-шляху прямо в `ПодключитьВнешнююКомпонентуАсинх` дасть відмову.

### 2.2. ⚠️ Кеш нативної компоненти (важливо під час розробки)

1С розпаковує DLL у кеш `%APPDATA%\1C\1cv8\ExtCompT\` **за ІМЕНЕМ файлу** (напр.
`ExtCompT\SimplyAddinConnectWin_x64.dll`) і перевикористовує вже розпаковану — **незалежно від
нового вмісту** (`manifest.xml` формату `<bundle>` не має версії, тож 1С нема за чим виявити зміну).
Тому після перезбірки компоненти 1С може вперто вантажити СТАРУ версію: стара `Версия`, або
«Тип не определен» для нових методів/класів.

Що працює, а що ні (перевірено на практиці):

- Підключення зі свіжого ZIP через тимчасове сховище (як вище) обходить лише кеш
  `УстановитьВнешнююКомпоненту`, але **НЕ кеш екстракції** — 1С усе одно бере стару розпаковану DLL.
- Перезапуск клієнта 1С кеш екстракції **не чистить**.
- **Надійний обхід:** видали конкретні файли DLL у `%APPDATA%\1C\1cv8\ExtCompT\`
  (`SimplyAddinConnectWin_x64.dll` / `_x86.dll`) → наступне підключення розпакує свіжу збірку.
  Перевір версію (напр. кнопкою стандартного тесту) — має показати новий build.
- **У проді** це не проблема — версія компоненти оновлюється рідко.

> Автоматична інвалідація (напр. унікальне ім'я DLL за номером збірки) — у планах; поки під час
> розробки після кожної перезбірки компоненти чисти `ExtCompT`.

### 2.3. Тримай об'єкт живим між викликами

Драйвер тримає стан з'єднання з обладнанням **у C++** (усередині об'єкта). Тому створюй об'єкт
драйвера **один раз** (напр. змінна форми `&НаКлиенте Перем`) і перевикористовуй між натисканнями
кнопок — інакше кожен `Новый(...)` дасть нове неприєднане з'єднання.

## 3. Спільні конвенції всіх драйверів

### 3.1. Логування

Успадкований метод `ИспользоватьЛогирование(Рівень, Шлях)` вмикає файловий лог драйвера:

```bsl
ОбъектДрайвера.ИспользоватьЛогирование("Trace", "C:\log\SimplyAddinConnect.log");
```

Рівні: `0/Off`, `1/Error`, `2/Warn`, `3/Info`, `4/Debug`, `5/Trace`. Реєструвати цей метод не
треба — він є в кожній компоненті.

### 3.2. Уніфікований результат — `ResultEnvelope` (JSON)

Операції драйверів повертають результат **єдиним конвертом** — JSON-рядком такої форми:

```json
{ "ok": true, "code": "0000", "description": "", "payload": { } }
```

| Поле | Тип | Зміст |
|---|---|---|
| `ok` | Булево | успіх операції |
| `code` | Рядок | машинний код: протокольний (напр. `"0000"`) або драйверний (`"TIMEOUT"`, `"DEVICE_BUSY"`, …) |
| `description` | Рядок | людиночитний опис (для не-`ok`) |
| `payload` | Структура | корисні дані операції (набір полів — у файлі драйвера) |

Розбирай його штатним JSON-читанням 1С:

```bsl
&НаКлиенте
Функция РаскодироватьJSON(ТекстJSON)
    Читання = Новый ЧтениеJSON;
    Читання.УстановитьСтроку(ТекстJSON);
    Возврат ПрочитатьJSON(Читання);
КонецФункции

// ...
РезультатJSON = ОбъектДрайвера.Оплата("100.00");   // повертає JSON-рядок
Результат = РаскодироватьJSON(РезультатJSON);
Если Результат.ok Тогда
    Сообщить("Успіх, код " + Результат.code);
Иначе
    Сообщить("Помилка " + Результат.code + ": " + Результат.description);
КонецЕсли;
```

### 3.3. Синхронний vs асинхронний виклик

Операції обладнання бувають довгими (оплата — десятки секунд). Драйвери дають **дві форми**:

- **Синхронна** (`Оплата`, `Возврат`, …) — блокує потік 1С до завершення й одразу повертає
  результат. Просто, але **морозить UI** на весь час операції. Годиться для швидких операцій або
  фонових завдань.
- **Асинхронна** (`НачатьОплату` → полінг `СостояниеОперации` → `РезультатОперацииJSON`) —
  повертається одразу; стан операції ти **опитуєш** (напр. з `ПодключитьОбработчикОжидания`), UI
  лишається живим, можна показувати онлайн-статус і скасувати операцію.

Модель **poll-based**: за замовчуванням драйвер не шле подій — ти сам опитуєш стан. За бажанням
події можна ввімкнути (§3.4).

### 3.4. Події `ВнешнееСобытие` (опційно)

Драйвер може **опційно** пушити події в 1С через `ВнешнееСобытие`. Вмикається методом драйвера
(напр. `ВключитьСобытия(Истина)`); обробник на формі/модулі:

```bsl
// Источник = ім'я класу компоненти; Событие = тип; Данные = JSON-рядок
&НаКлиенте
Процедура ВнешнееСобытие(Источник, Событие, Данные)
    Если Источник <> "ECRPrivatJSON" Тогда Возврат; КонецЕсли;
    Стр = РаскодироватьJSON(Данные);
    // ... обробити Событие ("state"/"status"/"result" — конкретика у файлі драйвера)
КонецПроцедуры
```

Якщо обробника `ВнешнееСобытие` немає — пуш просто нічого не робить (помилки не буде). Набір і
формат подій — у файлі конкретного драйвера.

## 4. Тестування без обладнання

Компонента постачається з **тестовим контуром** — можна відлагодити прикладний 1С-код, не маючи
фізичного пристрою. Драйвери мають протокол-обізнані **емулятори** (окремі EXE), що слухають
localhost і віддають скриптовані відповіді.

Загальна схема:

1. Зібрати тестові EXE: `powershell -File build_project.ps1 -WithTests` (кладе `*.exe` у
   `bin/Release`).
2. Запустити емулятор потрібного драйвера (напр. `ecr_terminal_emulator.exe 2000`).
3. У 1С підключити компоненту й спрямувати драйвер на емулятор (напр. `tcp://127.0.0.1:2000`).
4. Викликати методи — емулятор друкує обмін у консоль, драйвер поводиться як із реальним пристроєм.

Конкретні кроки, порт і поведінка емулятора — у файлі драйвера.
