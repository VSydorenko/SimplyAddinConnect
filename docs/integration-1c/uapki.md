# Компонента AddinUAPKIConnect (ЕЦП/крипто) — інструкція для 1С-розробника

Компонента для **електронного підпису й шифрування** українським стеком **UAPKI**
(КЕП/ЕЦП ДСТУ 4145, ДСТУ 7624/7564, формати CAdES, контейнери PKCS#12). Клас компоненти в
1С — **`AddinUAPKIConnect`**.

На відміну від драйверів обладнання ([ECRPrivatJSON](ecr-privatjson.md),
[LabelPrinter](label_printer.md)), це **не** БПО-драйвер. Компонента — тонкий фасад над
бібліотекою UAPKI з **єдиною точкою входу** `ВызватьUAPKI(Метод, JSONПараметри)`, яка повертає
**JSON-рядок** відповіді бібліотеки. Уся семантика — це JSON-протокол UAPKI (методи, параметри,
коди помилок); повний опис — авторитетна настанова бібліотеки
[`extern/uapki/doc/UAPKI-PM-2.0.16.md`](../../extern/uapki/doc/UAPKI-PM-2.0.16.md).

Спільні механізми (підключення DLL, кеш компоненти, логування) — у [README.md](README.md);
тут — специфіка саме UAPKI.

> **Провайдер НКІ вбудований у DLL.** Крипто-провайдер `cm-pkcs12` (робота з файловими ключами
> `.p12`/`.pfx`) вкладено в головну DLL ресурсом і компонента розгортає його сама при `INIT` —
> **ставити додаткові файли не треба**. Внутрішня механіка — [docs/architecture/uapki.md](../architecture/uapki.md).

## 1. Швидкий старт

```bsl
&НаКлиенте
Перем ОбъектUAPKI;   // одна instance на форму — стан бібліотеки (ініціалізація, відкритий НКІ) живе в C++

// 1) Підключити компоненту (README §2) → маємо СимвольноеИмя, напр. "ECRTest"
// 2) Створити об'єкт ОДИН раз:
ОбъектUAPKI = Новый("AddIn." + СимвольноеИмя + ".AddinUAPKIConnect");
ОбъектUAPKI.ИспользоватьЛогирование("Trace", "C:\log\SimplyAddinConnect.log");

// 3) Ініціалізація бібліотеки (провайдер cm-pkcs12 розгортається сам):
Відповідь = РаскодироватьJSON(ОбъектUAPKI.ВызватьUAPKI("INIT", "{""offline"":true}"));
Если Відповідь.errorCode <> 0 Тогда Сообщить("INIT: " + Відповідь.error); Возврат; КонецЕсли;
Если Відповідь.result.countCmProviders = 0 Тогда
    Сообщить("Провайдер НКІ не завантажився — підпис приватним ключем недоступний"); Возврат;
КонецЕсли;

// 4) Далі: OPEN контейнера → SELECT_KEY → SIGN → VERIFY → CLOSE → DEINIT (§4)
```

## 2. Єдина точка входу — `ВызватьUAPKI`

| Метод (EN / RU) | Параметри | Повертає |
|---|---|---|
| `CallUapki` / `ВызватьUAPKI` | `Метод:Рядок`, `JSONПараметри:Рядок` | **Рядок** (JSON-відповідь UAPKI) |

- **`Метод`** — назва методу UAPKI (`INIT`, `OPEN`, `SIGN`, `VERIFY`, …; регістр методу
  бібліотека не розрізняє для `INIT`, решту пиши як у протоколі — великими).
- **`JSONПараметри`** — параметри методу. Приймаються у **двох форматах**:
  - **готовий JSON-об'єкт** (рядок починається з `{`) — передається в бібліотеку як поле
    `parameters` без змін (єдиний спосіб задати вкладені структури — `cmProviders`, `signParams`,
    `dataTbs`, `trustedCerts`);
  - **плоский** `ключ=значення,ключ=значення` — зручно для простих методів без вкладень.
- **Повертає JSON-рядок** відповіді бібліотеки (не Булево). Розбирай штатним `ЧтениеJSON`.

> **Порожні параметри дозволені:** `ВызватьUAPKI("DEINIT", "")`, `ВызватьUAPKI("VERSION", "")`.
> Для `INIT` порожній рядок = «параметри за замовчуванням» (компонента однаково сама інжектить
> `cmProviders`, див. §5).

Хелпер розбору відповіді (використовується скрізь нижче):

```bsl
&НаКлиенте
Функция РаскодироватьJSON(ТекстJSON)
    Читання = Новый ЧтениеJSON;
    Читання.УстановитьСтроку(ТекстJSON);
    Возврат ПрочитатьJSON(Читання);
КонецФункции

// Виклик методу + розбір + перевірка успіху в одному місці
&НаКлиенте
Функция UAPKI(Метод, JSONПараметри = "")
    Стр = РаскодироватьJSON(ОбъектUAPKI.ВызватьUAPKI(Метод, JSONПараметри));
    Возврат Стр;   // Стр.errorCode = 0 — успіх; інакше Стр.error — опис
КонецФункции
```

## 3. Формат відповіді

Усі методи повертають єдиний конверт (протокол UAPKI):

```json
{ "errorCode": 0, "method": "INIT", "result": { }, "error": "" }
```

| Поле | Тип | Зміст |
|---|---|---|
| `errorCode` | Число | **`0` — успіх**; інше — код помилки (Додаток А протоколу) |
| `method` | Рядок | ехо назви методу |
| `result` | Структура | вихідні дані методу (склад залежить від методу) |
| `error` | Рядок | короткий опис помилки (лише за `errorCode <> 0`) |

**Успіх операції визначай ТІЛЬКИ за `errorCode = 0`** (а не за наявністю `result`).

## 4. Життєвий цикл: `INIT → OPEN → SELECT_KEY → SIGN → VERIFY → CLOSE → DEINIT`

> **Три правила бібліотеки (важливо):**
> - **`INIT` — один раз на процес.** Повторний `INIT` без `DEINIT` дасть помилку
>   `RET_UAPKI_ALREADY_INITIALIZED`. Не ініціалізуй на кожну операцію.
> - **Один відкритий НКІ й один вибраний ключ водночас** — стан глобальний для всіх потоків.
>   Щоб узяти інший ключ — спершу `SELECT_KEY` на нього.
> - **Тримай об'єкт живим** між викликами (стан ініціалізації/відкритого НКІ — у C++).

### 4.1. `INIT` — ініціалізація

Провайдери НКІ компонента інжектить сама (§5) — зазвичай досить передати лише режим:

```bsl
Р = UAPKI("INIT", "{""offline"":true}");
Если Р.errorCode <> 0 Тогда Сообщить("INIT: " + Р.error); Возврат; КонецЕсли;
Сообщить("Завантажено провайдерів НКІ: " + Р.result.countCmProviders);   // має бути >= 1
```

Поля `result` `INIT`: `countCmProviders` (скільки провайдерів завантажено — **звіряй з 0**,
див. §5), `offline`, `certCache`, `crlCache` тощо.

### 4.2. `OPEN` — відкрити контейнер ключа (`.p12`/`.pfx`)

```bsl
ПараметриOpen = "{""provider"":""PKCS12"","
    + """storage"":""C:\\keys\\key.p12"","
    + """password"":""pin-код"","
    + """mode"":""RO""}";
Р = UAPKI("OPEN", ПараметриOpen);
Если Р.errorCode <> 0 Тогда Сообщить("OPEN: " + Р.error); Возврат; КонецЕсли;
```

- `provider` — `"PKCS12"` для файлових контейнерів.
- `storage` — шлях до файлу (у JSON зворотні слеші подвій: `C:\\keys\\key.p12`).
- `password` — пароль/PIN контейнера.
- `mode` — `"RO"` (лише читання/підпис), `"RW"`, `"CREATE"` (новий контейнер).
- Ключі з пам'яті: `storage:"file://memory"` + `openParams.bytes` (Base64 вмісту `.p12`).

### 4.3. `KEYS` → `SELECT_KEY` — вибрати активний ключ

```bsl
Ключі = UAPKI("KEYS", "");                       // Ключі.result.keys — масив {id, label, signAlgo, ...}
ИдКлюча = Ключі.result.keys[0].id;               // або обери потрібний за label
UAPKI("SELECT_KEY", "{""id"":""" + ИдКлюча + """}");
```

Після `SELECT_KEY` у `result` повертається сертифікат ключа (`certificate`, Base64) — якщо він є
в контейнері/кеші.

### 4.4. `SIGN` — підписати дані

Дані передаються масивом `dataTbs`, кожен елемент — Base64 (`bytes`). Формат підпису й опції —
у `signParams`/`options`:

```bsl
// Дані для підпису → Base64
ДвоичныеДанные = ПолучитьДвоичныеДанныеИзСтроки("Текст для підпису");
ДаніBase64 = Base64Строка(ДвоичныеДанные);

ПараметриSign = "{""signParams"":{"
    + """signatureFormat"":""CAdES-BES"","        // BES (офлайн) | T (з позначкою часу, потребує TSP/онлайн)
    + """signAlgo"":""1.2.804.2.1.1.1.1.3.1.1"","  // ДСТУ 4145
    + """detachedData"":false,"                    // false = дані всередині підпису (enveloping)
    + """includeCert"":true,"                      // вкласти сертифікат підписувача
    + """includeTime"":true},"
    + """dataTbs"":[{""id"":""doc-0"",""bytes"":""" + ДаніBase64 + """}],"
    + """options"":{""ignoreCertStatus"":true}}";  // не звіряти статус сертифіката (тест/офлайн)

Р = UAPKI("SIGN", ПараметриSign);
Если Р.errorCode <> 0 Тогда Сообщить("SIGN: " + Р.error); Возврат; КонецЕсли;
ПідписBase64 = Р.result.signatures[0].bytes;      // готовий CMS-підпис (Base64)
```

### 4.5. `VERIFY` — перевірити підпис

**Холістичний вердикт бери з `signatureInfos[0].status` (`"TOTAL-VALID"` = валідно)**, а НЕ з
`statusSignature` — останній лишається `"VALID"` навіть при пошкодженому detached-контенті.

```bsl
ПараметриVerify = "{""signature"":{""bytes"":""" + ПідписBase64 + """},""options"":{""validationType"":""STRUCT""}}";   // enveloping + структурна (офлайн) перевірка
Р = UAPKI("VERIFY", ПараметриVerify);
Если Р.errorCode = 0 И Р.result.signatureInfos[0].status = "TOTAL-VALID" Тогда
    Сообщить("Підпис валідний");
Иначе
    Сообщить("Підпис НЕ валідний: " + ?(Р.errorCode = 0, Р.result.signatureInfos[0].status, Р.error));
КонецЕсли;
```

### 4.6. `CLOSE` / `DEINIT`

```bsl
UAPKI("CLOSE", "");    // закрити НКІ (за потреби перед відкриттям іншого)
UAPKI("DEINIT", "");   // деініціалізація бібліотеки (в кінці роботи)
```

## 5. Провайдери НКІ — самодоставка (нічого налаштовувати не треба)

Робота з приватними ключами (`OPEN`/`SIGN`) в UAPKI виконується **окремим провайдером НКІ**
(`cm-pkcs12`). Компонента робить це **прозоро**:

- при `INIT` вона сама додає в параметри `cmProviders` (каталог + `cm-pkcs12` з арх-суфіксом),
  тож **власноруч задавати `cmProviders` не потрібно**;
- сам файл провайдера **вбудований у DLL** і розгортається компонентою при першому `INIT`
  (у `%LOCALAPPDATA%\SimplyAddinConnect\providers\<версія>\`) — жодних додаткових DLL коло
  бази 1С класти не треба.

**Єдина перевірка з боку 1С:** після `INIT` подивись `result.countCmProviders`. Якщо `0` — провайдер
не завантажився (антивірус заблокував запис/завантаження, немає прав на `%LOCALAPPDATA%` тощо), і
`OPEN`/`SIGN` не працюватимуть. Сама бібліотека при цьому все одно віддає `errorCode:0` — тому
`countCmProviders` і є справжнім індикатором готовності.

Якщо треба вказати власний каталог провайдерів (напр. апаратний токен `cm-pkcs11`) — передай
`cmProviders.dir` явно в параметрах `INIT`: непорожній `dir` компонента поважає як є (розгортання
вбудованого ресурсу не виконується).

## 6. Офлайн-режими (без доступу до мережі)

Тестові/локальні сценарії часто без доступу до OCSP/CRL/TSP:

- `"offline": true` у **`INIT`** — вимикає онлайн-перевірки статусу сертифікатів.
- `"options": {"ignoreCertStatus": true}` у **`SIGN`** — не звіряти статус сертифіката (потрібно
  для тестового/простроченого ланцюга).
- **`VERIFY` у режимі STRUCT** (без `validationType`) — чисто структурна офлайн-перевірка підпису.
- Онлайн-формат в офлайні (напр. **CAdES-T**, якому потрібен TSP) → помилка
  `RET_UAPKI_OFFLINE_MODE` (код `4120`) — **очікувана поведінка**, не збій.

## 7. Помилки

- **Помилки бібліотеки:** `errorCode <> 0` + `error` (короткий опис). Повний перелік кодів —
  **Додаток А** настанови [`extern/uapki/doc/UAPKI-PM-2.0.16.md`](../../extern/uapki/doc/UAPKI-PM-2.0.16.md).
  Часті: `4120` (`RET_UAPKI_OFFLINE_MODE` — онлайн-операція в офлайні), `RET_UAPKI_ALREADY_INITIALIZED`
  (повторний `INIT`), помилки пароля/формату контейнера в `OPEN`.
- **Помилки рівня компоненти** (виняток C++, некоректний виклик) повертаються у тому ж форматі з
  `errorCode: 500`: `{"errorCode":500,"error":"<текст>"}`.

```bsl
Р = UAPKI("OPEN", ПараметриOpen);
Если Р.errorCode <> 0 Тогда
    Сообщить("UAPKI помилка [" + Строка(Р.errorCode) + "]: " + Р.error);
КонецЕсли;
```

## 8. Підпис документів ПРРО (фіскальні чеки/Z-звіти)

Для ЄВПЕЗ (фіскальний сервер ДПС) підпис має бути **CAdES з позначкою часу (E-T), enveloping**
(дані всередині), із **вкладеним сертифікатом підписувача**, але **без** CRL/OCSP/ланцюга видавця
й **без** content-timestamp. У термінах `SIGN` це:

```jsonc
"signParams": {
  "signatureFormat": "CAdES-T",   // з позначкою часу (потрібен онлайн-доступ до TSP)
  "detachedData": false,          // enveloping — дані всередині
  "includeCert": true,            // сертифікат підписувача — так
  "includeContentTS": false,      // content-timestamp — ні
  "includeTime": true
}
```

Точні вимоги до підпису, еталони й крос-валідацію див. у скілі
[`.claude/skills/prro-fiscal`](../../.claude/skills/prro-fiscal/SKILL.md); формати підпису — Додаток Б
настанови UAPKI.

## 9. Тестування без 1С

Крипто-стек має **автоматичний тест-контур** (збирається лише разом із `-WithUAPKI`), яким можна
відлагодити ланцюг ЕЦП без 1С:

- **`uapki_selftest.exe`** (L1) — крипто-ядро через `process()` за JSON-сценаріями
  [`tests/scenarios/*.json`](../../tests/scenarios) (`INIT`/`OPEN`/`SIGN`/`VERIFY`/… на тестовому
  контейнері `test-diia.p12`, пароль `testpassword`).
- **`native_host.exe`** (L2/L3) — компонента `AddinUAPKIConnect` **через головну DLL** (як 1С):
  розгортання провайдера ресурсом, повний ланцюг підпис→перевірка, крос-валідація еталонів ПРРО.

Запуск гейта: `build_project.ps1 -WithUAPKI -WithTests`, потім `run_tests.ps1 [x64|x86]`. Точний
склад — [AGENTS.md](../../AGENTS.md) «Тести»; ноу-хау тестування ЕЦП без 1С — скіл
[`.claude/skills/ecp-testing-without-1c`](../../.claude/skills/ecp-testing-without-1c/SKILL.md).

> Тестовий ланцюг сертифікатів **прострочений** (тому в сценаріях скрізь `offline:true` +
> `ignoreCertStatus:true`, а `VERIFY` — у режимі STRUCT). Для бойового підпису потрібні чинні
> ключ і сертифікат.

## 10. Типові помилки й рішення

| Симптом | Причина / рішення |
|---|---|
| `INIT` → `countCmProviders = 0` | Провайдер не завантажився (антивірус/права на `%LOCALAPPDATA%`) — `OPEN`/`SIGN` не працюватимуть (§5) |
| Повторний `INIT` → помилка | `RET_UAPKI_ALREADY_INITIALIZED` — `INIT` робиться раз на процес; тримай об'єкт живим, не ре-ініціалізуй (§4) |
| `SIGN`/`OPEN` → `errorCode:500` | Виняток компоненти: перевір формат JSON-параметрів (вкладені структури — лише «сирим» JSON, §2) |
| CAdES-T → `4120` в офлайні | `RET_UAPKI_OFFLINE_MODE` — формат із часом потребує TSP/онлайн; для офлайну бери CAdES-BES (§6) |
| `VERIFY` `errorCode:0`, але `statusSignature` `VALID` при битому контенті | Дивись `signatureInfos[0].status` (`TOTAL-VALID`), а не `statusSignature` (§4.5) |
| 1С вантажить стару версію компоненти | Кеш нативної компоненти — [README §2.2](README.md) |
