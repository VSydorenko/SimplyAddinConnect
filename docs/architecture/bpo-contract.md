# Контракт «Подключаемое оборудование» (БПО) — що реально кличе 1С

Спільна підсистема для **всіх драйверів обладнання** проєкту: `LabelPrinter`, майбутній
БПО-фасад еквайрингу, наступні. Тут — **контракт між 1С і компонентою**, звірений із кодом
конфігурації. Специфіка конкретного драйвера лишається у своєму документі
(`label_printer.md`, `ecrprivatjson.md`).

> **Статус: звірено на ОБОХ продуктах — УНФ ru і BAS УНФ ua** (2026-08-31), ключові
> механізми перевірені на живій 1С 8.3.27 зонд-компонентою `ProbeBPO`.
> Системні імена ідентичні; **сигнатура оплати залежить від ревізії**, тож компонента
> дає **фасад на кожне сімейство сигнатур** — 3004 і 4000 (§2.1–2.3).

---

## 1. Головне: обробник драйвера один на всі драйвери

Обробник вибирається **не** за моделлю обладнання. Але механізм вибору у двох продуктів різний.

**УНФ ru** — `МенеджерОборудованияКлиент.ПараметрыПодключенияДрайвера`, лише за типом клієнта:

```bsl
Если ОбщегоНазначенияБПОКлиент.ЭтоВебКлиент() Тогда
    ОбработчикДрайвера = ПодключаемоеОборудованиеДрайверWEBКлиент;
Иначе
    ОбработчикДрайвера = ПодключаемоеОборудованиеДрайверКлиент;   // ~3049 рядків
КонецЕсли;
```

Реквізит довідника драйверів, який колись задавав BSL-обробник під модель, називається
`УдалитьОбработчикДрайвера` — механізм виведений з ужитку.

**BAS УНФ ua** — старша версія БПО, `МенеджерОборудованияКлиентПереопределяемый.
ПолучитьОбработчикДрайвера`: спершу жорсткий перелік legacy-обробників (1С-сканери, АртСофт,
Cashalot, Атол-офлайн…), а для **завантажуваного** драйвера (`ЗагружаемыйДрайвер`, тобто з
макета) — падіння у fallback:

```bsl
// Используем универсальный обработчик драйвера по стандарту "BAF".
#Если ВебКлиент Тогда
    Результат = ПодключаемоеОборудованиеУниверсальныйДрайверАсинхронноКлиент;
#Иначе
    Результат = ПодключаемоеОборудованиеУниверсальныйДрайверКлиент;   // ~3193 рядки
#КонецЕсли
```

**Наслідок для нас — головний:** наш драйвер постачається з макета, тобто **в обох продуктах
автоматично отримує універсальний обробник**. Прикладна конфігурація не потребує **жодного
рядка** коду під конкретний протокол, і кожен наступний протокол не потребує правок у 1С.

Різниця у СПОСОБІ виклику (для компоненти неістотна): ru кличе асинхронно
(`Ждать ОбъектДрайвера.МетодАсинх(...)`), ua — синхронно (`Ответ = ОбъектДрайвера.Метод(...)`).
`Асинх`-варіанти генерує платформа сама; компонента реєструє **один** метод. Але на прогрес
операції ця різниця впливає радикально — див. §4.

## 2. ⚠️ Імена системних методів — КОРОТКІ, не Equipment-*

Це найважливіший факт документа, і він **суперечить документу ІТС** (§5).

Виклики йдуть як `Ждать ОбъектДрайвера.<Метод>Асинх(...)`; результат — структура з
`.Значение` (функціональний результат) і `.Параметры[N]` (OUT-параметри, індексація з 0).

| Метод | Параметри | Повертає |
|---|---|---|
| `ПолучитьРевизиюИнтерфейса` | — | Число |
| `ПолучитьОписание` | `ОписаниеДрайвера`[OUT XML] | Булево |
| `ПолучитьПараметры` | `ПараметрыДрайвера`[OUT XML] | Булево |
| `УстановитьПараметр` | `Имя`, `Значение` | Булево |
| `Подключить` | `ИДУстройства`[OUT] | Булево |
| `Отключить` | `ИДУстройства` | Булево |
| `ТестУстройства` | `РезультатТеста`[OUT], `АктивированДемоРежим`[OUT] | Булево |
| `ПолучитьОшибку` | `ОписаниеОшибки`[OUT] | Число (LONG-код) |
| `ПолучитьДополнительныеДействия` | `ДополнительныеДействия`[OUT XML] | Булево |
| `ВыполнитьДополнительноеДействие` | `ИмяДействия` | Булево |
| `УстановитьЛокализацию` | `КодЯзыка`, `ШаблонЛокализации` | Булево |

**Послідовність підключення жорстка й безальтернативна:**

```
УстановитьПараметр("EquipmentType", <тип>)
УстановитьПараметр(<ім'я>, <значення>) × N      // усі параметри підключення
Подключить(ИДУстройства[OUT])                   // безпараметровий, крім OUT
```

Тобто `EquipmentType` і параметри приходять **окремими викликами ДО** підключення, а не одним
XML-пакетом. Отриманий `ИДУстройства` далі передається **першим** параметром у кожну операцію.

Перевірка ревізії біля `Подключить` стосується **лише локалізації**
(`Если РевизияИнтерфейса >= 4000 Тогда … УстановитьЛокализациюАсинх`), альтернативної гілки
з довгими іменами немає. Наслідок нашого вибору ревізії `3004` (§2.1): `УстановитьЛокализацию`
1С нам не викличе — інтерфейсні рядки драйвер віддає своєю мовою, і це прийнятно.

**Доказ (звірка 2026-08-31, конфігурація УНФ ru, 13255 файлів `.bsl`):**

| Шуканий рядок | Збігів |
|---|---|
| `ОбъектДрайвера.ПодключитьОборудование` | 0 |
| `ОбъектДрайвера.ПараметрыОборудования` | 0 |
| `ОбъектДрайвера.ТестированиеОборудования` | 0 |
| `ОбъектДрайвера.ОтключитьОборудование` | 0 |
| `ConnectEquipment` / `EquipmentParameters` / `EquipmentTest` / `SetApplicationInformation` | 0 |
| `ОбъектДрайвера.ПодключитьАсинх` | є |

Той самий пошук по українській конфігурації (24688 файлів) — теж **0 збігів** довгих імен.
`ПодключаемоеОборудованиеУниверсальныйДрайверКлиент` кличе рівно ті самі короткі імена
(плюс `ПолучитьНомерВерсии`). **Питання імен закрите для обох продуктів.**

### 2.1. Ревізія інтерфейсу визначає СІМЕЙСТВО СИГНАТУР → фасад на ревізію

`ПолучитьРевизиюИнтерфейса()` — це не «наскільки ми сучасні», а **вибір розкладки параметрів**,
за якою 1С кличе операції. Тому ревізія не підбирається «спільним знаменником»: компонента
реалізує **окремий клас-фасад на кожне сімейство сигнатур**, а конфігурація бере той, який
підтримує (§2.3).

Причина — сигнатура `ОплатитьПлатежнойКартой` різна.

**ua** (`…УниверсальныйДрайверКлиент:2056`) — **без жодної перевірки ревізії**, завжди 7:

```bsl
Ответ = ОбъектДрайвера.ОплатитьПлатежнойКартой(ИДУстройства, НомерКарты, Сумма,
                                               НомерЧека, КодRRN, КодАвторизации, СлипЧек);
```

**ru** (`…ДрайверКлиент`, ~2015-2071) — три гілки за ревізією:

| Умова | Параметрів | Перші параметри |
|---|---|---|
| `>= 4000` | 9 | `ИДУстройства, НомерМерчанта, РеквизитыКартыQR, СуммаОперации, …` |
| `>= 3005` | 8 | `ИДУстройства, НомерМерчанта, СуммаОперации, …` |
| інакше | **7** | `ИДУстройства, НомерКарты, СуммаОперации, НомерЧека, СсылочныйНомер, КодАвторизации, ТекстСлипЧека` |

Сім параметрів ru-гілки `Иначе` і сім параметрів ua збігаються **позиція в позицію**
(`КодRRN` = `СсылочныйНомер`, `СлипЧек` = `ТекстСлипЧека`). Об'єднати 7 і 8 в одному методі
неможливо: на позиції 2 в ua стоїть `НомерКарты`, а в ru на 3005 — `НомерМерчанта`; різний
**зміст** на тій самій позиції дефолтами не лікується.

`ПараметрыТерминала` в ru охороняється `Если ПараметрыПодключения.РевизияИнтерфейса >= 3004`
(рядок 1850) і кличеться одразу після успішного `Подключить` для типу `ЭквайринговыйТерминал`.
В ua `ПараметрыТерминала` немає — на його місці безпараметровий `ПечатьКвитанцийНаТерминале()`.

### 2.2. Чому одним класом не обійтися

**Одне ім'я методу = одна арність.** `GetNParams` віддає для методу рівно одне число, тож
зареєструвати `ОплатитьПлатежнойКартой` двічі з різною кількістю параметрів **неможливо**.

Підкласти дефолти теж не рятує: це не «додаткові хвостові аргументи», а **інша розкладка** —
на позиції 1 у 7-параметровій сімці стоїть `НомерКарты`, а у 8/9-параметрових — `НомерМерчанта`.
Різний зміст на тій самій позиції.

Звідси єдине робоче рішення — **клас-фасад на сімейство сигнатур**, усі над одним драйвером.
Коштує це майже нічого: логіка драйвера спільна, фасад лише розкладає той самий
`ResultEnvelope` по своїх позиціях і віддає свою `ПолучитьРевизиюИнтерфейса`.

### 2.3. Які фасади робимо (рішення 2026-08-31)

| Фасад | Ревізія | Оплата/Повернення/Скасування | Кому |
|---|---|---|---|
| `3004` | `3004` | 7 параметрів | BAS УНФ ua (кличе безумовно) + старші ru |
| `4000` | `4000` | 9 параметрів (скасування — 10) | сучасний УНФ ru |

Проміжні `3005`/`3006` (8 параметрів) **свідомо пропущено** — жодна з цільових баз на них не
стоїть; додати третій фасад пізніше дешево.

**Наслідок для складу операцій:** `РеквизитыКартыQR`, `НомерМерчанта`, `СуммаОригинальнойОперации`,
часткове скасування й видача готівки існують **лише у фасаді 4000**. У фасаді 3004 їх немає в
принципі — і це не втрата, бо конфігурація на тій ревізії їх не кличе.

**Максимальна арність — 10** (`ОтменитьПлатежПоПлатежнойКарте` на 4000). Розширення ядра до 16
(коміт `c03a613`) покриває із запасом.

**Як конфігурація обирає фасад — окремим записом довідника драйверів на кожен.** Автовизначення
немає й бути не може: `ИдентификаторОбъекта` запису — це буквально ім'я класу, БСП створює
об'єкт як `Новый("AddIn." + СимволическоеИмя + "." + Идентификатор)`
(`ОбщегоНазначенияСлужебныйКлиент.НовыйОбъектКомпоненты:1015`); поля версії поруч немає.

⚠️ **Обидва записи їдуть в обидва продукти, вибір робить адміністратор при налаштуванні.**
Жорстко зашивати фасад під продукт не можна: розширення їде в багато клієнтських баз, версія
УНФ у них різна, а звірка робилась по вивантаженню ОДНІЄЇ бази кожного продукту. Якщо в клієнта
старіша збірка без гілки `>= 4000`, драйвер, що оголосив 4000, впаде в гілку `>= 3005` — вісім
параметрів замість дев'яти, тобто **тиха розбіжність розкладки**. При виборі адміністратором
помилка натомість дає негайну видиму відмову на «Тест устройства».

### 2.3.1. Операції, яких обладнання не вміє — реєструвати й чесно відмовляти

**Правило (рішення 2026-08-31):** фасад реєструє **ВСІ** методи своєї ревізії, включно з тими,
яких драйвер/термінал поки не підтримує. Непідтримувана операція повертає `Ложь`, а
`ПолучитьОшибку` віддає код і текст, що операція обладнанням не підтримується.

Це прямо відповідає вимозі ІТС §1.3: *«Обеспечить возможность реализации функционала в полном
объеме… Если оборудованием данная функция не поддерживается, должно возвращаться "False", а в
описании ошибки, возвращаемом методом "ПолучитьОшибку/GetLastError", содержится текст, что
данная функция оборудованием не поддерживается»*.

Захист **двошаровий**, і плутати шари не можна:

1. **Прапорці `ПараметрыТерминала`** (`PartialCancellation`, `CashWithdrawal`,
   `ConsumerPresentedQR`, `ElectronicCertificates`, `ListCardTransactions`) для невміючих
   операцій **не виставляються**. Конфігурація перевіряє їх **ДО** виклику драйвера й сама
   каже касиру «Частичная отмена не поддерживается драйвером». Це основний шар — касир не
   бачить недоступної дії.
2. **Чесна відмова методу** — підстраховка на випадок, коли метод усе-таки покликали (інша
   гілка конфігурації, ревізія без прапорця, помилка налаштування). Мовчазне `Истина` або
   виняток тут неприпустимі.

Практично для нас це майже нічого не коштує: у драйвера вже є код `UNSUPPORTED` у
`ResultEnvelope`, а фасад мапить його в стабільний числовий код для `ПолучитьОшибку` — так само,
як `CodeToInt` у `AddinLabelPrinter`.

Станом на зараз до цієї категорії у фасаді **4000** належать: часткове скасування, видача
готівки (`ОплатитьПлатежнойКартойCВыдачейНаличных`), Consumer-Presented QR, електронні
сертифікати, `ПолучитьОперацииПоКартам`. Драйвер ECRPrivatJSON їх не реалізує
(`ecrprivatjson.md` §8), і піднімати це в пріоритеті зараз не плануємо.

### 2.4. Еквайрингові методи фасаду 3004

Звірено позиція в позицію між ru (гілка `Иначе`) і ua — **збігаються всі**:

| Метод | ru | ua |
|---|---|---|
| `ОплатитьПлатежнойКартой` | 2069 | 2056 |
| `ВернутьПлатежПоПлатежнойКарте` | 2073 | 2106 |
| `ОтменитьПлатежПоПлатежнойКарте` | 2077 | 2157 |
| `ИтогиДняПоКартам` | 2303 | 2013 |
| `АварийнаяОтменаОперации` | 2283 | 2189 |
| `ПолучитьОперацииПоКартам` | 1970 | — |

Три платіжні методи мають **однакову сімку**:

```
(ИДУстройства, НомерКарты, СуммаОперации, НомерЧека, СсылочныйНомер, КодАвторизации, ТекстСлипЧека)
```

ua-іменування позиційно те саме: `КодRRN` = `СсылочныйНомер`, `СлипЧек` = `ТекстСлипЧека`,
`Сумма` = `СуммаОперации`. Решта два:

```
ИтогиДняПоКартам(ИДУстройства, ТекстСлипЧека[OUT]) → Булево
АварийнаяОтменаОперации(ИДУстройства)              → Булево
```

Охорони за ревізією в цих двох немає в жодній редакції.

**`ПолучитьОперацииПоКартам` у фасаді 3004 НЕ реалізовувати.** В ua методу немає взагалі, а в ru
функція `ОперацииПоКартам` починається з `Если РевизияИнтерфейса < 4000 Тогда … Возврат` — на
3004 конфігурація повертає відмову, не доходячи до драйвера, тож реалізація була б мертвим
кодом. Прапорець `ListCardTransactions` у `ПараметрыТерминала` відповідно теж не виставляти.
У фасаді **4000** метод досяжний — там питання лише в тому, чи вміє це сам термінал.

#### Розкладка OUT і що з неї бачить касир

Усі **шість** параметрів після `ИДУстройства` — **IN/OUT** (ru, рядки 2129-2134):

```
Параметры[1] = НомерКарты      Параметры[4] = СсылочныйНомер
Параметры[2] = СуммаОперации   Параметры[5] = КодАвторизации
Параметры[3] = НомерЧека       Параметры[6] = ТекстСлипЧека
```

⚠️ `СуммаОперации` — **число**, не рядок: інший шлях у `VariantHelper::clear()`
(`VTYPE_R8`/`VTYPE_I4` не кличуть `FreeMemory`) і власний ризик — втратити дробову частину
суми, прочитавши її як ціле. Читати й писати саме `double`.

Мапінг із `payload` нашого драйвера ECRPrivatJSON:

| Наше поле | Параметр БПО |
|---|---|
| `cardPAN` | `НомерКарты` |
| `amount` | `СуммаОперации` |
| `invoiceNumber` | `НомерЧека` |
| `rrn` | `СсылочныйНомер` |
| `approvalCode` | `КодАвторизации` |
| `receiptText` | `ТекстСлипЧека` |

`ТекстСлипЧека` додатково лягає в `ПодключаемоеОборудование.ПоследнийСлипЧек` — звідти працює
команда «Надрукувати останній сліп-чек».

### 2.5. Еквайрингові методи фасаду 4000

Звірено дослівно (`ПодключаемоеОборудованиеДрайверКлиент`, гілка `Если РевизияИнтерфейса >= 4000`,
рядки 2014-2035):

```
ОплатитьПлатежнойКартой(ИДУстройства, НомерМерчанта, РеквизитыКартыQR, СуммаОперации,
    НомерКарты, НомерЧека, СсылочныйНомер, КодАвторизации, ТекстСлипЧека)              → 9

ВернутьПлатежПоПлатежнойКарте( … та сама дев'ятка … )                                   → 9

ОтменитьПлатежПоПлатежнойКарте(ИДУстройства, НомерМерчанта, РеквизитыКартыQR, СуммаОперации,
    СуммаОригинальнойОперации, НомерКарты, НомерЧека, СсылочныйНомер,
    КодАвторизации, ТекстСлипЧека)                                                      → 10

ОплатитьПлатежнойКартойCВыдачейНаличных(ИДУстройства, НомерМерчанта, РеквизитыКартыQR,
    СуммаОперации, СуммаНаличных, НомерКарты, НомерЧека, СсылочныйНомер,
    КодАвторизации, ТекстСлипЧека)                                                      → 10
```

⚠️ **Дві різні десятки.** На позиції 4 у скасуванні стоїть `СуммаОригинальнойОперации`, а у
видачі готівки — `СуммаНаличных`. Далі обидві зсунуті на одну проти дев'ятки.

#### Розкладка OUT (рядки 2086-2110)

Спільне для всіх чотирьох: `Параметры[1]`=`НомерМерчанта`, `[2]`=`РеквизитыКартыQR`,
`[3]`=`СуммаОперации`. Далі галузиться:

| Команда | Далі |
|---|---|
| `AuthorizeSales` / `AuthorizeRefund` | `[4]`=НомерКарты, `[5]`=НомерЧека, `[6]`=СсылочныйНомер, `[7]`=КодАвторизации, `[8]`=ТекстСлипЧека |
| `AuthorizeVoid` | `[5]`=НомерКарты, `[6]`=НомерЧека, `[7]`=СсылочныйНомер, `[8]`=КодАвторизации, `[9]`=ТекстСлипЧека |
| `PayByPaymentCardWithCashWithdrawal` | `[4]`=СуммаНаличных, `[5]`=НомерКарты, `[6]`=НомерЧека, `[7]`=СсылочныйНомер, `[8]`=КодАвторизации, `[9]`=ТекстСлипЧека |

⚠️⚠️ **ПАСТКА: `СуммаОригинальнойОперации` — єдиний IN-only параметр на 4000.**
У гілці `AuthorizeVoid` читання стрибає з `Параметры[3]` одразу на `[5]` — позицію 4
конфігурація **назад не забирає**. Записане туди фасадом зникне **без винятку й без сліду**,
на відміну від усіх сусідів, які IN/OUT. Не писати в неї нічого.

#### Прапорці відсіюють ДО виклику драйвера

Дві операції взагалі не дійдуть до компоненти зі знятим прапорцем (рядки 2023-2026, 2032-2036):

```bsl
Если СуммаОригинальнойОперации > 0 И НЕ ПараметрыПодключения.ЧастичнаяОтмена Тогда
    ОписаниеОшибки = НСтр("ru='Частичная отмена не поддерживается драйвером.'");
```

Те саме з `ВыдачиНаличныхДенежныхСредств` для видачі готівки. Це підтверджує двошарову модель
§2.3.1: **основний шар — прапорці**, і він на боці конфігурації. Наслідок для тестування:
гілку «чесна відмова» цих двох методів через касу перевірити **неможливо** — тільки прямим
викликом методу.

#### Пороги, які нас НЕ стосуються

`>= 3007` охороняє `ПолучитьПараметрыКарты` (7 параметрів із `СсылкаНаПлатежныйСчет` проти 6
без нього) — це читання параметрів картки, не платіжна операція. `>= 4001` охороняє тарування
ваг. У платіжній частині фасаду 4000 понад перелічене вище нічого немає.

## 3. Формати XML

Три РІЗНІ формати — не плутати між собою.

### 3.1. `ТаблицаПараметров` — опис форми налаштувань (OUT з `ПолучитьПараметры`)

Форма БПО (`Catalogs.ПодключаемоеОборудование`, `ФормаНастройки`) читає XML послідовно й
**входить у розбір лише за кореневим вузлом `Settings`**. Інший корінь → форма мовчки
лишається без жодного поля.

```xml
<Settings>
  <Page Caption="Параметри">
    <Group Caption="Підключення">
      <Parameter Name="Port" Caption="Порт" TypeValue="Number" DefaultValue="9100">
        <ChoiceList><Item Value="9100">RAW</Item></ChoiceList>
      </Parameter>
    </Group>
  </Page>
</Settings>
```

Розпізнаються: `Page@Caption`, `Group@Caption`, `Parameter@Name/@Caption/@TypeValue/
@DefaultValue/@Description/@FieldFormat/@ReadOnly`, `ChoiceList/Item@Value` (текст вузла —
представлення). Тип — атрибут **`TypeValue`** (`String`/`Number`/`Boolean`), НЕ `Type`.
Решта атрибутів ігнорується.

**Умовної видимості полів НЕМАЄ.** Механізму залежності одного параметра від значення
іншого (`DependsOn`/`EnabledBy`) у переліку атрибутів немає — попри те, що текст ІТС його
обіцяє. Це прямо визначає рішення «клас на протокол, а не один клас із перемикачем»
(див. §4).

### 3.2. `ПараметрыПодключения` — значення (IN, через `УстановитьПараметр`)

Пласке, з атрибутом **`Value`** (а не `DefaultValue`):

```xml
<Parameters>
  <Parameter Name="Host" Value="192.168.1.50"/>
</Parameters>
```

### 3.3. `ТаблицаДействий` — додаткові дії (OUT з `ПолучитьДополнительныеДействия`)

```xml
<Actions>
  <Action Name="XReport" Caption="X-звіт"/>
</Actions>
```

Пункти лягають у меню «Функции» форми налаштувань екземпляра обладнання, після «Тест
устройства»; команда називається `"A_" + @Name`, вибір кличе
`ВыполнитьДополнительноеДействие(ИмяДействия)`. Це **форма адміністратора** — для щоденних
операцій касира (напр. X-звіт у РМК) вона не годиться.

## 4. Наслідки для архітектури драйверів

- **Клас компоненти на кожен протокол** (`ECRPrivatJSON`, далі `ECRCommXBPOS1`, …), а не один
  клас із параметром-перемикачем. Причини: набори параметрів підключення в протоколів різні,
  а умовної видимості полів форма не має (§3.1) — один клас віддавав би об'єднання всіх
  параметрів усіх протоколів, і всі були б завжди видимі. Плюс стан з'єднання живе в C++ в
  об'єкті драйвера. Ціна для 1С — один запис довідника драйверів на протокол, коду не потребує.
- **Усі класи реалізують ОДИН і той самий контракт** із §2 — прикладний код у 1С однаковий.
- ⚠️ **Тип обладнання на ВХОДІ й на ВИХОДІ — це різні рядки. Не переплутати.**
  Див. §4.1 нижче.
- **Для `KKT` і `POSTerminal` ІТС вимагає вмикати лог драйвера за замовчуванням**, а рівень
  деталізації виносити в параметри драйвера. Конфігурація справді читає `LogIsEnabled` і
  `LogPath` із `DriverDescription` — заповнювати обидва.
- **Архітектура постачання.** ІТС вимагає багатокомпонентної архітектури (інтеграційний
  компонент + основна поставка з інсталятором) для всіх типів, крім дисплея покупця, пристроїв
  вводу, принтерів чеків, ТЗД і ваг — тобто і для `POSTerminal`, і для `LabelPrinter`.
  **Свідоме рішення проєкту — лишатись однокомпонентними** (`IntegrationComponent="false"`,
  `MainDriverInstalled="true"`): конфігурація БПО архітектуру не перевіряє, а інсталятор
  суперечить вимозі «нічого ставити руками». Ціна рішення: сертифікат «1С:Совместимо»
  потребуватиме переробки схеми постачання.
- **Прогрес і скасування довгих операцій контрактом НЕ передбачені.** У штатному обробнику
  немає ні переривання операції, ні обробки `ВнешнееСобытие` для еквайрингу. Онлайн-прогрес
  можливий лише накладкою над тим самим об'єктом драйвера, який 1С уже тримає:
  `МенеджерОборудованияКлиент.ПолучитьПодключенноеУстройство(ИД).ОбъектДрайвера`. Другий
  об'єкт компоненти для цього НЕ годиться — доступ до термінала монопольний.
- ⚠️ **ЗМІРЯНО: прогрес із компоненти неможливий у ЖОДНІЙ редакції.** Перевірено на живій
  1С 8.3.27 (`ProbeBPO.БлокироватьИСобытия`, 2026-08-31): `Асинх`-варіант методу платформа
  генерує сама, але виклик **не виходить із клієнтського потоку** — проміс резолвиться після
  синхронного виконання. За 5 секунд блокування `ПодключитьОбработчикОжидания` з інтервалом
  1 с **не спрацював жодного разу**, а всі 10 подій прийшли одним пакетом через 23 мс ПІСЛЯ
  повернення (усередині компоненти вони випускалися за розкладом — 1С тримала їх у буфері).
  В ua ще й виклик синхронний за побудовою.
  **Наслідок:** штовхати прогрес із компоненти марно. Онлайн-статус у РМК показує **власне
  вікно очікування конфігурації** — інтегруватися треба з ним, а не робити своє.
  Опційні події `ВнешнееСобытие` лишаються корисними лише для **прямого** класу
  `ECRPrivatJSON` з його асинхронним API (`НачатьОплату` + полінг), де потік не заблокований.

### 4.1. ⚠️ `EquipmentType`: на вході — ім'я значення переліку, на виході — рядок ІТС

**НА ВХОДІ** (`УстановитьПараметр("EquipmentType", …)`) 1С передає **ім'я значення переліку
метаданих**, а НЕ англійський рядок із таблиці ІТС. Для еквайрингу це
**`ЭквайринговыйТерминал`**. Драйвер, який чекає `POSTerminal`, тип не впізнає.

Ланцюжок (звірено в обох редакціях):

```bsl
// ru: Catalogs/ПодключаемоеОборудование/Ext/ManagerModule.bsl:269
ДанныеУстройства.Вставить("ТипОборудованияИмя", XMLСтрока(Выборка.ТипОборудования));
// ua: те саме через МенеджерОборудованияВызовСервера.ПолучитьИмяТипаОборудования(),
//     який віддає МетаОбъект.ЗначенияПеречисления[Индекс].Имя

// далі, ПодключаемоеОборудованиеДрайверКлиент:347
Ждать ОбъектДрайвера.УстановитьПараметрАсинх("EquipmentType", ПараметрыПодключения.ТипОборудованияИмя);
```

Ім'я значення в `Enums/ТипыПодключаемогоОборудования` — `ЭквайринговыйТерминал` в **обох**
конфігураціях (перевірено читанням XML переліку).

**Правило:** порівнювати **толерантно** — без урахування регістру, приймаючи і
`ЭквайринговыйТерминал`, і `POSTerminal`. Коштує нічого, страхує від наступної редакції.

**НА ВИХОДІ** (`EquipmentType` в `DriverDescription`) значення суто **інформаційне**:
`МенеджерОборудованияКлиент.ПолучитьОписаниеДрайвера` кладе його в `Параметры.ТипОборудования`
як рядок і ніде не звіряє з переліком. Тож `POSTerminal` за конвенцією ІТС там безпечний.

### 4.2. Атрибути `DriverDescription`, які конфігурація реально читає

`МенеджерОборудованияКлиент.ПолучитьОписаниеДрайвера:312-329`; усе інше в XML ігнорується:

| Атрибут | Куди лягає |
|---|---|
| `Name` | `НаименованиеДрайвера` |
| `Description` | `ОписаниеДрайвера` |
| `EquipmentType` | `ТипОборудования` (рядок, інформаційний) |
| `DriverVersion` | `ВерсияДрайвера` |
| `IntegrationComponentVersion` | `ВерсияИнтеграционногоКомпонента` |
| `DownloadURL` | `URLЗагрузкиДрайвера` |
| `LogPath` | `ЛогДрайвераПутьКФайлу` |
| `IntegrationComponent` | `ИнтеграционныйКомпонент` |
| `MainDriverInstalled` | `ОсновнойДрайверУстановлен` |
| `LogIsEnabled` | `ЛогДрайвераВключен` |
| `LocalizationSupported` | `ПоддерживаетсяЛокализация` |
| `IsEmulator` | `ЭтоЭмулятор` |

Булеві читаються як `ВРег(значення) = "TRUE"` — писати `true` або `TRUE`; **`1` не спрацює**.
`LocalizationSupported` виставляти не треба: `УстановитьЛокализацию` на 3004 не викликається
(§2.1).

## 5. Розбіжність із документом ІТС

Документ ІТС «Разработка драйвера для подключения оборудования локально к устройству
пользователя» описує **інші, довгі** імена — `ПодключитьОборудование (ConnectEquipment)`,
`ПараметрыОборудования (EquipmentParameters)`, `ТестированиеОборудования` — причому в розділі
«Использование оборудования пользователем в процессе работы», тобто саме як контракт
1С → компонента. `УстановитьПараметр` і `ПолучитьПараметры` в документі не згадуються жодного
разу.

Найпростіше пояснення: **документ відстав від бібліотеки**.

**Правило проєкту, що з цього випливає:** імена методів беремо з **конфігурації**, формати XML —
з ІТС (там вони збіглися з парсером). Документ ІТС лишається джерелом для таблиці типів
обладнання, складу `DriverDescription` і вимог до логування.

## 6. Перевірене на живій 1С і що лишилось відкритим

### 6.1. ✅ Закрито зондами `ProbeBPO` (1С 8.3.27, версія компоненти 3.0.3.130, 2026-08-31)

> Саму зонд-компоненту **видалено після того, як вона відповіла** — вона не мала їхати в
> продуктову DLL (її `БлокироватьИСобытия` блокує потік на 5 секунд). Шукати її в коді не
> треба: результати нижче й у §4 — це все, що вона дала, а регресію тримає
> `tests/ecr_native_host.cpp`. Історія зонда лишилась у git.

- **IN/OUT-параметри працюють повністю.** `ВходВыход7` повторив справжню сімку оплати: усі
  шість параметрів після `ИДУстройства` повернулись зміненими, сам `ИДУстройства` (тільки IN)
  лишився недоторканим, багаторядковий `ТекстСлипЧека` пройшов межу без втрат. Шлях
  `VariantHelper::clear()` → `FreeMemory` на пам'яті, яку виділила **платформа**, коректний.
- **Число IN/OUT: тип — `VTYPE_R8`** (`amountVt` = 5). Сума прочитана як `100.500000`,
  повернута як `100,51` — **дробова частина вціліла**. Конверсії ядра (`operator double()`)
  цей тип приймають, розширювати їх під `I8`/`UI4`/`INT` **не потрібно**.
- **Прогрес із компоненти неможливий** — деталі й цифри у §4.

### 6.2. Відкрите

1. **Вибір класу-фасада з боку конфігурації** — окремим записом довідника драйверів на кожен
   фасад чи розширення визначає версію БПО й підставляє клас. За агентом сесії SimplyConnect;
   впливає лише на іменування класів.
2. **Чи є у формі РМК куди підключити онлайн-статус** — за агентом сесії SimplyConnect.
   Врахувати зміряний факт із §4: під час виклику драйвера клієнтський потік мертвий, тож
   якщо те вікно показує живий статус, механізм там принципово інший, ніж припускалося.

### 6.3. Свідомо поза обсягом компоненти

- **Журнал транзакцій.** Рішення 2026-08-31: це робота розширення 1С. Реєстр
  `СМП_НезавершенныеОперацииЭквайринга` **уже зроблено** на боці розширення: намір пишеться до
  звернення до термінала, знімається після відповіді, correlation id — штатний
  `ИдентификаторЗапроса` з параметрів операції. Від компоненти для цього не потрібно нічого;
  вона стану між сеансами не тримає, лишається лише файловий лог. Контекст, чому питання
  взагалі виникало: в ua немає ні модуля `ЛогированиеОперацийБПО`, ні реєстру
  `ПлатежныеОперации`, тож слід операції поза обліковим документом там веде саме розширення.
- **Вікно прогресу.** У РМК воно вже є і на живому обладнанні працює; компонента до нього
  нічого не додає (§4).

**Скасування платежу** в обох фасадах виконується **поверненням за RRN** — власної операції void
протокол у нашій реалізації не має. Керує параметр підключення `VoidAsRefund` (Boolean, дефолт
**увімкнено**, рішення користувача 2026-08-31); знятий → чесна відмова. Порожній RRN → `BAD_INPUT`.
Часткове скасування на 4000 відхиляється явно.
| `ECRPrivatJSON` | не БПО — власний прямий API (`docs/integration-1c/ecr-privatjson.md`). **Лишається** поряд із БПО-фасадами: тільки він дає асинхронну оплату, скасування й онлайн-статус, і тільки він перевірений на реальному терміналі |
