# Архітектура драйвера ECRPrivatJSON (платіжний термінал ПриватБанк)

Пілотний драйвер обладнання поверх [фундаменту device-core](device-core.md). Реалізує
JSON-протокол платіжних терміналів ПриватБанку (COM/TCP) і виставляє в 1С компоненту
**`ECRPrivatJSON`**. Цей документ описує **внутрішню будову** драйвера — для подальшого
розвитку й додавання операцій. Хто пише **прикладний 1С-код** проти готового драйвера — читає
[docs/integration-1c/ecr-privatjson.md](../integration-1c/ecr-privatjson.md).

Специфікація протоколу — [docs/ECR_Privat_JSON_Protokol.md](../ECR_Privat_JSON_Protokol.md).
Імена звірені з кодом (`src/drivers/ecr_privatjson/*`, `src/components/AddinECRPrivatJSON.*`,
`src/platform/*`).

> **Історична примітка.** До 2026-07 у проєкті був інший драйвер `AddinECRPrivatJSON`
> (`src/protocols/` + `src/helpers/ECRPrivatJSON/`), **видалений як непрацездатний**
> (два непоєднані буфери прийому). Його заміняє **цей** драйвер поверх device-core. Опис
> старої реалізації лишився в git-історії; тут не повторюється.

## 2. Прикладний протокол (стисло)

Повна спека — окремо; для розуміння драйвера достатньо:

- **Кадр** = UTF-8 JSON + термінатор `0x00` (C-рядок). Хендшейк-`PingDevice` має ще й **провідний
  `0x00`** на початку. Кодуванням делімітера опікується `NullTerminatedFramer`, не драйвер.
- **Структура повідомлення:** `{method, step, params{}, error(bool), errorDescription}`. Кореляція
  запит/відповідь — **за полем `method`** (окремого id немає; відповідь ехом дублює `method`).
- **Дві категорії методів:**
  - **несервісні** (власне `method`: `PingDevice`, `CheckConnection`, `GetTerminalInfo`,
    `Purchase`, `Refund`, `GetReceiptInfo`, …) — «займають» термінал, ідуть **primary**-доріжкою,
    їх не можна слати під час активної операції;
  - **`ServiceMessage`** (з `params.msgType`: `identify`, `getLastStatMsgCode`, `interrupt`,
    `correctTransaction`, …) — легкі, дозволені **паралельно** з операцією, ідуть **service**-доріжкою.
- **`deviceBusy`** — відповідь-відмова термінала на конкурентний несервісний запит.
- **`getLastStatMsgCode`** — опитування стану термінала під час операції (коди 0–11, §6.2).
- **Скасування:** сервісний `interrupt` → термінал шле `interruptTransmitted` (ack) + фінальну
  primary-відповідь операції з `responseCode 1001`.

Топологія — **монопольний постійний доступ**: один активний конект, термінал слухає (сервер),
каса конектиться (клієнт), TCP-порт за замовч. `2000`, COM — `115200 8N1`.

## 3. Кодек — `EcrJsonCodec`

`src/drivers/ecr_privatjson/EcrJsonCodec.{h,cpp}`. Чистий, без стану; делімітером `0x00` **не
оперує** (це `NullTerminatedFramer`):

```cpp
static std::vector<uint8_t> BuildRequest(method, step, params);   // {method,step[,params]} → UTF-8 байти; params==nullptr → без поля
static ParsedResponse       Parse(frameNoDelimiter);              // повний розбір; невалідний JSON → {valid=false}, БЕЗ винятку
static bool                 PeekMethod(frame, method, msgType);   // легкий парс лише method (+ msgType для ServiceMessage)
```

`ParsedResponse` = `{method, step, params, error, errorDescription, msgType, valid}`.

## 4. Класифікатор — `EcrPrivatJsonClassifier`

`src/drivers/ecr_privatjson/EcrPrivatJsonClassifier.{h,cpp}`, реалізує `IFrameClassifier`. Уся
логіка розрізнення потоків (спека §5). `Classify(pending, frame)`:

1. Розпарсити `method` (і `params.msgType`, якщо `method=="ServiceMessage"`).
2. `method` == `method` активного **primary** (не-`ServiceMessage`) → `{PrimaryResponse}`.
3. `method=="ServiceMessage"`:
   - `msgType` корелює з активним **service**-запитом (у т.ч. `interrupt`→`interruptTransmitted`,
     `correctTransaction`→`correctionTransmitted` — це **відповіді** на service-запити, НЕ
     unsolicited; а також `identify`/`getLastStatMsgCode`/`getDiscountName`) → `{ServiceResponse}`;
   - `msgType=="deviceBusy"`: є активний primary → `{RejectPrimary, Busy}`; немає → `{Unsolicited}`;
   - `msgType=="methodNotImplemented"`: кадр не називає відхилений метод, тож при обох pending →
     `{RejectBoth}` (→ desync); при одній доріжці → `{Reject*, Unsupported}`;
   - інший `msgType` без відповідного pending → `{Unsolicited}`.
4. `method` == `method` активного **service** → `{ServiceResponse}`.
5. Інакше → `{Unsolicited}`.

Двохдоріжкова модель прямо підтримує **полінг статусу під час операції**: `Purchase` займає
primary, а `getLastStatMsgCode` летить service-доріжкою й **не** провокує `deviceBusy`.

## 5. Життєвий цикл — `Connect`

`EcrPrivatJsonDriver::Connect(connString)` реалізує **еталонну схему буквально** (спека:
«гарантує роботу з терміналами будь-яких вендорів»), перевикористовуючи `DeviceSession` короткими
сесіями для хендшейку/Identify і однією постійною для основного режиму:

1. **Розбір рядка** (`ParseConnString`): `tcp://host:port` (IPv6-літерали не підтримуються) або
   `COMn[:baud[,8,N,1]]` (з рядка береться лише baud, дефолт `115200`; формат кадру завжди 8N1,
   хвіст після baud ігнорується). Скидання `vendor_`/`model_`, `job_.ResetToIdle()`.
2. **Хендшейк** (коротка сесія): `MakeSession` → колбеки (лише до `Start()`) → `Start()` →
   `RequestPrimary(PingDevice, FrameOptions{leadingDelimiter=true})` → перевірка → **`Stop()`
   (дисконект)** → пауза 1с.
3. **Identify** (коротка сесія): нова сесія → `RequestService(ServiceMessage/identify)` → зберегти
   `vendor`/`model` з `params` (best-effort) → **`Stop()` (дисконект)**.
4. **Постійний режим:** нова `session_`, лишається відкритою; реконект — супервізор `DeviceSession`
   (`autoReconnect`, backoff). На **цю** сесію (і лише на неї) `Connect()` ставить
   `SetConnectionStateHandler` — джерело переходів стану зв'язку (§5.2). Далі — `SetLinkState(Ready)`
   **до** `session_->Start()` і `EnsureRecoveryRunning()` після нього.

`MakeTransport`: TCP → `TransportTCP(host, port)`; COM → `TransportCOM(port, baud, 8, 'N', 1.0f)` —
драйвер **явно** передає baud (дефолт `TransportCOM` = 9600). `MakeSession` збирає
`DeviceSession(transport, NullTerminatedFramer, EcrPrivatJsonClassifier)`, ставить колбеки й
(якщо увімкнено) `SetWireTraceHandler` для wire-трасування. Хук `SetUnsolicitedHandler` —
`NEUTRAL_REPORT_DEBUG` із кадром: `deviceBusy` без нашого запиту — це пізній дубль на
таймаутнутий запит (протокол §6.1), інших самостійних нотифікацій протокол не документує.

`Disconnect()` — порядок важливий (кожен крок куплений дефектом):

```
closing_ = true            // хук і фоновий джоб бачать і виходять
job_.Join()                // фінансову операцію НЕ рвемо
session_->Stop()           // усі pending → Stopped негайно; dispatcher join-нуто,
                           //   тож нових хуків (і нових стартів джоба) більше не буде
recoveryJob_.Join()        // ПІСЛЯ Stop(): до нього джоб міг стояти в RequestPrimary до 120 с
session_.reset()
SetLinkState(Disconnected, "closed")
closing_ = false
```

Сон у джобі — `SleepInterruptible` (кроками по 100 мс із перевіркою `closing_`): голий
`sleep_for(backoff)` ззовні не перервати, і `Отключить` під час мовчання термінала висів би на
`recoveryJob_.Join()` до кінця інтервалу.

Симетрично в `Connect()`: якщо `session_->Start()` не вдався — `SetLinkState(Disconnected,
"connect_failed")` → `session_->Stop()` → `recoveryJob_.Join()` → `session_.reset()`. `Stop()`
**перед** `reset()` не косметика: при `opened == false` `Start()` лишає dispatcher і супервізор
живими, хук уже стоїть, і без `Stop()` він міг би виконати `EnsureRecoveryRunning()` над знищеною
сесією (use-after-free).

`Connect()` **не скидає** `lastOutcome_` (§6.7): факти про попередній обрив належать операції, а не
сесії, і каса могла їх ще не забрати.

### 5.1. Семантика відключення (перевірено на реальному Newland N950, 2026-08-29)

Факти, встановлені наскрізним експериментом (лог + зонд по TCP при закритій 1С):

- **Закриття граційне:** `TransportTCP::Close()` = `shutdown(SD_BOTH)` → `closesocket` —
  термінал отримує коректний FIN. Порядок подій Disconnect правильний і достатній.
- **У протоколі НЕМАЄ «прощального» повідомлення.** Повний перелік `msgType` специфікації
  не містить disconnect/bye; еталонна схема прямо приписує касі «тримаємо з'єднання
  відкритим… НЕ ВІДКЛЮЧАЄМОСЬ». Тобто сказати терміналу «каса пішла» протокольно неможливо.
- **Індикатор «підключено» на терміналі ≠ живий TCP.** Зелена позначка N950 (ProstoPOS) —
  стан «режим касового суміщення активний»: вмикається першим хендшейком і скидається
  ЛИШЕ ручним «Розірвати з'єднання» у меню термінала (штатний вихід у standalone-режим).
  Після коректного `Disconnect()` вона лишається — це поведінка застосунку вендора.
- **Монополія діє лише при активній сесії.** Поки драйвер тримає з'єднання — другий клієнт
  отримує TCP-конект, але термінал йому не відповідає (silence). Після `Disconnect()`
  термінал відповідає новому клієнту на handshake навіть із «зеленим» індикатором —
  доведено зондом при повністю закритій 1С.

Практичний наслідок для фасаду/1С: орієнтир стану — `Подключен` (тобто `IsReady()`, §5.2) і лог,
не екран термінала; рекомендація `Отключить()` у `ПриЗакрытии` — у
`docs/integration-1c/ecr-privatjson.md` §2.1.

### 5.2. Стан зв'язку — `LinkState`

`connected_` транспорту означає «сокет відкрився», а не «термінал нас чує». На реальному N950 це
різні речі: поки застосунок термінала вважає стару сесію живою, новому клієнту він **не відповідає**
(монополія, §5.1). Тому готовність — окремий стан **драйвера**:

| Стан | Що означає | Як сюди потрапляємо |
|---|---|---|
| `Disconnected` | сесії нема | до `Connect()`; після `Disconnect()`; невдалий `Start()` |
| `Connecting` | сесія є, термінал **не підтвердив** готовність | сокет упав (супервізор стукає); TCP піднявся, Ping ще не пройшов; Ping у тишу монополії; `Timeout`/desync фінансової операції |
| `Ready` | термінал відповів на Ping — чує нас, вільний **або** зайнятий нашою операцією | `Connect()` успішний; після реконекту — Ping дав `Response` **або** `deviceBusy` |

**`Ready` ≠ `connected_`.** Публічний `IsReady()` — це `linkState_ == Ready`; внутрішній
`IsConnected()` лишається «сокет відкритий» і потрібен там, де без сокета немає сенсу
(`EnsureRecoveryRunning`, `CloseDevice` БПО-фасаду). У 1С `Подключен` віддає саме `IsReady()`
(§7.0), а `EcrPrivatJsonAcquiring::IsConnected()` для БПО — навпаки, **сокет**: `Close()` має
закривати сесію в будь-якому стані.

`Connect()` ставить `Ready` **до** `session_->Start()`: хендшейк-Ping пройшов секунду тому (крок 2),
повторювати його немає навіщо. Якби `Ready` ставився після `Start()`, хук `up=true` (він уже в черзі
dispatcher-а) побачив би `Connecting` і запустив зайвий Ping — рівно тоді, коли 1С після
`Подключить` одразу кличе оплату: `CONCURRENT` на першій операції зміни.

**Ping після реконекту, а не повторення еталонної схеми.** Супервізор `DeviceSession` після обриву
робить `Close → Open` **TCP і все** — нічого протокольного. Драйвер доганяє це сам: хук `up=true`
запускає фоновий джоб, крок 0 якого (`EnsureReady`) шле `PingDevice` з тим самим провідним `0x00`,
що й хендшейк, поки не отримає `Response` або `deviceBusy`. Окремих сесій і `Identify` не
повторюємо — вендор/модель відомі, `DeviceSession` не змінюється.

`Timeout` Ping — **не аварія**, а очікуваний стан «термінал ще тримає стару сесію», тож повтор без
обмеження кількості (супервізор стукає так само без обмеження: `reconnectMaxTries=0`).

> ⚠️ **`MarkSynchronized()` — перед КОЖНИМ Ping**, не лише на вході в цикл. Після таймауту primary
> сесія в desync, а `DoRequest` відбиває **будь-який** primary до дроту (`DeviceSession.cpp:175`) —
> наш Ping відновлення теж. Зняти прапорець «на вході» недосить: `Timeout` самого Ping ставить
> desync знову, і один мовчазний Ping отруював би всі наступні. Гроші при цьому захищає **не**
> desync, а гейт §6.7: `MarkPending` уже стоїть, тож між зняттям desync і `Ready` від користувача
> на дріт не виходить нічого — фінансові виклики отримують `UNKNOWN_OUTCOME`, нефінансові
> `RECONNECTING`. Ping службовою доріжкою не працює принципово: відповідь має
> `method == "PingDevice"`, класифікатор корелює її лише з primary.

**Епоха зв'язку — `linkEpoch_`.** Гонка, яку вона закриває: Ping отримав `Response`, і в ту саму
мить сокет упав. Без епохи порядок «джоб пише `Ready`» / «хук пише `Connecting`» довільний, і при
програші лишається `Ready` на мертвому сокеті — а наступний `up=true` уже не полагодить, бо
`EnsureRecoveryRunning` побачить `needReady == false`. Тому `SetLinkState(Ready, …, epoch)` записує
`Ready` **лише зі збіжною епохою**, а епоха — це **покоління З'ЄДНАННЯ, не покоління `Ready`**:
`++linkEpoch_` робиться на **кожному** записі не-`Ready`, **до** перевірки «той самий стан»; подія
при незміненому стані не емітиться.

> Перша редакція інкрементувала епоху лише на **виході з `Ready`**, а перевірку «той самий стан»
> робила раніше. Але в цій гонці джоб працює в `EnsureReady`, тобто стан **уже** `Connecting`; хук
> `up=false` при другому обриві потрапляв на `prev == target` і виходив **без інкременту** — і
> `Ready` зі старою епохою проходив guard. Ping, відправлений у сокет S, не має піднімати `Ready`,
> якщо сокета S уже нема, — незалежно від того, в якому стані ми були на момент його падіння.

**TCP keepalive — завжди, без опції** (`TransportTCP::Open`, одразу після `m_socket = sock`):
`SO_KEEPALIVE` + `SIO_KEEPALIVE_VALS` з `idle = 10 с`, `interval = 1 с` (кількість проб у Windows
фіксована — 10). Мертва лінія виявляється за ~20 с: `recv` у reader повертає помилку → стан вниз →
супервізор. Нуль протокольного трафіку, термінал не турбуємо, працює й під час операції. Невдача
`setsockopt`/`WSAIoctl` — `WARN` і продовжити. Опція свідомо не заводиться: `TransportTCP`
спільний з `LabelPrinter`, і принтеру keepalive не шкодить. Протокольного heartbeat у простої
**не** робимо — він не розв'язує головного (термінал після обриву наших запитів не бачить).

**Подія `connection`** (лише прямий API, після `ВключитьСобытия`) — при кожній **зміні** стану:
`{state: "connecting"|"ready"|"disconnected", reason}`, де `reason` — `"dropped"` (обрив),
`"timeout"` (таймаут/desync фінансової операції), `"closed"` (ручний `Отключить`),
`"connect_failed"` (не вдався `Start()` персистентної сесії), порожньо для `ready`.

**Що не додано свідомо:** окремого методу `СостояниеСвязи` немає — споживача немає, стан видно з
`Подключен` і події. Публічного `PingDevice` теж немає: Ping — внутрішній механізм (хендшейк
`Connect()` і крок 0 джоба); тиха перевірка стану для 1С — `Подключен`, вона термінала не турбує.

## 6. Модель операцій

### 6.1. Потокова модель (важливо)

`RequestPrimary` **блокує** свій потік до відповіді/таймауту. Тому активна операція тримає **два
потоки**:

- **worker** (синхронний виклик 1С або worker `JobEngine`) — тримає `RequestPrimary(операція)`;
- **poller** — окремий потік, піднятий на час операції: раз на `kPollIntervalMs` (500мс)
  шле `getLastStatMsgCode` через `RequestService`, оновлює `lastStatus_`, і — якщо надійшов запит
  на скасування — раз надсилає `interrupt` (service). Poller — **єдиний власник service-доріжки**.

Poller піднімається/зупиняється всередині `ExecuteInternal` через **RAII-guard**: `PollerJoin`
у деструкторі виставляє `stop` і `join`-ить потік — навіть при винятку з `RequestPrimary`
(service-доріжка звільняється, `std::terminate` не станеться).

Поза операцією живе ще один потік:

- **`recoveryJob_`** — **другий** екземпляр `JobEngine` (не `job_`): крок 0 — Ping до готовності
  (§5.2), крок 1 — з'ясування долі операції (§6.6). Чому окремий движок: `job_` несе контракт
  `СостояниеОперации` для 1С, і касовий полінг бачив би «операцію», якої касир не починав. Стартує
  його **лише** `EnsureRecoveryRunning()` — з п'яти точок (§6.6).

**`JobEngine::Start` серіалізовано `startMutex_`.** Перевірка стану йшла під `m_`, а `join()`
попереднього потоку й присвоєння `worker_` — поза ним; для одного викликача це було безпечно, а
тепер викликачів **двоє** — потік 1С (`ExecuteInternal`) і dispatcher-хук. Два одночасні `Start()`
при «не `Running`» давали б подвійний `join` того самого потоку й присвоєння joinable-потоку
(`std::terminate`). Виправлення — у платформі, не в драйвері: кожен майбутній споживач `JobEngine`
отримує його безкоштовно.

**Правило м'ютексів:** під `outcomeMutex_` і `linkMutex_` — **ні мережі, ні подій** (той самий
стиль, що `eventMutex_`). Єдиний навмисний виняток — **зовнішній `linkEmitMutex_`**: він накриває
весь `SetLinkState`, тобто перехід **разом** з емісією `connection`. Це дає контракт для 1С:

> **Порядок подій `connection` = порядок переходів; остання отримана подія відповідає поточному
> стану зв'язку.**

Без нього індикатор у РМК брехав би рівно там, де потрібен: джоб записав `Ready` і його витіснили,
хук записав `Connecting` і емітнув `connecting`, джоб прокинувся й емітнув `ready` — стан
`Connecting`, а в журналі 1С останнє `ready`. Це **не** дефект епохи: стан правильний, бреше
послідовність. Порядок узяття — **завжди** `linkEmitMutex_` → `linkMutex_` і `linkEmitMutex_` →
`eventMutex_` (усередині `EmitEvent`), ніколи навпаки: жоден обробник події не кличе
`SetLinkState`. Сам `EmitEvent` лишається **поза** `linkMutex_` — правило не порушене.

Інші події цієї форми не потребують: `outcome` пише один потік (recovery-джоб) і несе
`generation`; `status` емітить один poller на операцію, `state`/`result` — потік операції, і poller
join-иться **до** `result`. `connection` — єдина подія з двома конкурентними писачами одного стану.

**Send-арбітр (`GateSend`, 0.1с):** спека забороняє слати дві команди одночасно. `DeviceSession`
серіалізує лише в межах доріжки, тож драйвер має власний send-gate з мінімальним інтервалом
`kSendGapMs` (100мс) поверх **обох** доріжок; кожне фактичне відправлення проходить через нього.

### 6.2. `getLastStatMsgCode` → `LastStatus`

Poller зберігає останній код у `lastStatus_` (атомік, `-1` якщо ще не було). Мапа кодів
(`StatusText`): `0` Готово/очікування, `1` Картку зчитано, `2` Чіп-картку, `3` Авторизація,
`4` Очікування касира, `5` Друк чека, `6` Введіть PIN, `7` Картку вилучено, `8` Оберіть застосунок,
`9` Вставте/піднесіть картку, `10` Виконується, `11` Коригування транзакції.

### 6.3. Синхронні операції

`Execute(method, params, timeoutMs)` → `ExecuteInternal`. Реалізовані:
`Purchase(amount)`, `Refund(amount, rrn)`, `CheckConnection()`, `GetReceiptInfo(invoiceNumber)`,
`Audit(merchantId="0")` (X-звіт, §5.17), `Verify(merchantId="0")` (Звірка/Загальний звіт, §5.18),
плюс `Execute("GetTerminalInfo", …)`.

**Обов'язкові поля params оплати/повернення** (`FillPaymentDefaults`, спека §5.1.1/§5.2.1):
`Purchase`/`StartPurchase` і `Refund`/`StartRefund` перед відправленням дозаповнюють
`discount:""`, `merchantId:"0"`, а Purchase — ще `facepay:"false"`. Реальний термінал
(Newland N950, інцидент 2026-08-29) без цих полів відбиває запит кодом `1000`
«Введіть discount» — еталонна каса ПриватБанк шле їх завжди. Дефолти не перетирають
значення, передані через `extra`; `subMerchant` свідомо НЕ додається (спека дозволяє
поле лише після реєстрації субмерчанта в банку). Регрес-тест — строгий емулятор у
`TestDriverStrictTerminalParams` (`ecr_privatjson_selftest`). Кожна: скид прапорців скасування (у **викликача**, не в
worker — інакше cancel одразу після Start губиться) → `job_.ResetToIdle()` → `ExecuteInternal`:
забір `requestId` (для фінансових) → гейт §6.7 → `IsConnected` → `IsReady` (§6.5) → підняти poller
(RAII) → `GateSend` → `RequestPrimary` → тригер «доля невідома» (§6.7) або мапінг у
`ResultEnvelope`.

### 6.4. Асинхронний API (поверх `JobEngine`)

`StartOperation(method, params, timeoutMs)` (та обгортки `StartPurchase`/`StartRefund`) —
неблокуючий старт: `job_.Start([...]{ return ExecuteInternal(...); })`. 1С опитує:

- `OperationState()` → `JobState` (`Idle=0, Running=1, Interrupting=2, Done=3, Error=4`);
- `TryGetOperationResult(out)` → `true` при `Done/Error`;
- `CancelOperation()` = `RequestInterrupt()` (виставити прапорець для poller) + `job_.RequestCancel()`
  (гардовано `Running→Interrupting`).

**Poll-based, без обов'язкових подій:** стан операції 1С **опитує**, а не отримує подіями.

### 6.5. Мапінг результату — `MapResult`

`RequestStatus` → `ResultEnvelope`:

| `RequestStatus` | `ResultEnvelope` |
|---|---|
| `Response` | розбір кадру: `payload=params`, `code=responseCode` (або `ERROR`/`0000`), `ok=!error` |
| `Busy` | `Fail("DEVICE_BUSY", "Термінал зайнятий")` |
| `Unsupported` | `Fail("UNSUPPORTED", "Метод не підтримується терміналом")` |
| `Timeout` | `Fail("TIMEOUT", "Немає відповіді термінала")` |
| `Disconnected` | `Fail("DISCONNECTED", "Обрив зв'язку з терміналом")` |
| `SendFailed` | `Fail("SEND_FAILED", "Помилка відправки")` |
| `Stopped` | `Fail("STOPPED", "Операцію перервано")` |
| `Concurrent` | `Fail("CONCURRENT", "Операція вже виконується")` |
| `Desynchronized` | `Fail("DESYNC", "Потрібне відновлення зв'язку")` |
| невалідний кадр | `Fail("BAD_RESPONSE", "Невалідна відповідь термінала")` |

`ok` визначає прапорець `error` термінала (спека: Partial approval `0010` приходить із `error:false`
— теж `ok:true`).

Два коди в цю таблицю не входять, бо їх ставить не `MapResult`, а сам `ExecuteInternal` **до**
дроту: `UNKNOWN_OUTCOME` (доля фінансової операції невідома, §6.7) і `RECONNECTING` (зв'язок
відновлюється, §5.2). Порядок перевірок на вході `ExecuteInternal` — **три різні стани, три різні
коди**, саме в такій послідовності:

```cpp
if (IsFinancial(method) && Pending()) { EnsureRecoveryRunning(); return BuildUnknownOutcome(); } // 17
if (!IsConnected())                    return Fail("NOT_CONNECTED", …);   // 1: сесії/сокета нема
if (!IsReady())                        return Fail("RECONNECTING",  …);   // 18: сокет є, Ping не пройшов
```

`!IsReady()` без `IsConnected()` перед ним перекрив би `NOT_CONNECTED` для всіх викликів до
`Connect()` і після `Отключить` — каса чекала б реконекту, якого нікому робити. `RECONNECTING`
стосується **будь-якого** методу, не лише фінансового.

### 6.6. Фоновий джоб відновлення — `recoveryJob_`

> Попередня реалізація — синхронна процедура відновлення прямо в `ExecuteInternal`, із прапорцем
> захисту від рекурсії й лімітом у 5 спроб полінгу — **прибрана повністю** (2026-09; імена шукати в
> git-історії, у коді їх більше немає). Вона мала три дефекти, кожен про гроші: справжній обрив
> (`Disconnected`) відновлення
> взагалі не запускав; результат `GetReceiptInfo("")` — «останній чек у пакеті», хоч би чий, —
> ставав **результатом нашої операції**; `MarkSynchronized()` викликався безумовно через 2.5 с
> (5 × 500 мс), коли термінал ще вів операцію.

Відновлення — це **фоновий джоб** `recoveryJob_` (другий `JobEngine`, §6.1) із тілом
`RecoveryJob(generation)` з двох кроків:

- **Крок 0 — готовність** (`EnsureReady`, §5.2): якщо `!IsReady()` — цикл `PingDevice` із backoff,
  доки термінал не відповість (`Response` **або** `deviceBusy` — обидва означають «чує нас»).
  `Disconnected`/`Stopped` → вихід (перезапустить хук); `closing_` → вихід.
- **Крок 1 — з'ясування долі** (`CaptureOutcome(generation)`), і **лише** якщо стан долі —
  `Pending` того самого покоління. З'ясування після `Ready` не випадково: полінг статусу в тишу
  монополії дав би хибний `TERMINAL_BUSY`.

`CaptureOutcome`:

1. `PollStatusOnce(code)` циклом із кроком `kPollIntervalMs` (500 мс), доки код не стане `0`
   («термінал у спокої», §6.2), але не довше `outcomeIdleWaitMs_` (дефолт `kOperationTimeoutMs`, 120 с; скорочується швом `SetOutcomeTimingForTest` —
   стільки термінал може вести операцію: касир вводить пін). Кожна ітерація перевіряє `closing_` і
   покоління; `Disconnected`/`Stopped` від `PollStatusOnce` → вихід **без запису** (`ABORTED`) —
   продовжувати на непідтвердженому з'єднанні не можна, наступний `up=true` приведе сюди знову
   через крок 0.
2. `terminalIdle = (код == 0)`.
3. `MarkSynchronized()` — **в обох** випадках: після спокою — штатно; після вичерпання ліміту — бо
   лишити сесію в desync назавжди нікому було б зняти (гейт після `Resolved` не діє), а нова
   операція чесно отримає `deviceBusy`/`Timeout` від самого термінала. Виклик ідемпотентний:
   desync уже зняв `EnsureReady` перед Ping (§5.2). Різниця двох шляхів видима у знімку:
   `terminalIdle` і `factsCode`.
4. `facts = RequestReceiptFacts("")` — **вузький** приватний виклик (`GateSend` → `BuildRequest` →
   `RequestPrimary` з **операційним** таймаутом 120 с → `MapResult`), **без** `EmitEvent`, без
   дотику до `lastStatus_`/`interruptSent_`/`job_`. Публічний `GetReceiptInfo` (`ПолучитьЧек`)
   лишається як був. При `terminalIdle == false` замість запиту — `Fail("TERMINAL_BUSY", …)`.
5. Під `outcomeMutex_`, якщо покоління збігається: `state = Resolved`, записати `terminalIdle` і
   `facts`.
6. Один рядок `NEUTRAL_REPORT_WARN` «Доля операції з'ясована» зі знімком (`generation`, `reason`,
   `requestId`, намір, `startedAt`, `capturedAt`, `terminalIdle`, `factsOk`/`factsCode`,
   `responseCode`, `rrn`, `invoiceNumber`, `amount`, `date`/`time`) — **без `pan` і без тексту
   чека**. Це єдиний слід, якщо каса знімок не забрала. Потім `EmitEvent("outcome", …)`.

Повернене значення джоба **не читається** — воно лише сигнал завершення для `JobEngine`; факти
беруть із `lastOutcome_`.

**`EnsureRecoveryRunning()` — єдина ідемпотентна точка старту**, і в неї **п'ять** викликачів:

| Викликач | Навіщо |
|---|---|
| `ExecuteInternal` після `MarkPending` | штатний шлях: операція провалилась |
| dispatcher-хук, `up == true` | сокет піднявся після обриву → Ping до готовності |
| гейт §6.7 | самозцілення: `Pending` є, а джоба немає |
| `InquireLastOutcome` | те саме самозцілення з боку 1С |
| `Connect()` після `session_->Start()` | ручний реконект із 1С (`Отключить`/`Подключить`) при збереженому `Pending` |

Стартує, коли є **що** робити: зв'язок не готовий (потрібен Ping) **або** є нерозв'язане питання
про долю; без сокета — no-op. Чому не «рівно один раз з одного місця»: `CaptureOutcome` міг
записати `Resolved`, але лямбда ще не повернула — `JobEngine` досі `Running`, і `Start()` нової
операції поверне `false`; без самозцілення покоління 2 лишилося б `Pending` назавжди, а гейт
блокував би все.

### 6.7. Доля операції після обриву

Принцип, з якого все випливає: **компонента з'ясовує факти, каса вирішує.** Драйвер інкапсулює
протокол (дочекатися спокою → забрати чек) і віддає **факти**: є чек на суму X о 12:34:07, RRN
такий-то, `responseCode` такий-то. Рішення «це наша транзакція, зараховуємо» приймає 1С, де є
реєстр намірів. Компонента ніде не пише «збіглося».

**Тригер.** Після `RequestPrimary` **фінансового** методу (`IsFinancial` — whitelist
`{Purchase, Refund}`) доля вважається невідомою, якщо статус ∈ {`Timeout`, `Disconnected`,
`SendFailed`, `Stopped`} **або** `session_->IsDesynchronized()`. Друга частина ловить `RejectBoth`,
який переліком статусів пропускається. `Busy`, `Unsupported` і `Concurrent` — **усі три за
відсутності desync** — відомі однозначно й тригером не є; при `desync` кожен із них іде гілкою
`DESYNC`. Нефінансові методи при обриві поводяться як раніше.

| Умова (перевіряються саме в цьому порядку) | `reason` |
|---|---|
| `status == Timeout` | `"TIMEOUT"` |
| `status == Disconnected` | `"DISCONNECTED"` |
| `status == SendFailed` | `"SEND_FAILED"` |
| `status == Stopped` | `"STOPPED"` |
| інакше, якщо `IsDesynchronized()` | `"DESYNC"` |

`SendFailed` трактується так само консервативно, як `Disconnected`: `ITransport` не гарантує, що
при `Send < 0` на дріт нічого не пішло. `Stopped` — страховка на випадок, коли `Stop()` завершить
запит, поки термінал уже щось робив.

**Стан.** `LastOutcome` під `outcomeMutex_`: `state` (`None`/`Pending`/`Resolved`), `generation`,
`intent` (`method`, `amount`, `rrn`, `requestId`, `startedAt`), `reason`, `terminalIdle`, `facts`.
Три стани, не п'ять: успіх/невдача з'ясування читаються з `facts.ok`/`facts.code`.

`generation` бампається на **кожному** переході в `Pending` і має два призначення: головне —
**ідентифікатор питання для 1С** (каса, що вже обробила `generation=3`, бачить, що наступний виклик
повернув той самий знімок, і не зараховує його вдруге); допоміжне — guard запису в `CaptureOutcome`.

**Знімок один і смертний.** `MarkPending` затирає `lastOutcome_` **цілком**. Успішна операція його
не чіпає, але після `Resolved` гейт спав — і перша ж наступна оплата з невідомою долею, хоч через
годину, знищує факти попередньої безповоротно.

**Гейт нової оплати.** На вході `ExecuteInternal` для фінансового методу, **перед** перевірками
стану зв'язку: якщо `state == Pending` → `EnsureRecoveryRunning()` і `UNKNOWN_OUTCOME` з описом
**для касира** (залежно від `IsConnected()`: «Доля попередньої карткової операції ще з'ясовується;
зачекайте кілька секунд і повторіть» / «Зв'язку з терміналом немає; доля попередньої карткової
операції з'ясується після підключення»). Імен методів компоненти в цих текстах немає — штатний код
1С показує касиру саме `description`. **На дріт нічого не йде.** Це закриває найімовірніший шлях до
подвійного списання (касир бачить помилку й тисне ще раз, поки фоновий запит іде) і конкуренцію за
єдину primary-доріжку.

Гейт **не вічний**: вийти з `Pending` може лише `CaptureOutcome`, а він іде після `EnsureReady` без
ліміту спроб. Три випадки, коли `Ready` не настає: сокета нема (платити все одно нікуди; щойно за
адресою з'явиться термінал — `Connect()` → `Ready` → знімок → гейт знято); TCP є, термінал мовчить
(тоді **всі** операції й без `Pending` отримують `RECONNECTING`); термінал не виходить із «зайнятий»
(крок 1 обмежено `outcomeIdleWaitMs_`, `Resolved` настане з `terminalIdle:false`). Тому окремого
квитування, TTL наміру чи байпасу гейта **немає** — кнопка «забути нерозв'язане питання про гроші»
була б неправильним стимулом для касира.

Після `Resolved` гейт **не діє**: факти віддані, далі рішення каси. Нефінансові методи гейт не
блокує — вони можуть отримати `CONCURRENT`, поки фоновий запит тримає доріжку (секунди), і це
чесніше, ніж ховати діагностику саме тоді, коли адміністратор її хоче.

**Відбитий гейтом виклик споживає `requestId`.** `pendingRequestId_` забирається одноразово на
самому вході `ExecuteInternal` фінансового методу — **до** гейта й перевірок стану. Id належить
операції, яка до термінала не дійшла, і помирає з нею; інакше він прилип би до наступної операції
без сеттера.

**Bounded очікування в синхронному виклику.** Якщо зв'язок справді живий (`IsConnected() &&
!IsDesynchronized()` — де-факто це `SendFailed` без закриття транспорту), `ExecuteInternal` чекає
знімок до `kOutcomeSyncWaitMs` = 8 с, кроком 500 мс, виходячи за першою з умов: «`Resolved` мого
покоління» або «джоб більше не працює». Для синхронного БПО-шляху, де потік 1С під час виклику
мертвий, це єдиний спосіб віддати факти в тому ж виклику. При `Timeout`/desync драйвер натомість
сам переводить стан у `Connecting` і віддає `UNKNOWN_OUTCOME` **негайно**: супервізор у цю мить
уже рве й перевідкриває сесію, тож «зв'язок є» тут — гонка, а знімок зробить джоб після реконекту.

**Форма `payload.outcome`** (той самий об'єкт — і в результаті операції, і в
`ИсходПоследнейОперацииJSON`, і в події `outcome`):

```json
{ "state": "pending" | "resolved" | "none",
  "generation": 3,
  "reason": "DISCONNECTED",
  "intent": { "method": "Purchase", "amount": "100.51", "rrn": "",
              "requestId": "e4b1c9d2-…", "startedAt": "2026-09-05T12:34:07.123Z" },
  "terminalIdle": true,
  "facts": { "amount": "100.51", "rrn": "…", "invoiceNumber": "…", "date": "…", "time": "…",
             "responseCode": "0000", "txnType": "1", "approvalCode": "…", "pan": "…" },
  "factsOk": true, "factsCode": "0000",
  "channelConnected": true }
```

`facts` — **сирі** поля §5.30 як є; `null`, поки `state != "resolved"` (а `factsOk` тоді `false` і
`factsCode` порожній). `intent.amount` — рядок у тому вигляді, в якому пішов на дріт (`MoneyToString`:
крапка, рівно два знаки, без групових роздільників), тож 1С може порівнювати текстово.
`intent.startedAt` — годинник **машини каси** (ISO 8601 UTC); `facts.date`/`facts.time` — годинник
**термінала** у його форматі. `channelConnected` — сокет, не готовність.

**Події.** `outcome` несе **лише** об'єкт `outcome` (без конверта `ok`/`code`) — як `status`/`state`
несуть свої дані; конверт є в `result` і в `InquireLastOutcome`. На операцію з невідомою долею
подія `result` приходить рівно **один** раз, із кодом `UNKNOWN_OUTCOME`. Події — лише прямий API
після `ВключитьСобытия`; БПО-фасади подій не мають і не матимуть.

**Чого компонента НЕ робить** (і на що розширенню 1С не варто розраховувати):

- не зіставляє чек із наміром — жодного `if (amount == intent.amount) ok = true`;
- не повторює й не сторнує фінансову операцію автоматично;
- не заповнює OUT-параметри БПО фактами чужого чека — `СсылочныйНомер`/`КодАвторизации`/
  `ТекстСлипЧека` при `UNKNOWN_OUTCOME` лишаються порожні (ревізійні шари `AcquiringBpo3004/4000`
  для цього не міняли: їхній `if (!MapEnvToBool(env)) return false;` уже дає потрібну поведінку);
- не тримає стан між сеансами: після перезапуску процесу 1С `state == "none"`, джерело правди про
  незавершені наміри — реєстр у 1С;
- не квитує знімок — запис реєстру закриває каса, без підтвердження від компоненти.

Прикладний бік (як цим користуватись із 1С) — `docs/integration-1c/ecr-privatjson.md` §8.

## 7. Фасади 1С — ДВА шляхи до одного драйвера

Драйвер віддається в 1С **двома незалежними способами**, і плутати їх не можна:

| Шлях | Класи | Коли |
|---|---|---|
| **Прямий** | `ECRPrivatJSON` | прикладний код створює об'єкт сам; є асинхронна оплата, онлайн-статус, скасування операції. Єдиний шлях, перевірений на **реальному терміналі** |
| **БПО** | `ECRPrivatBPO3004`, `ECRPrivatBPO4000` | штатна підсистема «Подключаемое оборудование»; прикладного коду не потребує взагалі |

БПО-фасади описано **не тут, а в [bpo-contract.md](bpo-contract.md)** — це контракт підсистеми,
спільний з іншими драйверами обладнання, і його джерело правди там. Тут лишається прямий фасад.

> Два класи на БПО — не дублювання, а **вимога контракту**: ревізія інтерфейсу визначає розкладку
> параметрів платіжних методів (7 проти 9), а одне ім'я методу в компоненті = одна арність.
> Деталі — `bpo-contract.md` §2.1-2.3.

**Про протокол ПриватБанку БПО-шар не знає.** Між ним і драйвером стоїть інтерфейс
`IAcquiringDriver` (`src/drivers/IAcquiringDriver.h`), а `EcrPrivatJsonDriver` під нього
загорнуто адаптером **`EcrPrivatJsonAcquiring`**
(`src/drivers/ecr_privatjson/EcrPrivatJsonAcquiring.{h,cpp}`, ціль
`driver_ecr_privatjson_component`). Адаптер перевизначає лише те, що протокол справді вміє
(`Open`/`Close`/`Probe`/`Purchase`/`Refund`/`DayTotals`/`Audit` + асинхронна трійця); `Void` і
`EmergencyVoid` лишаються дефолтною чесною відмовою — власних операцій протокол не має, і
скасування фасад робить поверненням за RRN. Він же віддає `AcquiringCapabilities`: `terminalId` =
`Model()` (справжнього TID протокол не віддає), `printSlipOnTerminal = true` (N950 друкує
квитанції сам), решта — `false`, бо часткове скасування, видача готівки, Consumer-Presented QR,
електронні сертифікати й список операцій термінал не вміє (§8). Шарування фасадів і ціна нового
протоколу — `bpo-contract.md` §2.6.

### 7.0. Прямий фасад — `AddinECRPrivatJSON`

`src/components/AddinECRPrivatJSON.{h,cpp}`. Тонка компонента: успадковує `AddInNative`,
`REGISTER_COMPONENT(u"ECRPrivatJSON", AddinECRPrivatJSON)`, тримає `EcrPrivatJsonDriver driver_`.
Реєструє 22 методи (пари EN/RU) у `RegisterMethods()` + успадкований `EnableLogging`; повний довідник методів, типів повернення
й прикладів — [docs/integration-1c/ecr-privatjson.md](../integration-1c/ecr-privatjson.md).

Два з них — про долю операції, і вони є **і** в прямому фасаді, **і** в еквайринговому
(`AcquiringFacadeBase::RegisterAsyncExtensions`, тобто в обох ревізійних фасадах БПО):

| Метод (EN / RU) | Що робить |
|---|---|
| `InquireLastOutcome` / `ИсходПоследнейОперацииJSON` | знімок долі (§6.7) рядком JSON; **без мережі**, у будь-якому стані зв'язку; спершу `EnsureRecoveryRunning()` (самозцілення) |
| `SetRequestId` / `УстановитьИдентификаторЗапроса` | покласти `ИдентификаторЗапроса` каси, що пройде у знімок прозорим рядком |

⚠️ **Інваріант: жоден із цих двох не чіпає `lastError` фасаду** — ні `ClearError()`, ні
`SetError()`. Сусіди в `RegisterAsyncExtensions` роблять `ClearError()` на старті, ці два —
**навмисно ні**: каса читає `ПолучитьОшибку()` і знімок у довільному порядку, і якби знімок чистив
помилку, читання після нього тихо давало б `0` замість `17`. Код помилки належить попередній
команді, поки наступна його не перепише. Перевіряється CHECK-ом у `ecr_native_host`.

Конвенції фасаду:

- **Синхронні операції** (`ПроверитьСвязь`/`ВерсияПО`/`Оплата`/`Возврат`/`ПолучитьЧек`)
  реєструються «голими» void-лямбдами (не через `Ret`): локальний `runSync` серіалізує
  `ResultEnvelope` у `this->result` (JSON-рядок) і кешує в `lastResultJson_`. Тому в 1С ці
  функції **повертають JSON-рядок** результату. (Обгортати їх `Ret()` не можна — перезаписав би
  корисний результат; правило з [AGENTS.md](../../AGENTS.md).)
- **Решта** (`Подключить`/`Подключен`/`НачатьОплату`/`СостояниеОперации`/`РезультатОперацииJSON`/
  `СтатусТерминала`/`Вендор`/`Модель`/`ВключитьТрассировку`/`ВключитьСобытия`) — через `Ret()`
  (bool/int/string).
- **Межа 1С — `try/catch` в кожному методі:** виняток C++ межу 1С не перетинає; при винятку —
  `REPORT_ERROR` (лог + `AddError`) і валідний `ResultEnvelope::Fail`, не сирий текст.
- `EnableLogging`/`ИспользоватьЛогирование` — успадкований (реєструвати не треба); у деструкторі —
  `driver_.Disconnect()` + `ServiceTools::DisableComponentLogging(this)`.

### 7.1. Опційні події — `ВключитьСобытия`

За замовчуванням драйвер poll-based (подій немає). `ВключитьСобытия(Истина)` ставить драйверу
`EventHandler`, що кличе `PostExternalEvent(event, dataJson)` ядра (потокобезпечний, з
poller/worker/recovery-потоку). Драйвер емітить п'ять подій (`EmitEvent`) — у 1С вони приходять як
`ВнешнееСобытие(Источник="ECRPrivatJSON", Событие, Данные)`:

| `Событие` | Коли | `Данные` (JSON) |
|---|---|---|
| `state` | старт операції | `{state:"Running", method}` |
| `status` | зміна `getLastStatMsgCode` | `{code, text, state:"Running"}` |
| `result` | завершення операції | `{ok, code, description, state:"Done"\|"Error", payload}` |
| `outcome` | знімок долі готовий (§6.7) | сам об'єкт `outcome`, **без** конверта `ok`/`code` |
| `connection` | зміна стану зв'язку (§5.2) | `{state:"connecting"\|"ready"\|"disconnected", reason}` |

Якщо у 1С немає обробника `ВнешнееСобытие` — `PostExternalEvent` тихо нічого не робить (не падає).

## 8. Каталог операцій: реалізовано vs заплановано

**Реалізовано (вертикальний зріз):** `Connect`/`Disconnect`/`IsConnected`, `CheckConnection`,
`GetTerminalInfo`, `Purchase`, `Refund`, `GetReceiptInfo` (sync + `Purchase`/`Refund` також async),
`Audit` (X-звіт, §5.17) і `Verify` (Звірка/Загальний звіт, §5.18) для звірки з обліковою системою,
`interrupt` (скасування), полінг `getLastStatMsgCode`, стан зв'язку з Ping після реконекту (§5.2),
з'ясування долі операції після обриву (§6.6-6.7). Цей набір вправляє **всі** механізми фундаменту
(обидві доріжки, класифікатор, JobEngine, poller, send-арбітр).

⚠️ **`IsFinancial` — whitelist `{Purchase, Refund}`**, і на нього спираються гейт, наскрізний
`requestId` і сам тригер `Pending`. Метод, що рухає гроші й не доданий туди, **тихо** випаде з усіх
трьох: помилки збірки не буде. Протокол уже описує фінансові методи, яких драйвер не реалізує
(`Cashback` §5.16, `Preauthorization` §5.26, `SaleCompletion` §5.27, `Withdrawal[Partly]`,
`ServiceRefund`, `ServicePbP`/`ServiceRefPbP`) — реалізуєш будь-який, додай його у whitelist і в
тести тригера.

**Заплановано інкрементально** (переважно описи операцій + парсинг полів, без нових механізмів):
`Withdrawal[Partly]`, `Cashback`, `Preauthorization`, `SaleCompletion`, `GetBalance`,
`VerifyCopy`, друк, сервіси розстрочки/`ServiceGeneric`, бонусні картки,
`GetPhoneNumber`/`GetOTPpassword`, поле `adv`.

**Свідомо НЕ реалізовано (as-built):** пауза на рішення каси (`getLastStatMsgCode==11` →
`getDiscountName`+`correctTransaction`) — код `11` наразі не перериває продаж (штатно, спека);
методи `ПодтвердитьОперацию`/`СкорректироватьСумму`/`ОтклонитьОперацию` відсутні. **Partial
approval** (`0010`) поки трактується як звичайний `ok:true` без окремої гілки вибору каси. Ці
розширення потребуватимуть додаткових станів `JobEngine` (`AwaitingCashDecision`/
`AwaitingPartialDecision`).

### 9.0. Верифікація на реальному обладнанні (2026-08-29)

Драйвер пройшов **повний живий тест з реальної 1С проти реального термінала Newland N950**
(Android, ПЗ `3.1.3.36`, Wi-Fi, `tcp://<ip>:2000`, бойовий еквайринг ПриватБанку):

| Операція | Статус | Примітка |
|---|---|---|
| `Подключить`/`ПроверитьСвязь`/`ВерсияПО` | ✅ | еталонна схема Ping→Identify→постійний конект |
| `Оплата` | ✅ | реальне списання з картки, повний `payload` (RRN, чек, receipt) |
| `Возврат` за RRN | ✅ | заявка на повернення прийнята хостом |
| `ПолучитьЧек` | ✅ | копія чека за `invoiceNumber` |
| `НачатьОплату`/`ПрерватьОперацию`/полінг | ✅ | скасування підтверджено (`1001`) |
| Онлайн-статуси (`ВключитьСобытия`) | ✅ | живі статуси 9→1→6→3→10 у формі 1С |
| `ХОтчет` (Audit) | ✅ | повний X-звіт (лічильники/суми по терміналах) |
| `Отключить` | ✅ | доведено логом + TCP-зондом (див. §5.1) |
| `Сверка` (Verify) | ⚠️ емулятор | реалізовано за спекою §5.18, на реальному терміналі свідомо не запускалась (шле підсумки на хост банку) |

Саме цей прогін виявив і закрив дві прогалини: строгість реального термінала до складу
`params` (§6.3, «Введіть discount») і невидимість діагностики з 1С (лог-фікси в
`docs/architecture/core.md` §5.1).

- **L0.7 `ecr_privatjson_selftest`** (без UAPKI) — кодек (`BuildRequest`/`Parse`/`PeekMethod`),
  класифікатор (усі гілки §4), transport-e2e поверх `DeviceSession`+`TransportTCP` проти
  `tests/support/TerminalEmulator` (Winsock, скриптовані відповіді за `method`): `Connect` за
  еталонною схемою, `JobEngine`, sync-операції + `MapResult`, poller, `interrupt`, async-API,
  смоук 1С-фасаду через `AddInNative::CreateObject`.
- **L2-ecr `ecr_native_host`** — компонента `ECRPrivatJSON` через **головну DLL** (`LoadLibraryW`+
  `GetClassObject`): `Подключить`+`Оплата` проти in-process `TerminalEmulator`, звірка `tVariant`.
- **`ecr_terminal_emulator.exe`** (standalone, `[port]`, default 2000) — протокол-обізнаний
  TCP-емулятор для ручного тесту з **реальної 1С без обладнання**: реалістична `Purchase` ~4с з
  прогресом статусу `9→1→6→3→10`, переривається `interrupt` (→ `1001`).

### 9.1. Життєвий цикл зв'язку й доля операції — сценарії

Додано до `ecr_privatjson_selftest` (L0.7), крім keepalive — той у `wire_selftest` (L0.6):

| Сценарій | Функція тесту | Що доводить |
|---|---|---|
| Чужий чек не зараховано | `TestForeignReceiptNotCredited` | код `UNKNOWN_OUTCOME`, чужий `rrn` не на топ-рівні `payload`; рівно одна подія `result` |
| `Disconnected` → 17 негайно; знімок після реконекту | `TestOutcomeAfterReconnect` | `state=pending`, `facts=null` до реконекту → `resolved`, `terminalIdle=true`; подія `outcome` рівно одна |
| Гейт у `Pending` / гейт знято після `Resolved` | `TestGateBlocksSecondPurchase` | другий `Purchase` до емулятора **не дійшов** (лічильник = 1) |
| `SendFailed` при живому з'єднанні | `TestSendFailedResolvesInline` | знімок у тому ж виклику, `channelConnected=true` |
| Термінал не виходить із «зайнятий» до ліміту | `TestTerminalBusyUntilLimit` | `terminalIdle=false`, `factsCode="TERMINAL_BUSY"`; `MarkSynchronized` викликано |
| `Disconnect()` посеред `Pending` | `TestDisconnectDuringPending` | без `terminate`/UAF; `lastOutcome_` переживає повторний `Connect()` |
| Повторний обрив під час з'ясування | `TestSecondDropDuringCapture` | перший джоб вийшов `ABORTED` без запису; знімок один |
| Нефінансовий метод при обриві | `TestNonFinancialNotTracked` | `DISCONNECTED`, `lastOutcome_` не чіпається |
| `InquireLastOutcome` при `None` | `TestInquireNone` | `ok:true`, `state:"none"` |
| `JobEngine::Start` із двох потоків | `TestJobEngineStartRace` | рівно один `true`, жодного `terminate` |
| Самозцілення з `InquireLastOutcome` | `TestSelfHealingFromInquire` | вікно «`Pending` без виконавця» закривається |
| `Stopped` як тригер | `TestStoppedIsTrigger` | 17, `reason="STOPPED"` |
| Ping після реконекту → `Ready` | `TestPingAfterReconnect` | послідовність подій `connecting`(dropped) → `ready`; рівно один `PingDevice` на новій сесії |
| Мовчання після реконекту (монополія) | `TestSilenceAfterReconnect` | `Подключен`=`Ложь`; `Purchase` → `RECONNECTING`, на дріт не пішов; Ping повторюється |
| `deviceBusy` на Ping | `TestPingBusyIsReady` | `Busy` теж піднімає `Ready` |
| Keepalive увімкнений (L0.6) | `wire_selftest`, `GetSocketForTest` | `getsockopt(SO_KEEPALIVE) != 0` після `Open()` |
| `requestId` одноразовий | `TestRequestIdIsOneShot` | `intent.requestId` у знімку; наступна операція без сеттера → `""` |
| `Отключить` під `Connecting` | `TestLinkStateOnDisconnect` | подія `disconnected`(closed), не `dropped` |
| Гейт раніше за `RECONNECTING` | `TestGateBeforeReconnecting` | `Pending` + `Connecting` → 17, не 18 |
| Три стани — три коди | `TestThreeStatesThreeCodes` | до `Connect()` і після `Отключить` → `NOT_CONNECTED`, під `Connecting` → `RECONNECTING` |
| Епоха зв'язку | `TestLinkEpochRejectsStaleReady` | `Ready` не переживає обрив без нового Ping; стан останньої події `connection` ⇔ `IsReady()` |
| Епоха зв'язку, детерміновано | `TestLinkEpochStaleReadyDeterministic` | `Ready` зі старою епохою відкинуто (через `SetBeforeReadyHookForTest`) |
| Повторний `Connect()` без зайвого Ping | `TestReconnectByHandKeepsReady` | `Purchase` проходить, **не** `CONCURRENT`; нуль `PingDevice` на персистентній сесії |
| `Отключить` під backoff-сном | `TestDisconnectInterruptsBackoff` | повернення < 300 мс (поріг між двома зміряними значеннями) |
| Гейт споживає `requestId` | `TestGateConsumesRequestId` | `"B"` не прилипає до наступної операції |

**Тестові шви драйвера** (усі `…ForTest`, у продакшені не викликаються):

| Шов | Навіщо |
|---|---|
| `SetTransportFactoryForTest` | стаб транспорту з `Send < 0` **без** закриття сокета — інакше `SendFailed` при живому з'єднанні не відтворити |
| `SetOutcomeTimingForTest(idleWaitMs, syncWaitMs, pingTimeoutMs = -1)` | 120 с ліміту спокою в гейті нестерпні; короткий таймаут Ping потрібен, щоб джоб **дійшов** до backoff-сну |
| `MarkPendingForTest` | вікно «`Pending` є, джоб не `Running`» штатним шляхом не створити |
| `StopSessionForTest` | моделює `Stopped` від сесії; справжній `Disconnect()` з іншого потоку під активним запитом дав би UAF |
| `SetBeforeReadyHookForTest` | хук **між** `Response` на Ping і `SetLinkState(Ready)` — детермінує гонку епохи, вікно якої інакше мікросекундне |

**Емулятор** отримав два режими обриву: `DropConnection()` — розірвати активне з'єднання з боку
сценарію; `DropAfterNextResponse()` — закрити сокет **одразу після** відправки наступної відповіді
(«відповів на Ping і зник» інакше недетермінований).

`ecr_native_host` (L2-ecr) перевіряє те саме через головну DLL: `ОплатитьПлатежнойКартой` при
обриві → `Ложь`, `ПолучитьОшибку()` = `17`, **усі OUT порожні**, `ИсходПоследнейОперацииJSON`
віддає конверт зі знімком, і **повторний** `ПолучитьОшибку()` після знімка — усе ще `17`.

> **Правило, куплене дефектом (спека §6.5):** сценарій не має права перевіряти поведінку в стані X,
> доки не довів CHECK-ом, що система **в** стані X — тією самою парою предикатів, якою код
> розрізняє його від сусідів (`IsConnected() && !IsReady()` = `Connecting`, `!IsConnected()` =
> `Disconnected`, `IsReady()` = `Ready`). Після обриву `!IsReady()` задовольняється за мілісекунди,
> а `Connecting` настає лише після backoff супервізора ≥ 1 с — тест, що чекав `!IsReady()` і одразу
> кликав `Purchase`, працював у `Disconnected` і отримував `NOT_CONNECTED`. Небезпечніший сорт цієї
> пастки — той, що **зеленіє**: він живе в гейті як покриття, якого немає, і негативна верифікація
> його не ловить. Так само доводиться й поріг вимірювання — **двома** вимірами, з фічею і без.

### 9.2. Припущення до живого прогону (НЕ перевірено на реальному терміналі)

⚠️ **Усе нижче — припущення, а не факти.** Протокол про це мовчить, а емулятор відтворює **наші ж**
припущення, тому емулятором ці пункти не перевіряються **принципово**. Живий прогін на Newland N950
робиться окремо; до нього не посилайся на цей список як на встановлену поведінку.

| # | Питання | Чому важливо |
|---|---|---|
| 1 | Чи термінал **доводить** оплату до кінця, коли каса зникла посеред операції, чи скасовує її | від цього залежить, що взагалі може лежати в `facts` |
| 2 | Чи `GetReceiptInfo("")` віддає **відхилену** останню операцію з її `responseCode`, чи лише успішні | інакше «немає чека» не означає «не списано» |
| 3 | Чий годинник у `date`/`time` і наскільки розходиться з касою | звірка часу в §6 контракту 1С стоїть саме на цьому |
| 4 | Чи повертає термінал `1008` при повторі `Purchase` після виконаної операції | сигнал дублювання для каси |
| 5 | Чи монотонний `invoiceNumber` у межах пакета | впливає на пізнє діставання чека за номером |
| 6 | **Чи переживають факти операції нову TCP-сесію** — каса зникла після `Purchase`, термінал операцію довів, каса реконектилась **новою** сесією: чи бачать `GetReceiptInfo("")`/`getLastStatMsgCode` ту операцію | **найгостріше.** Якщо стан скидається разом із сесією, з'ясування долі в найгіршому сценарії не працює, і зіставлення можливе лише за номером чека |
| 8 | **Чи справді термінал повертає номер картки під іменем `pan`** — у відповіді `Purchase` (§5.1) і в чеку `GetReceiptInfo` (§5.30) | до 2026-09-15 фасади читали `cardPAN`, якого в специфікації **немає жодного разу**, тож `НомерКарты` не заповнювався НІКОЛИ, а e2e-тест сам підставляв вигадане ім'я й тому був зелений. Виправлено на `pan` за протоколом, але саме це поле на живому Newland не звірялось |
| 7 | **Скільки термінал тримає мертву сесію** після тихого обриву (висмикнути кабель на ~30 с у простої, вставити — через скільки відповість новому `PingDevice`) | **друге за гостротою:** від цього залежить, скільки касир бачитиме `RECONNECTING` |

Що про ритм відомо точно (виміряно на емуляторі, механізм у коді): у мовчанні термінала ритм Ping —
**сталий ≈ 6 с**, а не зростаючий до 15 с, як читається з backoff у псевдокоді. Кожен `Timeout`
Ping ставить `reconnectRequested_`, супервізор рве з'єднання посеред backoff-сну, `EnsureReady`
виходить, а після `Close→Open` хук `up=true` запускає **свіжий** `EnsureReady` з початковим
backoff; сам супервізор свій backoff після вдалого `Open` теж скидає. Тобто **кожен цикл — нове
TCP-з'єднання**, і саме це побачить термінал (пункт 7 вище). Подвоєння в коді лишене свідомо: воно
коштує рядок і стане чинним, якщо супервізор колись перестане рвати сесію на `Timeout` primary.

Ще одне, що варто знати наперед: **вікно `Disconnected` після обриву — щонайменше 1 с**.
Супервізор чекає `reconnectDelayMs` (1000 мс) **перед першою** спробою `Close→Open`, тоді як
`Ready` падає за ~20 мс. Тобто «не `Ready`» ≠ «`Connecting`»: першу секунду після обриву сокета
немає взагалі, і будь-яка операція чесно отримає `NOT_CONNECTED`, а не `RECONNECTING`.
