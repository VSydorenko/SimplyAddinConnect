# Платформенна архітектура SimplyAddinConnect — дизайн-специфікація

*Дата: 2026-07-19. Статус: затверджено напрям, специфікація на рев'ю.*
*Підготовлено за результатами глибокого дослідження: 4 розрізи поточної кодової бази,
повне прочитання 3 протокольних специфікацій (`docs/ECR_Privat_JSON_Protokol.md`,
`docs/ECRCommXBPOS1_Protokol.md`, `docs/POSAPI_Protokol.md`), аудит проєкту-попередника
`R:\github\SMP_SimplyConnect\SimplyConnect_Addin` (v2.3.1, прямий предок поточного v3.0.x).*

---

## 1. Мета

Перебудувати SimplyAddinConnect у **платформенне рішення**: спільні механізми
(точки входу 1С, реєстрація методів, параметри, логування/відлагодження, підключення,
асинхронне виконання, транспорт, кадрування) — один раз у платформі; протоколи
обладнання — компактні **драйвери** навколо неї з максимальним перевикористанням.

Ключові установки (затверджені):

- **ECRCommXBPOS1 і POSAPI — власні АНАЛОГИ** вендорських бібліотек: wire-рівень
  реалізуємо самі, розмовляючи з обладнанням напряму. Вендорські документи — лише
  **семантичні референси** (перелік операцій, модель статусів, флоу підтверджень),
  **не** контракти API.
- **Жодної сумісності з історичними API** (MSComm/MSWinsock OCX, інтерфейси вендорських
  DLL). 1С-конфігурація адаптується під нашу компоненту. 1С-API усіх драйверів —
  **власне, єдине, консистентне**.
- **Компонента — завжди клієнт** щодо обладнання/систем (1С-сторона), Windows-only.
- Обмеження — лише сучасні технології взаємодії Windows з обладнанням:
  Win32 Comm API (serial/USB-CDC/BT-SPP), Winsock2 (TCP), WebSocket-клієнт.
- **UAPKI — єдине зовнішнє рішення**, не наше: взаємодіємо як з бібліотекою,
  не модернізуємо; фасад поступово приводимо до спільних конвенцій.

## 2. Чому переробка потрібна зараз (докази)

### 2.1 Два підтверджені структурні баги поточного коду

1. **Розірваний шлях приймання ECRPrivatJSON** (детермінований, 100%):
   транспортні колбеки під'єднані лише до `Protocol::OnDataReceived`
   (`ECRPrivatJSON_Connection.cpp:66,210,335`), а всі очікувачі
   (`SendReceive`/`WaitForResponse`, хендшейк) висять на condition variable
   **хелпера**, чий продюсер `ProcessReceivedData` не викликається ніде.
   Наслідок: `Connect*` і всі операції завжди фейляться по таймауту.
2. **Конвенція повернення значень у 1С**: ядро зберігає всі хендлери як
   `std::function<void(...)>` (`AddInNative.h:90-108`), повернути значення можна лише
   присвоєнням `this->result`; ECR-фасади цього не роблять ніде (локальні
   `bool result` затінюють член) — методи «німі» для 1С.

### 2.2 Системний урок обох проєктів (поточного і попередника)

1. **Ланцюг приймання/подій ніколи не був замкнутий end-to-end**: у поточному — два
   роз'єднані буфери; у legacy — монітор подій порту лише логує
   (`SerialPortConnection.cpp:666-680`), `RaiseCommEvent` не викликається,
   `IAddInDefBase::ExternalEvent` не викликається **в жодному з двох репозиторіїв**.
2. **За відсутності wire-специфікації дротовий рівень підміняли вигадкою**:
   BPOS1 у legacy — фіктивний формат `PURCHASE|AMOUNT=…` (0% реального протоколу),
   POSAPI — in-memory заглушка (~5-10%); тести — «зелені» проти власної фікції.

Платформа має унеможливити обидва класи провалів конструктивно (див. §3, §7).

### 2.3 Ключові факти зі специфікацій протоколів

- **Приват (ECR JSON)**: термінал слухає сирий TCP:2000 або COM 115200 8N1;
  кадр = JSON + термінатор `0x00` (хендшейк — додатково `0x00` на початку);
  еталонна схема: connect→handshake→disconnect→connect→identify→disconnect→
  connect→**постійне keepalive-слухання** з реконектом; 3 логічні потоки в одному
  з'єднанні (операція + ServiceMessage + `deviceBusy`); кореляція відповідей за полем
  `method`; операції до 120с; корекція суми `correctTransaction` при
  `getLastStatMsgCode=11`; wire-трейс — обов'язок клієнта (§6.6 спеки).
  **WebSocket** — топологія з middleware-транслятором: транслятор тримає монопольне
  з'єднання з терміналом, каса (ми) — WS-**клієнт** до транслятора. За рішенням
  користувача: WS-клієнт — рівноправний транспорт пілотного драйвера з першого дня
  (найімовірніша прод-топологія Привату).
- **B-POS1 (Ingenico)**: вендор-док описує лише ActiveX API. Семантика для аналога:
  асинхронний запуск операції + полінг `LastResult` (2=in progress) +
  статуси `LastStatMsgCode` (0-18) + явний `Confirm` + `CorrectTransaction`.
  **Wire-формат невідомий** — здобувається (є доступ до заліза).
- **POSAPI (Printec USO)**: вендор-док описує лише C-API. Семантика для аналога:
  сесія = одна операція; цикл прийому з проміжними статусами (`RESP_MESSAGE`) і
  **паузами** (`RESP_IDENTIFIER` — термінал чекає рішення каси в тій самій сесії:
  `ACTION_CONFIRM` або `ACTION_REVISION` зі зміненою сумою); `POS_TRANS_ID` зберігати
  до фіналу (відновлення після обриву через `ACTION_STATUS` в новій сесії); невідомий
  код відповіді → обов'язковий `ACTION_BREAK`; таймаути транспортозалежні (2-4 хв).
  **Wire-формат невідомий** — здобувається.

Спільні концепції всіх трьох → у платформу: асинхронна операція зі статусами,
**пауза на рішення каси**, дефолти/валідація параметрів, wire-трейс, реконект.

   │ tVariant / IComponentBase / ExternalEvent
┌──▼──────────────────────────────────────────────────────┐
│ 0. ЯДРО-МІСТ 1С (src/core)                              │
├─────────────────────────────────────────────────────────┤
│ 1. ПЛАТФОРМА ДРАЙВЕРІВ (src/platform) — нове            │
│    OperationRegistry · JobEngine · ResultEnvelope       │
│    Logger + WireTrace · EventBridge                     │
├────────────────────────────┬────────────────────────────┤
│ 2. WIRE-СТЕК (src/wire)    │ 2б. КАНАЛЬНА КОМПОНЕНТА    │

### 3.0 Ядро-міст 1С (зміцнення наявного)

Наявне ядро (`AddInNative`, `VariantHelper`, реєстр компонент) чисте від протокольної
специфіки і зберігається. Доповнення:

1. **Єдина конвенція повернення**: розширити `AddFunction` прийманням
   value-повертаючих хендлерів (`std::function<R(VH...)>`) з авто-присвоєнням
   `this->result`; явний `this->result = ...` лишити допустимим. Виправити всі
   наявні фасади.
2. **`REGISTER_COMPONENT(Name, Class)`** — макрос, що інкапсулює статичну реєстрацію
   `names` + анти-стрип `_force`-reference.
3. **`EnableLogging` та спільний ctor/dtor-каркас** — у базовий клас (зараз
   скопійовано в 3 компонентах).
4. **Декларативні параметри операцій** (див. §4): типи, обов'язковість, дефолти,
   діагностики — валідація в ядрі/платформі, не в кожному методі.
5. **EventBridge — потокобезпечний міст подій у 1С**: черга подій з фонових потоків →
   виклик `IAddInDefBase::ExternalEvent` (глибина вже налаштована:
   `SetEventBufferDepth(100)`). Правила потоків: результати методів і `AddError` —
   лише на потоці виклику 1С; з фонових потоків — лише EventBridge.
6. **Boot-фікси**: прибрати глобальну `std::locale("ru_RU.UTF-8")` зі статичної
   ініціалізації (`AddInNative.cpp:473` — ризик незавантаження DLL); виправити
   усічення вказівника в `GetClassObject` (`:57`); дефолтний sink логера до
   `EnableLogging` (OutputDebugString), щоб ранні логи не губились.

### 3.1 Платформа драйверів (нове)

- **OperationRegistry** — операція драйвера описується один раз:
  ім'я en/ru, перелік параметрів (ім'я, тип, обов'язковість, дефолт), таймаут,
  прапорець «підтримує паузу на рішення каси», обробник. З опису автоматично:
  реєстрація в 1С (типізований метод + асинхронна пара), валідація параметрів із
  точними повідомленнями, документація.
- **JobEngine** — виконавець операцій. Стани:
  `Idle → Running → [AwaitingCashDecision] → Done | Error`.
  Один worker-потік на екземпляр драйвера (з'єднання). 1С-модель використання:
  - синхронно: `Оплата(...)` = start + wait (для простих сценаріїв);
  - асинхронно: `НачатьОплату(...)` → `ПолучитьСостояние()` /
    `ПолучитьСтатусОперации()` (полінг з `ОбработчикОжидания`) →
    `ПолучитьРезультат()`; опційно подія через EventBridge
    (`ВнешнееСобытие`) про зміну стану;
  - пауза: у стані `AwaitingCashDecision` 1С викликає
    `ПодтвердитьОперацию(...)` / `СкорректироватьСумму(...)` / `ОтклонитьОперацию()`.
- **ResultEnvelope** — уніфікований конверт результату кожної операції:
  `{ ok: bool, code: string, description: string, payload: json }`.
  У 1С: функція повертає `ok`, деталі — геттери/`ПолучитьРезультатJSON()`.
- **Logger + WireTrace** — власний тонкий логер (заміна spdlog: ротований файл,
  рівні, потокобезпека) + окремий канал wire-трейсу: hex-дамп прийому/передачі
  у форматі, сумісному з §6.6 спеки Привату (`trace.log`). Вмикається з 1С.

### 3.2 Wire-стек (нове; фундамент усіх драйверів-аналогів)

- **`ITransport`** — вузький байтовий контракт: `Open/Close/IsOpen/Send` + колбеки
  (дані/помилка/стан з'єднання). Потокова модель зафіксована в контракті:
  один reader-потік на з'єднання, колбек даних викликається з нього; `Send`
  потокобезпечний. Реконект — НЕ в транспорті (вище). Реалізації:
  - **TransportCOM** — Win32 Comm API: `CreateFileW("\\\\.\\COMn")`, `DCB`,
    `COMMTIMEOUTS`, overlapped I/O + `WaitCommEvent` (переносимо ноу-хау
    `SerialPortConnection` попередника: монітор подій, DTR/RTS, парсер налаштувань
    `"115200,8,N,1"`); покриває RS-232, USB-CDC містки, Bluetooth SPP;
  - **TransportTCP** — Winsock2: неблокуючий connect + select (таймаут з'єднання),
    reader-потік, `SO_KEEPALIVE`;
  - **TransportWSClient** — ixwebsocket (client-only збірка), ping-interval,
    вбудований автореконект бібліотеки вимикаємо (реконект керується вище).
  Рядок підключення платформенний: `"COM3:115200,8,N,1"` | `"tcp://host:port"` |
  `"ws://host:port/path"`.
- **`IFramer`** — плагінне кадрування: `Feed(chunk) → frames[]`, `Wrap(payload)`,
  `Reset()`. Реалізації: `NullTerminatedFramer` (Приват; + префіксний `0x00` для
  хендшейку), майбутні `StxEtxLrcFramer`/`LengthPrefixedFramer` — за фактичними
  wire-спеками BPOS1/USO.
- **`FramedSession`** — єдиний власник байтового потоку з'єднання:
  буфер + framer + м'ютекс/CV + **кореляція запит↔відповідь за предикатом**
  (для Привату — за полем `method`), паралельні сервісні запити під час основної
  операції, канал unsolicited-повідомлень (`deviceBusy`, `interruptTransmitted`),
  таймаути, **реконект-супервізор** (політика: N спроб, backoff, події стану).
  Структурно унеможливлює клас багів «два буфери» — драйвер не має власного приймання.

### 3.2б Канальна компонента SimplyChannel (включено в обсяг)

Окрема 1С-компонента над тим самим `ITransport` — сирий канал для простого
обладнання без C++-драйвера: `Открыть(строкаПодключения)`, `Закрыть()`,
`Отправить(данные)` (рядок/BLOB), прийом — накопичувальний буфер +
`Прочитать()`/поріг + подія `ВнешнееСобытие` про надходження даних (вмикається
опційно). API власне, сучасне; MSComm-сумісності немає. Роль у проєкті:
корисний інструмент для 1С + рання обкатка транспорту і EventBridge на залізі.

### 3.3 Драйвери

- **ECRPrivatJSON (пілот; wire повністю відомий)** — переписується на платформі:
  - транспорти: COM, TCP, **WS-клієнт (рівноправний з першого дня** — очікувана
    прод-топологія через транслятор);
  - еталонна схема підключення зі спеки (handshake→disconnect→identify→disconnect→
    keepalive-з'єднання; реконект);
  - операції через OperationRegistry (Purchase, Refund, Withdrawal[Partly],
    Verify, Audit, GetReceiptInfo, сервісні...); під час `Running` драйвер сам
    полить термінал `getLastStatMsgCode` і оновлює статус операції;
    `correctTransaction` — через стан `AwaitingCashDecision`; `interrupt` —
    `ПрерватьОперацию()`;
  - unsolicited: `deviceBusy` → помилка/повтор за політикою.
- **ECRCommXBPOS1 і POSAPI (аналоги; після здобуття wire)** — семантика операцій,
  статусів і флоу підтверджень/корекцій береться з вендор-доків; 1С-API — спільна
  конвенція платформи (не клон вендорського). **Wire-first правило**: імплементація
  драйвера стартує лише після появи документа `docs/wire/<протокол>.md` з форматом
  кадрів, контрольними сумами, квитуванням і hex-прикладами реального обміну.
- **UAPKI** — без змін по суті (зовнішня бібліотека, `process()/json_free()`);
  фасад поступово приводиться до конвенцій (повернення, параметри, логування).

### 3.4 Здобуття wire-специфікацій (передумова етапу 4; залізо є)

Окрема підзадача «механізми збору обміну» (детальне ТЗ — коли дійдемо):

- COM: пасивний сніфінг обміну вендорської DLL з терміналом (port-splitter:
  com0com+hub4com або еквівалент; альтернативно наш логер-міст на TransportCOM);
- TCP: власна утиліта-проксі з hex-дампом (тривіально на нашому wire-стеку);
- результат: `docs/wire/bpos1.md`, `docs/wire/posapi_uso.md` з анотованими
  дампами → тест-вектори для framer/кодека.

## 4. Конвенція 1С-API (єдина для всіх драйверів)

- Імена методів — пари en/ru, дієслівні, консистентні між драйверами
  (`Connect/Подключить`, `Disconnect/Отключить`, `НачатьОплату/StartPurchase`...).
- Кожна операція має синхронну і асинхронну форму (генеруються з одного опису).
- **Параметри**: строгі позиційні з дефолтами (механізм `MethDefaults` вже є) +
  валідація за декларацією з точними помилками
  («Параметр 'Сумма' метода 'Оплата' обов'язковий; отримано порожнє значення»).
  Мовчазної перестановки параметрів немає (небезпечна неоднозначність).
  Додатково кожен метод має JSON-форму (один параметр-об'єкт, іменовані поля) —
  повністю знімає питання порядку.
- **Результат**: bool через `this->result` (авто) + `ПолучитьРезультатJSON()` +
  типізовані геттери останньої операції там, де це зручно 1С.
- **Помилки**: `REPORT_ERROR` (лог + `AddError` в 1С) → `return false`; винятки
  не перетинають межу 1С.
- Логування: `ВключитьЛогирование(уровень, путь)` + `ВключитьТрассировкуОбмена()` —
  однаково в усіх компонентах DLL.

  boot-фікси. Тестується без заліза — харнес `core_selftest` (L0.5 у `run_tests.ps1`).
- **Етап 1 — платформа + wire-стек**: Logger/WireTrace, JobEngine,
  OperationRegistry, `ITransport` (COM/TCP/WS-клієнт), `IFramer`, `FramedSession`.
  Юніт-тести: loopback-транспорт, framer-вектори, кореляція, реконект.
  **Wire-фундамент виконано (2026-07-20, гілка `device-core`):** `ITransport`+фікси COM/TCP/WS-клієнт
  (§9.1), `IFramer`/`NullTerminatedFramer`, `IFrameClassifier`, `DeviceSession` (роль `FramedSession`;
  дві доріжки primary/service, реконект, desync, WireTrace), детермінований `LoopbackTransport`;
  харнес `wire_selftest` (L0.6 + режим `-NoUapki`). Дизайн/план —
  `docs/tasks/2026-07-20_{design_device_transport_session,plan_device_core}.md`.
  **Лишається в Етапі 1:** Logger, JobEngine, OperationRegistry.
- **Етап 2 — пілот ECRPrivatJSON**: драйвер заново за еталонною схемою
  (баг №1 вмирає структурно) + **TCP-емулятор термінала** (байтові приклади зі
  спеки = готові тест-вектори; PingDevice/Identify/Purchase/помилкові сценарії) +
  тонкий WS-міст над емулятором для перевірки WS-шляху. Інтеграція в
  `run_tests.ps1` (рівні L0-L3 за зразком UAPKI-харнесу).
- **Етап 2б — SimplyChannel** (паралельно з 2): канальна компонента + обкатка
  EventBridge на реальному порту.
- **Етап 3 — дієта**: spdlog→логер, ixwebsocket client-only, видалення WSServer,
  `CreateTransport`/`SetTransport` та іншого мертвого коду.
  **Частина виконана достроково (гілка `device-core`):** видалено `Transport_WSServer`, серверний
  режим TCP, старий непрацездатний ECR-драйвер (`AddinECRPrivatJSON`, `protocols/ECRPrivatJSON`,
  `helpers/ECRPrivatJSON`) і мертві `CreateTransport`/`SetTransport`. **Лишається:** spdlog→логер,
  повна ix-дієта.
- **Етап 4 — аналоги BPOS1/POSAPI**: спершу підзадача wire-здобуття (§3.4),
  потім драйвери (framer+кодек+опис операцій; решта з платформи).

Тестова політика (з уроку §2.2): жодних тестів проти вигаданих форматів;
тест-вектори — лише зі специфікацій або реальних дампів. Юніт-тести чистої логіки
(патерн `test_bpos1_parser` попередника — патерн так, вектори ні).

## 7. Ризики

| Ризик | Пом'якшення |
|---|---|
| Wire BPOS1/USO може виявитись складнішим за очікуване (MAC, ретрансмісії) | Wire-first правило: без задокументованого формату драйвер не стартує; залізо для дампів є |
| Немає термінала Привату для e2e | Емулятор зі спеки (байтові приклади); архітектура дозволяє пізню верифікацію на залізі без переробки |
| Регресія UAPKI-функціоналу при правках ядра | Наявний харнес L0-L3 (`run_tests.ps1`) ганяється на кожному етапі |
| `ExternalEvent` поведінка в різних контекстах 1С (тонкий/товстий клієнт, фон. завдання) | Полінг — базовий механізм скрізь; події — опційне доповнення; емпірична перевірка в 1С на етапі 2б |
| Обсяг переробки | Поетапність: кожен етап самодостатній, збірка завжди зелена |
