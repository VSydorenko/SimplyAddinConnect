# Провайдер НКІ не піднімається при повторному `INIT` у живому процесі 1С — драфт задачі

*Дата: 2026-09-22. Статус: **дефект локалізовано до рядка коду; знайдено робочий обхід
(§4.1, зміряно), рішення не обране**.
Знайдено під час живого тесту §4.3 з реальної 1С (гілка `uapki-certid-key-selection`,
збірка 3.2.0.219). До підписання за сертифікатом (`SELECT_KEY` за `certId`) стосунку
не має — це окремий, раніше не помічений дефект життєвого циклу.*

> **Для нової сесії:** цей документ — **опис проблеми й доказова база**, а не план.
> Рішення (який із ЧОТИРЬОХ напрямків брати, як тестувати, що патчити) **не ухвалене**
> свідомо — його ухвалює сесія, яка візьме задачу, разом із користувачем.

---

## 1. Симптом

У живій 1С компонента підписує **лише в першому відкритті обробки в процесі**. Далі
`INIT` повертає `errorCode: 0`, але `countCmProviders: 0`, і кожен наступний виклик
падає:

```
OPEN       -> 4102 UNKNOWN_PROVIDER
SELECT_KEY -> 4121 STORAGE_NOT_OPEN
SIGN       -> 4121 STORAGE_NOT_OPEN
```

**`INIT` при цьому рапортує успіх.** Жодної помилки, жодного попередження з боку
бібліотеки — тільки нуль у полі, на яке ніхто не дивиться.

Спостережена послідовність у лозі компоненти за 2026-09-22
(`C:\log\SimplyAddinConnect.log`, той самий процес 1С, той самий ключ і шляхи):

| Час | `certCache.countCerts` | `countCmProviders` |
|---|---|---|
| 11:11 | 6 | **1** |
| 11:23 | 6 | 0 |
| 11:31 | 6 | **1** |
| 13:06 | 0 | 0 |
| 13:16 | 6 | 0 |
| 13:22 | 0 | 0 |

`certCache` до справи не стосується — на нього спершу впала підозра й не підтвердилась
(11:23 і 13:16 мають заповнений кеш і нуль провайдерів).

## 2. Причинний ланцюг — локалізовано до рядка

### 2.1. Провайдер тримає глобальний стан і віддає ПОМИЛКУ при повторній ініціалізації

`extern/uapki/library/cm-pkcs12/src/main-cm-pkcs12.cpp:67` — глобал на рівні DLL:

```cpp
static CmPkcs12* cm_pkcs12 = nullptr;
```

`provider_init` у тому ж файлі:

```cpp
CM_EXPORT CM_ERROR provider_init (CM_JSON_PCHAR providerParams)
{
    CM_ERROR cm_err = RET_CM_GENERAL_ERROR;
    if (!cm_pkcs12) {
        cm_pkcs12 = new CmPkcs12();
        ...
    }
    else {
        cm_err = RET_CM_ALREADY_INITIALIZED;   // <-- повторний виклик = ПОМИЛКА
    }
    return cm_err;
}
```

`RET_CM_ALREADY_INITIALIZED` — `extern/uapki/library/common/cm-api/cm-errors.h:40`.

### 2.2. UAPKI реєструє провайдер ЛИШЕ при `RET_OK`

`extern/uapki/library/uapki/src/cm-providers.cpp`, `CmProviders::loadProvider`:

```cpp
ret = storage->providerInit(jsonParams);
if (ret == RET_OK) {
    ...
    lib_cmproviders.providers.push_back(CM_PROVIDER(s_id, storage));
    storage = nullptr;
}
```

Провайдер **ініціалізований і повністю придатний до роботи**, але через `!= RET_OK`
у список не потрапляє. Звідси `countCmProviders: 0`.

### 2.3. `INIT` відкидає код помилки — тому ми сліпі

`extern/uapki/library/uapki/src/api/library-init.cpp:63-86`, `setup_cm_providers`:

```cpp
(void)CmProviders::loadProvider(s_dir, s_lib, s_config);
```

Результат відкинуто явним `(void)`. Тому `uapki_init` доходить до кінця, ставить
`setInitialized(true)` (`library-init.cpp:258`) і віддає `errorCode: 0` з нулем
провайдерів. Справжній код помилки не потрапляє нікуди — ні у відповідь, ні в лог.

### 2.4. Чому глобал переживає перестворення об'єкта

`src/components/AddinUAPKIConnect.cpp:19` — деструктор `~AddinUAPKIConnect()` **не
викликає `DEINIT`**. У лозі за 2026-09-22 видно шість викликів `INIT` і **жодного
`DEINIT`**.

Навіть якби 1С вивантажила нашу головну DLL, `cm-pkcs12_x64.dll` лишається в процесі
зі своїм лічильником посилань, а його `static CmPkcs12* cm_pkcs12` — ненульовим.
Наступний `provider_init` іде в гілку `else`.

### 2.5. Повний ланцюг

```
1-ше відкриття обробки в процесі 1С
  LoadLibrary(cm-pkcs12_x64.dll)  -> ok
  provider_init()                 -> RET_OK
  push_back(провайдер)            -> countCmProviders = 1   ПРАЦЮЄ

2-ге і далі (той самий процес 1С)
  LoadLibrary(...)                -> ok (лічильник посилань)
  provider_init()                 -> RET_CM_ALREADY_INITIALIZED
  if (ret == RET_OK) НЕ спрацював -> провайдер не зареєстровано
  (void) у setup_cm_providers     -> помилка зникла
  INIT                            -> errorCode 0, countCmProviders = 0   ТИХО ЛАМАЄТЬСЯ
```

## 4. Пастка, у яку вже впали: `DEINIT` не рятує

Очевидний обхід «побачили нуль -> `DEINIT` -> `INIT` заново» **не працює і робить
гірше**. Живий прогін 2026-09-22:

```
DEINIT -> {"errorCode":0,"method":"DEINIT","result":{}}
INIT   -> {"errorCode":33,"method":"INIT","result":{},"error":"SELF_TEST_FAIL"}
```

Механіка в коді:

- `library-init.cpp:224` — на повторному `INIT` повертається `ALREADY_INITIALIZED`,
  результат не заповнюється взагалі;
- `library-init.cpp:226` — **кожен** `INIT` ганяє `uapkic_init` із самотестом
  (`p_selftest_status`, `library-init.cpp:218`), і після деініціалізації той уже не
  проходить.

Перший висновок із цього виміру був **ширший за сам вимір**: «UAPKI не підтримує цикл
`INIT -> DEINIT -> INIT` взагалі». Насправді ламався **лише самотест**, і на нього є
документований вимикач — `skipSelfTest` (`library-init.cpp:218`, задокументовано в
`extern/uapki/doc/UAPKI-PM-2.0.16.md`). Див. §4.1: цикл **працює**.

> Походження помилки варте окремої згадки: висновок зробив виконавець, а архітектор
> прийняв його без перевірки й побачив пропущену ланку лише тоді, коли довелось
> переказувати результат чужій команді. Це той самий клас «твердження, ширшого за
> вимір», який ловився всю сесію, — тут він пройшов **через обох**.

### 4.1. `DEINIT` + `INIT{skipSelfTest}` — ЦИКЛ ПРАЦЮЄ, зміряно

Прогін `uapki_selftest_x64.exe` (ядро UAPKI через `process()` напряму, без 1С),
2026-09-22, робочий каталог `bin/Release`:

**Контроль — без `skipSelfTest`:**
```
[PASS] task #1 method='INIT'   errorCode=0
[PASS] task #2 method='DEINIT' errorCode=0
[FAIL] task #3 method='INIT'   errorCode=33 [unexpected errorCode=33] error='SELF_TEST_FAIL'
```

**Із `"skipSelfTest": true` у параметрах третього `INIT`:**
```
[PASS] task #1 method='INIT'   errorCode=0
[PASS] task #2 method='DEINIT' errorCode=0
[PASS] task #3 method='INIT'   errorCode=0
```

Усі три задачі несли `"expectCountCmProviders": 1`, тож третій `PASS` означає
**`countCmProviders == 1` після повторної ініціалізації** — провайдер піднявся.

Сама перевірка звірена на червоному (інакше зелене нічого не доводило б): з
`"expectCountCmProviders": 999` прогін дає
`[FAIL] task #3 … [countCmProviders expected 999 got 1]` — значення справді
вимірюється, а не приймається за замовчуванням.

**Чому глобал провайдера при цьому скидається** (ланцюг звірений архітектором):
`CmProviders::deinit` (`cm-providers.cpp:185-192`) видаляє проксі ->
`~CmStorageProxy` (`cm-storage-proxy.cpp:60-62`) кличе `providerDeinit()` ->
`provider_deinit` (`main-cm-pkcs12.cpp:112-115`) ставить `cm_pkcs12 = nullptr`.

**ЗАСТЕРЕЖЕННЯ, обов'язкове до врахування при виборі напрямку.** Самотест перевіряє
реалізацію криптоалгоритмів. Пропускати його можна **лише на ПОВТОРНОМУ `INIT`**,
ніколи на першому в процесі. Для ПРРО, де підпис юридично значущий, це різниця між
«зекономили секунду» і «не перевірили крипто на старті процесу».

## 4.2. Чому напрямок D працює — механіка, звірена в коді

`cm-storage-proxy.cpp:123` — `m_IsInitialized = (ret == RET_OK);`

На **першому** `INIT` `ret == RET_OK`, прапорець стає `true`, і тому `DEINIT` іде
повним шляхом: `CmProviders::deinit` -> `delete storage` -> `~CmStorageProxy`
(`cm-storage-proxy.cpp:60-62`, `if (isInitialized()) providerDeinit();`) ->
`provider_deinit` -> `cm_pkcs12 = nullptr`. D спирається саме на цю гілку, а не на
щасливий збіг.

> **ПАСТКА ДЛЯ НАПРЯМКІВ B і C.** Виправити **лише** `cm-providers.cpp:162`
> (трактувати `RET_CM_ALREADY_INITIALIZED` як успіх) — **половина роботи, і вона
> ламає другу**. `m_IsInitialized` виставляється **окремо**, на
> `cm-storage-proxy.cpp:123`, і при `ALREADY_INITIALIZED` лишиться `false`. Тоді
> провайдер зареєструється, але `~CmStorageProxy` **пропустить** `providerDeinit()` —
> і `DEINIT` перестане звільняти глобал. Полагодивши повторний `INIT`, зламали б
> `DEINIT`. Потрібні **обидва** місця. (Знайдено при рев'ю пропозиції
> `prro-uapki-spec`, яка містила рівно цю половину.)

## 4.3. Невідповідність моделі спостереженню — ЗАКРИТА виміром

**Як виникла.** У невдалій гілці `cm-providers.cpp:180-181` (`cleanup: delete storage`)
спрацьовує `~CmStorageProxy` -> `~CmLoader` (`cm-loader.cpp:65-68`) -> `unload()` ->
`DL_FREE_LIBRARY` (`cm-loader.cpp:137`). Тобто кожна невдала спроба **вивантажує**
провайдерську DLL. За моделлю «глобал лишився ненульовим» наступна спроба мала б
пройти — а дефект необоротний до перезапуску сеансу. Модель передбачала
самовилікування, спостереження його не показувало.

**Вимір, що закрив питання.** `uapki_selftest_x64.exe`, три `INIT` поспіль **без**
`DEINIT`, той самий процес:

```
[PASS] task #1 method='INIT' errorCode=0
[FAIL] task #2 method='INIT' errorCode=4106 error='ALREADY_INITIALIZED'
[FAIL] task #3 method='INIT' errorCode=4106 error='ALREADY_INITIALIZED'
```

Повторний `INIT` у тому самому екземплярі UAPKI **не доходить** до
`setup_cm_providers` взагалі — його зупиняє рання гілка `library-init.cpp:224`.

**Наслідок, і він вирішальний.** У 1С спостерігалось `errorCode: 0` з
`countCmProviders: 0` — тобто `lib_config->isInitialized()` був **`false`**. Отже в
1С кожен `INIT` бачив **свіжий стан UAPKI**, а провайдерська DLL при цьому лишалась
завантаженою з брудним глобалом. Стан бібліотеки скидався, стан провайдера — ні.

UAPKI злінковано **статично в нашу головну DLL**, тож його глобали живуть рівно
стільки, скільки завантажена наша DLL. Провайдер вантажиться окремим
`LoadLibrary` і має власний лічильник посилань.

**Звідси єдине пояснення, що узгоджується з усіма вимірами** (позначене як
**неперевірене**): у процесі 1С існує **більш ніж один екземпляр нашої головної
DLL** — наприклад, із кеша `ExtCompT` і з макета обробки (про три кеші компоненти
див. пам'ять проєкту й `docs/integration-1c/README.md` §2.2). Тоді:

- екземпляр A робить `INIT`, вантажить провайдера (лічильник 1), реєструє,
  `cm_pkcs12 != nullptr`;
- екземпляр B має **власні, чисті** глобали UAPKI, тож його `INIT` проходить
  `:224` і доходить до `setup_cm_providers`;
- `LoadLibrary` провайдера вдається (лічильник 2), `provider_init` віддає
  `ALREADY_INITIALIZED`, провайдер не реєструється;
- `cleanup: delete storage` робить `FreeLibrary` — лічильник 2 -> 1, **DLL лишається
  завантаженою екземпляром A разом із брудним глобалом**. Звідси необоротність.

**Як перевірити цю гіпотезу** (не зроблено): у процесі 1С після відтворення дефекту
перелічити завантажені модулі (`Process Explorer` або `EnumProcessModules`) і
порахувати, скільки разів присутні `SimplyAddinConnectWin_x64.dll` і
`cm-pkcs12_x64.dll`, та з яких шляхів.

**Чому це важливо для вибору напрямку.** Поки гіпотеза не перевірена, невідомо, чи D
лікує **причину**, чи один із двох її проявів. Якщо екземплярів нашої DLL справді
два, то `DEINIT` в одному з них не впливає на глобал, утримуваний іншим, — і D може
працювати нестабільно саме так, як нестабільно працював сам дефект (`1/0/1/0`).

## 4.4. Гіпотеза двох екземплярів має ПІДТВЕРДЖЕННЯ — і вона перевертає порядок напрямків

### Механізм уже зміряно в цьому проєкті (2026-07-27)

Пам'ять проєкту `1c-native-component-cache` фіксує, **доведено оглядом завантажених
модулів процесу `1cv8`**, що 1С кладе DLL компоненти за **двома різними шляхами**
залежно від способу підключення:

- `УстановитьВнешнююКомпоненту` -> `%APPDATA%\1C\1cv8\ExtCompT\<path з маніфесту>`,
  постійно;
- `ПодключитьВнешнююКомпонентуАсинх` **без** встановлення ->
  `%TEMP%\v8_<сесія>_c.<path>`, тимчасово; `ExtCompT` при цьому не задіяний узагалі.

Два різні шляхи до файла — для Windows **два різні модулі**, кожен із власним
набором статиків, отже з **власним екземпляром статично злінкованого UAPKI**.
Достатньо, щоб у сеансі компонента підключилась обома способами або з двох джерел
(макет обробки й макет розширення).

> **Пастка при перевірці:** шукати треба **за двома масками** — ім'я компоненти
> **і** префікс `v8_*_c.`. Маска лише за іменем тимчасову копію не знайде; на цьому
> вже спіткнулись у липні.

### Наслідок: у сценарії двох екземплярів напрямок D НЕ ПРАЦЮЄ

Виводиться з коду, не з гіпотези:

- в екземплярі B провайдер **не зареєстрований** — `push_back` не відбувся, бо
  `ret != RET_OK` (`cm-providers.cpp:176`);
- отже `lib_cmproviders.providers` у B **порожній**;
- `CmProviders::deinit` (`cm-providers.cpp:185-192`) робить рівно одне — ітерує цей
  вектор і видаляє те, що в ньому є. По порожньому вектору це **no-op**:
  `providerDeinit()` не викликається **жодного разу**, глобал `cm_pkcs12` лишається
  брудним;
- наступний `INIT{skipSelfTest}` знову впирається в `ALREADY_INITIALIZED`.

**D відтворює той самий дефект, від якого лікує.**

Вимір §4.1 цьому не суперечить: `uapki_selftest` — **один** екземпляр, провайдер у
ньому зареєстрований, `m_IsInitialized == true`, тож `DEINIT` іде повним шляхом.
**D доведено для однієї конфігурації і провально для другої.**

### Наслідок: напрямок A стає єдиним, що дістається до спільного стану

Дескриптор модуля в Windows **процесо-широкий**. `GetModuleHandleW(L"cm-pkcs12_x64.dll")`
з екземпляра B віддасть **той самий** модуль, який завантажив A, і `provider_deinit`
через нього скине **той самий** глобал. Вектор реєстрації для цього не потрібен
узагалі — саме тому A працює там, де D безсилий.

### Каверза й до кореневого виправлення (B/C)

Якщо `loadProvider` почне реєструвати провайдера при `ALREADY_INITIALIZED`, то в
сценарії двох екземплярів **обидва** ядра UAPKI працюватимуть через **один** об'єкт
`CmPkcs12`. Тоді `DEINIT` у будь-якому з них зруйнує провайдера для **обох** — новий
дефект замість старого, тільки з двома винуватцями. Кореневе виправлення має це
врахувати, інакше воно правильне лише для одного екземпляра — як і D.

### Третє місце, де чиститься список провайдерів — і доказ, що в 1С воно НЕ спрацювало

Хвіст `uapki_init` (`library-init.cpp:305-313`):

```cpp
cleanup:
    if (ret != RET_OK) {
        release_config();
        CmProviders::deinit();
        release_stores();
        HttpHelper::deinit();
    }
    return ret;
```

Тобто список провайдерів чиститься **не лише** в `DEINIT`, а й на **будь-якому
невдалому** `INIT`. Це третє місце, і воно зачіпає напрямки B/C.

Окремо: рання гілка `library-init.cpp:224` — **простий `return`, не через `cleanup`**.
Тому вимір §4.3 (три `INIT` -> `4106`) список **не чистив**, і в тому прогоні
`CmProviders::count()` лишався `1`.

**Логічний доказ, що в 1С список ніколи не наповнювався.** `cleanup` чистить лише
при `ret != RET_OK`, і той самий `ret` повертається наступним рядком. Отже
«список спорожнено» і «`errorCode: 0`» — **взаємовиключні за побудовою**. У 1С
спостерігався `errorCode: 0`, тож шлях через `cleanup` виключений повністю.

Лишається єдине: у тому екземплярі список **ніколи не наповнювався** — бо
`push_back` не відбувся через `ALREADY_INITIALIZED`. Це не альтернатива моделі двох
екземплярів, а **закриття єдиного іншого способу** отримати порожній список: модель
лишається без конкурентів.

**Наслідок для самотесту.** У 1С `errorCode: 0` означає, що самотест **пройшов**.
Отже те, що блокує 1С-сценарій, самотестом бути не може. `skipSelfTest` (§4.1)
знімає перешкоду шляху з `DEINIT`, а **не** 1С-шляху — ще один доказ, що це два
різні прояви, а не один дефект.

> **Практичне попередження до напрямків B/C, зміряти ДО релізу.** Після виправлення
> `ALREADY_INITIALIZED` повторний `INIT` у тому самому екземплярі може впертися в
> **самотест** — і тоді `cleanup` знесе список, давши **той самий симптом
> (`countCmProviders: 0`) з іншим стеком**. Тобто патч, який виглядатиме робочим на
> одному прогоні, може просто перемістити дефект.

### ГОЛОВНЕ ДЛЯ ТОГО, ХТО ВІЗЬМЕ ЗАДАЧУ

**Порядок переваг напрямків залежить від гіпотези, тож поки вона не закрита,
вибирати напрямок не можна взагалі.**

**Перший крок задачі — не «зробити D», а «перелічити завантажені модулі процесу
`1cv8`»** після відтворення дефекту: скільки разів присутні
`SimplyAddinConnectWin_x64.dll` (за іменем **і** за маскою `v8_*_c.`) та
`cm-pkcs12_x64.dll`, і з яких шляхів. Один цей вимір визначає, який із чотирьох
напрямків взагалі має сенс.

## 5. Чому це блокує продуктове використання

У бойовій 1С компонента живе в довгому процесі. Підпис працюватиме рівно доти, доки
об'єкт `AddinUAPKIConnect` не перестворять — після чого ПРРО почне отримувати
`UNKNOWN_PROVIDER`, а `INIT` і далі рапортуватиме успіх.

Особливо неприємні три властивості:

1. **Тихо.** `INIT` каже `errorCode: 0`. Єдина ознака — `countCmProviders: 0`, поле,
   яке прикладний код зазвичай не перевіряє.
2. **Невідтворювано з першого разу.** У свіжому процесі все працює, тож на тесті
   дефект не видно.
3. **Необоротно в межах процесу.** Полагодити сеанс не можна — лише перезапустити 1С.

Документація вже вимагає звіряти `countCmProviders` з нулем
(`docs/integration-1c/uapki.md` §5 і §1), і тестова обробка тепер на цьому
зупиняє ланцюг із діагностикою. Але це **виявлення, а не виправлення**.

## 6. Чотири напрямки — жоден не обраний

### Напрямок D. `DEINIT` + `INIT{skipSelfTest}` у нашій обгортці — НАЙДЕШЕВШИЙ, механіку зміряно

З'явився після §4.1 і виглядає найпростішим із усіх: при `countCmProviders == 0`
після `INIT` обгортка сама робить `DEINIT` і повторний `INIT` з
`"skipSelfTest": true`. Прозоро для 1С — прикладний бік про дефект взагалі не знає.

- **За:** цілком у нашому коді; upstream не чіпається; API бібліотеки не обходиться —
  використовується **документований** параметр; механіка **зміряна** (§4.1), а не
  припущена.
- **⚠️ ПРОТИ, вирішальне:** у сценарії двох екземплярів D **не працює взагалі** —
  `CmProviders::deinit` по порожньому вектору є no-op, і глобал не скидається
  (§4.4). D доведений лише для конфігурації з ОДНИМ екземпляром DLL.
- **Проти:** пропуск самотесту — рішення з наслідками для юридично значущого підпису
  (застереження в §4.1). Потрібне правило «`skipSelfTest` **лише** на повторному
  `INIT`», і його треба захистити механізмом, а не коментарем.
- **Що лишилось перевірити:** (1) чи працює той самий цикл **у процесі 1С**, а не лише
  в `uapki_selftest` — це різні хости, і саме 1С дала дефект; (2) чи `OPEN`/`SIGN`
  після такого повторного `INIT` справді працюють, чи піднявся лише лічильник;
  (3) **чи D узагалі лікує причину** — див. §4.3: якщо в процесі 1С живуть ДВА
  екземпляри нашої головної DLL, `DEINIT` в одному не впливає на глобал, утримуваний
  іншим, і D працюватиме так само нестабільно, як сам дефект.

### Перші три напрямки (сформульовані до виміру §4.1)

### Напрямок A. Виклик `provider_deinit` у DLL провайдера напряму

При `countCmProviders == 0` викликати `provider_deinit` через `LoadLibraryW` +
`GetProcAddress`, скинувши глобал, і повторити `INIT`.

- **За:** цілком у нашому коді.
- **За, і це може виявитись вирішальним:** дескриптор модуля в Windows
  **процесо-широкий**, тож A дістається до глобала, утримуваного ІНШИМ екземпляром
  нашої DLL, — єдиний із чотирьох, хто на це здатний (§4.4).
- **Проти:** обходить контракт UAPKI, лізе в чужу DLL напряму.
- **Коли обирати:** якщо вимір модулів покаже два екземпляри. Тоді A — не запасний,
  а основний.

### Напрямок B. Патч в UAPKI (upstream)

`CmProviders::loadProvider` має трактувати `RET_CM_ALREADY_INITIALIZED` як успіх:
провайдер ініціалізований і придатний, його треба зареєструвати.

```cpp
ret = storage->providerInit(jsonParams);
if (ret == RET_OK || ret == RET_CM_ALREADY_INITIALIZED) {
    ...
}
```

Окремо варто прибрати `(void)` у `setup_cm_providers` або хоча б логувати причину.

- **За:** виправляє першопричину для всіх користувачів бібліотеки; у проєкті вже є
  два змерджені upstream-PR (див. пам'ять `uapki-integration-state`), процес відомий.
- **Проти:** чужий репозиторій, цикл рев'ю; до мерджу потрібен форк-патч у сабмодулі
  (правки в `extern/uapki` комітяться **всередині сабмодуля**, `AGENTS.md`).
- **Перевірити перше:** чи `CmStorageProxy` після `ALREADY_INITIALIZED` справді
  придатний (чи коректно відпрацює `providerInfo`, `provider_open`).

### Напрямок C. Дисципліна на боці 1С

Тримати одну instance `AddinUAPKIConnect` на весь сеанс і не перестворювати.

- **За:** нічого не треба міняти в коді.
- **Проти:** **механізмом не захищено** — порушення тихе й діагностується лише по
  `countCmProviders`. Це не рішення, а обмеження, і воно має бути записане в
  `docs/integration-1c/uapki.md` явно, якщо оберуть саме його.

## 7. Як це тестувати (жоден із тестів ще не написаний)

Головна складність: **дефект не відтворюється в одному процесі харнеса**, бо кожен
прогін `native_host` — новий процес. Потрібен тест, що робить `INIT` двічі, імітуючи
перестворення об'єкта в тому самому процесі.

Мінімальний відтворювач — новий кейс у `tests/native_host.cpp`:

1. `LoadLibraryW` головної DLL, `GetClassObject`, `INIT` -> звірити `countCmProviders == 1`;
2. знищити об'єкт компоненти (`DestroyObject`), **не вивантажуючи DLL**;
3. створити об'єкт заново, `INIT` -> **очікується `countCmProviders == 0`** — це й є
   червоний, що доводить дефект;
4. після виправлення той самий кейс має давати `1`.

За правилом 1 `docs/architecture/testing-rules.md` цей `CHECK` треба побачити
червоним **до** виправлення — тут це виходить природно, бо дефект існує.

**Окремо перевірити:** чи `DestroyObject` + повторний `GetClassObject` у межах процесу
достатні, чи потрібне саме вивантаження/завантаження головної DLL — від цього залежить,
чи відтворює тест реальний сценарій 1С.
