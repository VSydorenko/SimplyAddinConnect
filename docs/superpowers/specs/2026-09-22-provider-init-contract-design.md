**Дата:** 2026-09-22
**Гілка:** `uapki-provider-init-contract` (від `origin/main`, `1007a9c`)
**Статус:** дизайн на рев'ю, план імплементації — окремо
**Вхід:** `docs/tasks/2026-09-22_provider_reinit_defect.md` — опис проблеми й доказова база
**Автор дизайну:** сесія-архітектор. **План і виконання:** окремою сесією.

## 1. Навіщо

### 1.1. Суть дефекту — одним реченням

У процесі живе **один** об'єкт `CmPkcs12` — глобал у `cm-pkcs12_xNN.dll`
(`extern/uapki/library/cm-pkcs12/src/main-cm-pkcs12.cpp:67`). Його час життя
**процесо-широкий**. Володіє ним `CmStorageProxy` всередині екземпляра UAPKI, чий час життя
**модульний** — стільки, скільки завантажений бінарник, що злінкував UAPKI.

> **Процесо-широкий ресурс із модульно-широким власником і неписаним контрактом, який усі
> реалізації прочитали як «власник рівно один».**

Контракт справді неписаний. `extern/uapki/library/common/cm-api/cm-api.h:62` — голі typedef'и:

```c
typedef CM_ERROR (*cm_provider_init_f) (CM_JSON_PCHAR providerParams);
typedef CM_ERROR (*cm_provider_deinit_f) (void);
```

Ні слова про повторний виклик, ні про кількох споживачів, ні про облік. Тому **обидві**
референсні реалізації незалежно вигадали однакову відповідь — «власник один»
(`main-cm-pkcs12.cpp:103` і `extern/uapki/library/cm-pkcs11/src/main-cm-pkcs11.cpp:85`, той
самий рядок), і реєстр UAPKI вигадав її втретє
(`extern/uapki/library/uapki/src/cm-providers.cpp:176`).

Другий екземпляр UAPKI в процесі — а Windows робить його буденним — цю домовленість тихо
ламає.

### 1.2. Причина, підсилювачі й наслідки — розділити

Задача-вхід перебирає чотири напрямки, і всі чотири лікують наслідок. Розкладка:

| Роль | Що саме | Де |
|---|---|---|
| **Причина** | неідемпотентний init без обліку власників | `main-cm-pkcs12.cpp:103`, `main-cm-pkcs11.cpp:85` |
| **Підсилювач: невидимість** | результат завантаження провайдера відкинуто `(void)`; `INIT` віддає `errorCode: 0` з нулем провайдерів | `extern/uapki/library/uapki/src/api/library-init.cpp:82` |
| **Підсилювач: необоротність** | сирий вказівник у реєстрі без деструктора → при руйнуванні статиків тече `CmStorageProxy` → `FreeLibrary` не кличеться → DLL лишається з брудним глобалом | `cm-providers.cpp:47`, `extern/uapki/library/common/loaders/cm-loader.cpp:134` |
| **Наслідок** | `4102 UNKNOWN_PROVIDER`, `4121 STORAGE_NOT_OPEN` | — |

Прибери обидва підсилювачі — дефект лишиться, просто стане гучним і самовиліковним.
Прибери причину — зникне він сам.

### 1.3. Антипатерни, названі поіменно

1. **Неідемпотентний ініціалізатор.** Функція з постумовою «ресурс ініціалізовано»
   **досягла мети**, якщо ресурс уже ініціалізовано. Повертати помилку за виконану
   постумову — семантична помилка. `mkdir -p`, `CREATE TABLE IF NOT EXISTS`, HTTP `PUT`.
2. **Володіння без обліку через межу DLL.** Індустрія зійшлася на лічильнику посилань у парі
   init/shutdown: `CoInitialize`/`CoUninitialize`, `WSAStartup`/`WSACleanup`. Відомий
   контрприклад — `curl_global_init` **без** лічильника.
3. **Володіння за домовленістю замість RAII.** Інваріант тримає код у сусідньому файлі
   (`CmProviders::deinit`, `cm-providers.cpp:185`), а не тип. Будь-який інший шлях
   руйнування тече.
4. **Часткова невдача, зведена до повного успіху.** Підсистема вміє впасти наполовину й не
   вміє про це сказати.

**Прецедент — у сусідньому файлі цієї ж бібліотеки.**
`extern/uapki/library/cm-pkcs11/src/storage/cryptoki-storage.cpp:2054` мапить
`CKR_CRYPTOKI_ALREADY_INITIALIZED` → `RET_CM_ALREADY_INITIALIZED`. Тобто PKCS#11 має точно цю
саму проблему, і світ PKCS#11 її вже розв'язав: `p11-kit` у *managed mode* існує саме для
того, щоб кілька споживачів ділили один модуль із обліком посилань.

### 1.4. Ідеал, розглянутий і відкинутий

Архітектурно правильно було б прибрати глобал: `provider_init` віддає **контекст-хендл**,
кожен споживач володіє своїм (`sqlite3_open`, `curl_easy_init`). Можна навіть без ABI-злому —
опціональні `*_ex`-експорти, яким `CmLoader` віддає перевагу за наявності.

**Ціна:** шість нових експортів, подвійні шляхи в лоадері, проксі й обох провайдерах.
**Виграш для `cm-pkcs12`: нульовий** — клас тримає єдине поле `m_DefaultParam`
(`extern/uapki/library/cm-pkcs12/src/cm-pkcs12.h:40`), `open()` виділяє незалежний
`SessionPkcs12Context` (`extern/uapki/library/cm-pkcs12/src/cm-pkcs12.cpp:84`), а `setDefault`
**копіює** значення, не тримає вказівник
(`extern/uapki/library/cm-pkcs12/src/storage/file-storage.cpp:69`). Ізолювати нічого — воно
вже ізольоване.

Правильний довгостроковий напрямок, неправильне рішення сьогодні → **TD-9**.

## 4. C1 — ідемпотентний init з обліком посилань

### 4.1. Патч

`extern/uapki/library/cm-pkcs12/src/main-cm-pkcs12.cpp`:

```cpp
static CmPkcs12* cm_pkcs12 = nullptr;
static size_t    cm_pkcs12_refcnt = 0;          // НОВЕ

CM_EXPORT CM_ERROR provider_init (CM_JSON_PCHAR providerParams)
{
    CM_ERROR cm_err = RET_CM_GENERAL_ERROR;
    if (!cm_pkcs12) {
        cm_pkcs12 = new CmPkcs12();
        if (cm_pkcs12) {
            cm_err = cm_pkcs12->parseConfig(providerParams, cm_pkcs12->getDefaultParam());
            if (cm_err != RET_OK) {
                delete cm_pkcs12;
                cm_pkcs12 = nullptr;
            }
            else {
                cm_pkcs12_refcnt = 1;           // НОВЕ
            }
        }
    }
    else {
        cm_pkcs12_refcnt++;                     // НОВЕ: було RET_CM_ALREADY_INITIALIZED
        cm_err = RET_OK;
    }
    return cm_err;
}

CM_EXPORT CM_ERROR provider_deinit (void)
{
    if (!cm_pkcs12) return RET_CM_NOT_INITIALIZED;
    if (cm_pkcs12_refcnt > 0) cm_pkcs12_refcnt--;
    if (cm_pkcs12_refcnt == 0) {
        delete cm_pkcs12;
        cm_pkcs12 = nullptr;
    }
    return RET_OK;
}
```

Симетрично для `cm_cryptoki` в `main-cm-pkcs11.cpp:85` — форма коду там ідентична.

### 4.2. Записаний контракт

`cm-api.h:62` — коментар над typedef'ами (англійською, як решта файла), що фіксує три
зобов'язання реалізації провайдера:

1. `init` **ідемпотентний**: на вже ініціалізованому провайдері повертає `RET_OK`, а не
   `RET_CM_ALREADY_INITIALIZED`;
2. провайдер **веде облік** викликів `init`/`deinit`;
3. `deinit` звільняє ресурс **на нулі** лічильника; при лічильнику > 0 повертає `RET_OK` і
   ресурс лишає живим.

Без цього пункту патч лишається «виправленням двох файлів», а не виправленням контракту.
`RET_CM_ALREADY_INITIALIZED` (`extern/uapki/library/common/cm-api/cm-errors.h:40`) **не
видаляємо** — константа лишається для сумісності зі сторонніми провайдерами.

### 4.3. Крайові випадки — вирішені свідомо

| Випадок | Рішення | Чому саме так |
|---|---|---|
| другий `init` з **іншими** параметрами | перемагає перший, мовчки | висновок із коду: параметри сесії вже перекривають глобальні на `provider_open` (`cm-pkcs12.cpp:107`), тож глобал і є справжній *default*. Документується в контракті §4.2 |
| `deinit` при лічильнику > 1 | `RET_OK`, об'єкт живий | у того, хто викликав, `m_IsInitialized` стає `false` — і це правильно **для нього**. Чужі відкриті сесії не страждають |
| `deinit` без жодного `init` | `RET_CM_NOT_INITIALIZED` | поведінка не змінюється |
| лічильник «протікає» (споживач зник без `deinit`) | ресурс лишається живим | це **безпечний** бік помилки: саме той стан, у якому все працює. Витік адресує C2 |
| гонка двох потоків на першому `init` | **не адресуємо** | існує сьогодні, ніхто її не міряв. Правило репозиторію — не робити тверджень ширших за вимір. Мьютекс змінив би поведінку в незміряному сценарії й розширив поверхню рев'ю → **TD-10** |

### 4.4. Перевірка, що шар обрано правильно

Після C1 рядок `extern/uapki/library/uapki/src/cm-storage-proxy.cpp:123`
(`m_IsInitialized = (ret == RET_OK);`) стає правильним **сам собою**, бо `ret` тепер і є
`RET_OK`. Пастка §4.2 задачі-входу — та, на якій спіткнулась сесія `prro-uapki-spec`, подавши
половину патча, — **зникає, а не обходиться**.

> **Діагностична ознака шару:** виправлення, яке вимагає двох узгоджених правок, щоб нічого не
> зламати, стоїть не на тому шарі. C1 вимагає однієї правки на провайдер і робить усе нижче за
> течією правильним без змін.

## 5. C2 — володіння виражене типом

### 5.1. Патч

`cm-providers.cpp:47`:

```cpp
typedef struct CM_PROVIDER_ST {
    const string                    id;
    std::unique_ptr<CmStorageProxy> storage;        // було: CmStorageProxy*
    CM_PROVIDER_ST (const string& iId, CmStorageProxy* iCmSession)
        : id(iId), storage(iCmSession) { }
    CM_PROVIDER_ST (CM_PROVIDER_ST&&) = default;    // vector потребує move-construct
} CM_PROVIDER;
```

Копіювальний конструктор стає неявно видаленим (`unique_ptr`) — це бажано. `const string id`
move-конструктору не заважає (рядок копіюється). Наслідки по файлу:

- `:176` `push_back(CM_PROVIDER(s_id, storage))` — працює через move-конструктор;
- `:185` `CmProviders::deinit` — `delete it.storage; it.storage = nullptr;` → `it.storage.reset();`
- шість місць читання (`:204`, `:247`, `:277`, `:314` та сусідні) — `.storage` → `.storage.get()`.

### 5.2. Що це дає

Руйнування статиків при вивантаженні DLL іде повним ланцюгом:
`~CmStorageProxy` (`cm-storage-proxy.cpp:54`) → `providerDeinit()` → лічильник −1 →
`~CmLoader` → `CmLoader::unload` (`cm-loader.cpp:134`) → `FreeLibrary`.

### 5.3. Чому C2 входить, хоч дефект без неї вже не проявляється

Після C1 витік **нешкідливий** — він лише не дає лічильнику впасти до нуля, а це саме той
стан, у якому все працює. Але витік **реальний і безмежний**: кожен цикл вивантаження лишає
`CmStorageProxy` + `CmLoader` + прип'яту `cm-pkcs12_xNN.dll`. У довгому процесі 1С із
періодичним оновленням розширення це росте без межі. І саме він зробив дефект необоротним —
тобто це друга половина того самого механізму, а не супутня прибирачка.

## 6. C3 — бібліотека звітує факти

### 6.1. Патч

`library-init.cpp:82` — `(void)` іде, сигнатура `setup_cm_providers` отримує
`JSON_Object* joResult`, і в результат додається **адитивний** об'єкт:

```json
"cmProviders": {
  "requested": 2,
  "loaded": 1,
  "failed": [ { "lib": "cm-pkcs11", "errorCode": 1027, "error": "CM_LIBRARY_NOT_LOADED" } ]
}
```

Рядок помилки — через наявний `error_code_to_str` (оголошено в
`extern/uapki/library/uapki/src/api/api-json.cpp:45`).

### 6.2. Межі зміни — названі явно

- **Толерантність не міняється.** Перелік `allowedProviders` законно може містити провайдера,
  відсутнього на цій машині; `setup_cm_providers` і далі повертає `RET_OK`, `INIT` і далі не
  падає. Це свідомо: інакше зміна була б ламкою для наявних конфігурацій.
- **`countCmProviders` (`library-init.cpp:273`) лишається незайманим** — сумісність.
- Зміна суто адитивна: споживач, який нового поля не читає, нічого не помічає.

### 6.3. Чому це в обсязі

C3 не потрібна, щоб дефект зник. Вона закриває **клас**: наступна невдача завантаження —
брак файлу, не та розрядність, карантин антивіруса (три з них задача-вхід перевіряла в §3) —
теж перестає бути німою. Саме німота коштувала цьому проєкту місяць.

## 7. C4 — політика: нуль провайдерів є помилкою

### 7.1. Правило

> Просили провайдерів (`cmProviders.allowedProviders` не порожній) і піднявся **нуль** —
> `INIT` для 1С є **помилкою**.

Саме нуль, а не «менше, ніж очікували»: 1 з 2 — законна ситуація (див. §6.2).

### 7.2. Реалізація

`src/helpers/UAPKIConnect/UAPKIConnectHelper.cpp:493` — `WarnIfProvidersNotLoaded` сьогодні
пише WARN у **наш** лог, якого 1С не бачить. Стає функцією, що не лише попереджає, а й формує
вердикт; точка виклику — `:734`.

Відповідь бібліотеки **зберігається цілою** у вкладеному полі — прозорість не втрачається,
втрачається брехня:

```json
{ "errorCode": 502,
  "error": "NO_CM_PROVIDERS_LOADED: requested 1, loaded 0",
  "method": "INIT",
  "uapkiResponse": { "...": "відповідь бібліотеки дослівно" } }
```

`502` — з **нашої** смуги кодів обгортки (400/500/503 уже вживані — `:643`, `:668`, `:741`),
не з простору кодів UAPKI. Колізії немає, і за кодом видно, хто говорить.

### 7.3. Це зміна контракту — її анонсуємо

Споживач — `SMP_SimplyConnect` (маршрут ПРРО `СМП_КриптографияUAPKIКлиент`). До злиття цієї
роботи сесія `prro-uapki-spec` отримує повідомлення з новим форматом відповіді й правилом.
Факти про їхній бік — лише з `file:line` і версією вивантаження; за їхній бік не вирішуємо.

### 7.4. Чому не «хай 1С дивиться `countCmProviders`»

Так уже записано в `docs/integration-1c/uapki.md` §5, і саме так дефект прожив місяць:
угода без механізму порушується тихо. Репозиторій цього класу гарантій не приймає.

## 8. C5 — `INIT` ідемпотентний для 1С

### 8.1. Проблема

`library-init.cpp:224` — повторний `INIT` у тому самому екземплярі UAPKI віддає
`4106 ALREADY_INITIALIZED` **із порожнім результатом**, хоча бібліотека жива й придатна.
Вимір задачі-входу §4.3: три `INIT` поспіль → `0`, `4106`, `4106`. Наша обгортка трактує це як
невдачу, і 1С отримує помилку там, де все справне.

Це той самий антипатерн, що й C1, шаром вище. Без C5 сценарій із заголовка задачі —
«повторний `INIT` у живому процесі» — лишається зламаним, просто іншим шляхом.

### 8.2. Рішення — вимір, а не кеш

У JSON-API є метод **`PROVIDERS`** (`api-json.cpp:81` →
`extern/uapki/library/uapki/src/api/library-list-providers.cpp:38`), що віддає живий
`CmProviders::count()` **незалежно** від стану ініціалізації.

Отже на `INIT` → `4106` обгортка:

1. викликає `PROVIDERS`;
2. рахує елементи масиву `providers`;
3. якщо їх **≥ 1** — віддає 1С успішну відповідь із реальним числом і явною ознакою:

```json
{ "errorCode": 0, "method": "INIT",
  "result": { "countCmProviders": 1, "alreadyInitialized": true } }
```

4. якщо їх **нуль** — спрацьовує правило C4 (`INIT` є помилкою).

**Чому не кеш останнього вдалого `INIT`.** Кеш — це пам'ять про минуле, і його правильність
довелося б доводити інваріантом «поки `isInitialized()`, склад провайдерів незмінний». Проба
`PROVIDERS` — це **вимір теперішнього**. Інваріанту доводити не треба, бо на нього не
спираємось.

### 8.3. Межа

`alreadyInitialized: true` означає рівно «бібліотека вже була піднята в цьому екземплярі
модуля, і провайдери в ній живі». Воно **не** означає, що параметри поточного `INIT`
застосовано — вони не застосовані, бо бібліотека не переініціалізовувалась. Це записується в
`docs/integration-1c/uapki.md` §4.1 прямим текстом: щоб змінити параметри, потрібен `DEINIT` і
`INIT` (з `skipSelfTest`, див. §4.1 задачі-входу).

## 10. Доставка

### 10.1. Форк — основний шлях, не запасний

Апстрім показав обидві свої грані: наші PR #25/#26 змерджено за день, але PR #16 закрито одним
рядком, а PR #27 («library may be loaded and unloaded multiple times» — наш же сценарій) висить
відкритим із 2026-07-20. **Планувати роботу під мердж не можна.**

Ми самі збираємо і `cm-pkcs12_xNN.dll`, і статичний UAPKI (`AGENTS.md`, розділ «Збірка»), тож
патч у сабмодулі потрапляє в наш артефакт негайно, без жодної залежності від апстріму.

### 10.2. Де це робиться

**Окремий форк відкривати не треба — він уже є і вже підключений.** `.gitmodules` вказує на
`https://github.com/VSydorenko/UAPKI` (`branch = main-dev`), тож каталог `extern/uapki` у
робочому дереві — повноцінний чекаут форку з двома ремоутами: `origin` (форк) і `upstream`
(`specinfo-ua/UAPKI`). Свіжий клон тягне сабмодуль із форку, отже наші комміти досяжні — так
само працювали PR #25/#26.

Правки комітяться **всередині сабмодуля**, у корені комітиться лише покажчик (gitlink) —
`AGENTS.md`, Git-нюанси. `extern/uapki` — частина спільного робочого дерева, тож створення
гілки там перемикає його так само, як і в корені.

### 10.3. Розкладка гілок

Три зміни **файлово не перетинаються**, тож ідуть трьома незалежними PR без конфліктів. Усі
три — від `fda2148` (= `upstream/main` = тег `v2.0.17`), щоб PR не залежали один від одного.

| | Гілка у форку | Які файли чіпає |
|---|---|---|
| C1 | `fix/provider-init-refcount` | `main-cm-pkcs12.cpp`, `main-cm-pkcs11.cpp`, `cm-api.h` |
| C2 | `fix/cm-providers-raii` | `cm-providers.cpp` |
| C3 | `feat/cm-providers-report` | `library-init.cpp` |
| — | `simplyaddin/provider-contract` | інтеграційна: злиття трьох; **сабмодуль вказує сюди** |

**Чому інтеграційна гілка, а не `main-dev`.** Зараз `main-dev` форку — точна копія апстріму,
власних правок форк не тримає. Саме це робить крок «після мерджу вернутись на апстрімовий тег»
тривіальним. Патчі на `main-dev` цю чистоту знищили б.

**Наслідок:** `.gitmodules` оновлюється на `branch = simplyaddin/provider-contract`, інакше
поле бреше про те, де лежить наш стан. Після мерджу в апстрім — назад на тег і `main-dev`.

### 10.4. Порядок

1. Розробка йде **на інтеграційній гілці**, окремим коммітом на кожну зміну (C1, C2, C3).
   Перемикати спільне дерево тричі задля трьох гілок не треба: гілки під PR нарізаються
   **наприкінці**, від `fda2148`, через `cherry-pick` відповідного комміту. Конфліктів не
   буде за побудовою — зміни файлово не перетинаються (§10.3).
2. Сабмодуль у корені перемикається на інтеграційну гілку; gitlink і `.gitmodules` комітяться
   разом.
3. Три окремі PR в `specinfo-ua/UAPKI` — C1, C2, C3. Малі й незалежні: саме той формат, що тут
   мерджиться за день.
4. Issue про ідемпотентний `uapki_init` — з описом принципу й готовим патчем у кишені.
5. Після мерджу — сабмодуль на апстрімовий тег, `.gitmodules` назад на `main-dev`, виняток в

## 11. Тестування

Рівні гейта не міняються; додається один новий і один кейс до наявного.

### 11.1. Новий рівень L1.5 — контракт провайдера (без 1С, без головної DLL)

Нова ціль `tests/provider_contract_selftest.cpp` (потребує `-WithUAPKI`, бо провайдер
збирається лише з ним). Працює з `cm-pkcs12_xNN.dll` напряму через `LoadLibraryW` +
`GetProcAddress`:

| CHECK | До патча | Після |
|---|---|---|
| `provider_init` вдруге | `RET_CM_ALREADY_INITIALIZED` | **`RET_OK`** |
| `provider_open` після другого `init` | — | сесія відкривається |
| `provider_deinit` при лічильнику 2 | `RET_OK`, об'єкт **знищено** | `RET_OK`, об'єкт **живий** (доводиться наступним `provider_open`) |
| `provider_deinit` до нуля | — | наступний `provider_open` → `RET_CM_NOT_INITIALIZED` |
| `provider_deinit` без `init` | `RET_CM_NOT_INITIALIZED` | без змін |

### 11.2. Детермінований відтворювач дефекту — кейс у `tests/native_host.cpp`

Два екземпляри головної DLL в одному процесі, **за двома різними шляхами** (друга — копія в
тимчасовому каталозі). Windows дає два модулі з власними статиками — точна модель §4.4
задачі-входу, без жодних припущень про поведінку 1С.

1. `LoadLibraryW` копії №1 → `GetClassObject` → `INIT` → **`countCmProviders == 1`**;
2. `LoadLibraryW` копії №2 (інший шлях) → `GetClassObject` → `INIT`;
3. **до патча:** `countCmProviders == 0` — це червоний, що доводить дефект;
4. **після:** `countCmProviders == 1`, і `OPEN`+`SIGN` у другому екземплярі проходять.

Пункт 4 обов'язковий: лічильник, що піднявся, ще не означає робочого провайдера.

**Це заодно закриває відкрите питання §7 задачі-входу:** `DestroyObject` + перестворення
об'єкта дефекту **не** відтворює — вимір §4.3 дав `4106` у тому самому екземплярі. Потрібні
саме два модулі.

### 11.3. Кейс на C5

Той самий процес, **той самий** екземпляр: `INIT` → `INIT`. До C5 обгортка віддає `4106`;
після — `errorCode: 0` з `alreadyInitialized: true` і `countCmProviders: 1`.

### 11.4. Негативна верифікація — обов'язкова

Правило 1 `docs/architecture/testing-rules.md`: кожен новий `CHECK` побачити червоним. Тут це
виходить природно — дефект існує, тому §11.1 і §11.2 червоні **до** патча за побудовою. Для
§11.3 і для порогів C4 червоне здобувається тимчасовим поверненням дефектної поведінки.

Правило 2 теж діє: перед перевіркою «провайдер живий» стан доводиться **парою предикатів**,
якою код розрізняє стани, — `provider_open` успішний **і** `PROVIDERS` дає ≥ 1. Очікування
виходу з попереднього стану доказом не є.

### 11.5. Гейт

`run_tests.ps1` отримує L1.5 між L1 і L2/L3. Повний прогін x64 + x86 зелений — умова
приймання.

## 14. Межі, названі явно

- **Гіпотезу двох екземплярів у 1С не доведено** і ця робота її не доводить. C1 працює під
  обома поясненнями (два екземпляри / витік із перезавантаженням), тому доведення не потрібне
  для вибору. Якщо колись знадобиться — метод у §4.4 задачі-входу, з обома масками пошуку
  (`ім'я компоненти` **і** префікс `v8_*_c.`).
- **Гонки в `provider_init` не адресовано** (TD-10).
- **Сторонні провайдери**, що не ведуть обліку, лишаються зламаними в сценарії двох
  споживачів. Це свідомо: ми виправляємо контракт і референсні реалізації, а не робимо
  спецкейс у реєстрі.
- **Не перевіряється цим дизайном:** чи платформа 1С справді дає два модулі під одним
  символьним іменем із різних адрес. У репозиторії це неперевірюване.
