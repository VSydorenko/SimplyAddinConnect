# Альтернативні джерела ключа для UAPKI (токени, HSM, зовнішній підпис) — дизайн

**Дата:** 2026-08-28 · **Гілка:** `uapki-sync-v2.0.16` · **Статус:** **намір зафіксовано; до
реалізації НЕ затверджено.** План імплементації пишемо пізніше — коли з'явиться зрозумілий
сценарій і доступ до фізичного носія (див. §8.2 «Тригери повернення»).

Документ фіксує напрацьовану фактуру, щоб вона не загубилась. Усі твердження нижче звірені з
кодом сабмодуля `extern/uapki` на комміті `325be0d` (реліз **v2.0.16**), настановою
`extern/uapki/doc/UAPKI-PM-2.0.16.md` і офіційними бінарниками релізу. Посилання на джерела —
у §9.

## 1. Мета й контекст

Сьогодні `AddinUAPKIConnect` уміє рівно **один** спосіб дістати підпис: файловий контейнер
PKCS#12 через провайдер `cm-pkcs12`. Усе інше — апаратні носії, смарт-карти, HSM, хмарний КЕП —
поза досяжністю. Для частини клієнтів (юрособи, вимоги ЦСК до захищеного носія) це не обмеження
зручності, а неможливість працювати взагалі.

Мета документа — зафіксувати **три напрями розширення**, їхню механіку, обсяг робіт і відкриті
питання. Не спроєктувати реалізацію: сценарій використання ще невідомий, фізичних носіїв на
руках немає, а код провайдера PKCS#11 опубліковано лише 25.08.2026 і він ще стабілізується.

### 1.1. Ключовий факт: це не «ще один провайдер», а дві різні осі

Інтуїція «додати підтримку токенів = зібрати другий провайдер» правильна лише наполовину.
Насправді напрями лежать на **двох незалежних осях**:

**Вісь 1 — звідки ядро бере ключ.** UAPKI знає рівно три CM-провайдери:
`cm-pkcs12` (файли), `cm-pkcs11` (токени/смарт-карти/HSM), `cm-almaz1c` (закритий, ІІТ). Тут
працює механізм «каталог провайдерів»: ядро вантажить провайдер-DLL у рантаймі й ходить у неї
за ключем. Розширення = **нова DLL у нашій поставці**.

**Вісь 2 — ключ узагалі поза UAPKI.** У v2.0.16 з'явився метод `BUILD_CMS_2PASS`: ядро будує
`signedAttributes`, віддає їхній геш, підпис робить **хтось інший**, ядро складає готовий
CAdES з отриманих байтів. Приватного ключа воно не бачить ніколи. Тут розширення = **не DLL, а
оркестрація**, і, найімовірніше, взагалі без C++.

Наслідок для планування: напрями A і B — це збірка та поставка; напрям C — це протокол
взаємодії. Вони не конкурують і можуть робитись у будь-якому порядку.

## 2. Незмінні обмеження

Ці рамки діють для будь-якого з напрямів і не обговорюються в межах цього документа.

1. **Гібридна архітектура лишається.** Крипто-ядро статично в головній DLL; провайдери —
   окремі DLL, які ядро вантажить у рантаймі. Статичного реєстру провайдерів у UAPKI немає
   (підтверджено автором бібліотеки), тож «однією DLL» бути не може.
2. **Самодостатність поставки.** 1С не розпаковує з ZIP нічого, крім файлів з `manifest.xml`,
   тому провайдер їде RCDATA-ресурсом усередині головної DLL і розгортається при `INIT`.
   Будь-який новий провайдер має вкладатись у цю ж схему — або свідомо її ламати з
   зафіксованим обґрунтуванням (§6.1).
3. **Один функціональний метод у 1С.** Компонента виставляє `ВызватьUAPKI(Метод, JSONПараметри)`.
   Нові можливості UAPKI за замовчуванням доступні з 1С **без правок C++** — окрім випадків,
   коли потрібна логіка на стороні компоненти.
4. **Арх-суфікс імен наших DLL** (`_x86` / `_x64`) обов'язковий: у плоскому ZIP/каталозі два
   бінарники різної розрядності не можуть мати однакове ім'я.
5. **Форк UAPKI — транслятор, не кодова база.** Власного функціоналу у форку не накопичуємо;
   потрібні правки йдуть атомарними PR в upstream (див. `docs/architecture/uapki.md` §7).

## 3. Напрям A — `cm-pkcs11`: токени, смарт-карти, HSM

### 3.1. Що це і чого воно варте

`library/cm-pkcs11` (v1.0.12) — CM-провайдер, який сам із залізом не говорить. Він **міст до
вендорського PKCS#11-модуля**, що ставиться разом із ПЗ носія. Ми віддаємо йому перелік модулів,
він їх вантажить, опитує слоти й показує ядру знайдені носії як сховища ключів.

Відкритий код провайдера з'явився **саме в релізі v2.0.16**: у changelog — «CM-PKCS11: Publish
code of CM-provider for PKCS11 tokens/smart cards». Це нова, ще не обкатана спільнотою частина;
у тому ж релізі є «Fix method ADD_CERT (bug when add cert to token)», тобто токенні сценарії
активно правлять.

### 3.2. Конфігурація

Провайдер налаштовується через `cmProviders.allowedProviders[].config`, який ядро серіалізує
й передає в `provider_init`:

```jsonc
{ "lib": "cm-pkcs11", "config": {
    "subjectKeyId": false,                                          // на рівні провайдера
    "modules": [
      { "name": "sisp11",         "ekuDevice": true, "pka": true }, // Спецінформсистеми
      { "name": "Av337CryptokiD", "ekuDevice": true },              // Автор
      { "name": "avcryptokinxt",  "ekuDevice": true }               // Avest
    ] } }
```

Імена модулів узяті з настанови UAPKI, це не здогадка. Розпізнавані моделі носіїв (у коді
провайдера): DIAMOND 1000/2000/3000/4000, OLYMP HSM, OLYMP mini HSM (Спецінформсистеми);
AvestKey (AvestUA); CC-337 RSA DSTU, ST-338 (Автор); E.key_Almaz-1C, NCM_Gryada301 (ІІТ);
**SoftHSM v2** (для тестування).

### 3.3. Що це дає прикладній частині

**API з боку 1С не змінюється взагалі.** `OPEN` бере ті самі поля — просто `provider: "PKCS11"`
замість `"PKCS12"`, `storage` — серійний номер носія замість шляху до файлу, `password` — PIN.
Далі `SELECT_KEY` / `SIGN` / `VERIFY` — байт у байт наш поточний потік. Це головна причина, чому
напрям взагалі реалістичний.

**Оживають два методи, які зараз мертві.** `cm-pkcs12` експортує рівно 7 обов'язкових CM-символів;
`cm-pkcs11` — **9**: додатково `provider_list_storages` і `provider_storage_info`. Тобто вперше
починають працювати методи ядра `STORAGES` і `STORAGE_INFO`:

- `STORAGES` — перелік підключених носіїв (серійник, модель, виробник). У 1С це дає **вибір зі
  списку носіїв** замість «вкажіть шлях до файлу».
- `STORAGE_INFO` — стан PIN: `passwordAttemptsLeft`, `passwordLocked`, `passwordFinalTry`,
  `passwordCountLow`, `passwordToBeChanged`, `passwordMinLen`/`MaxLen`. Дозволяє попередити
  користувача перед останньою спробою й не заблокувати носій.

**Ключ не залишає носій** — власне, причина існування апаратних носіїв.

**Батч-підпис.** `cm_key_sign` приймає **масив хешів за один виклик**. Токени повільні (сотні
мілісекунд на підпис), і для Z-звітів та пакетів чеків ПРРО це принципово.

**Повний набір операцій, не лише підпис.** Реалізовано: логін/логаут, перелік і вибір ключів,
**генерація ключа на носії**, видалення ключа, CSR із ключа на носії, читання/додавання/видалення
сертифікатів на носії, зміна PIN, `randomBytes` з апаратного ГВЧ, а також `dh_wrap`/`dh_unwrap` —
тобто наші `ENCRYPT`/`DECRYPT` (envelopedData) теж працюють. **Не** реалізовано лише `importKey`
(залити наявний ключ на носій через цей API не можна — і це правильно).

**Алгоритми.** DSTU 4145 (з ГОСТ 34.311 та Купиною-256/384/512), ECDSA і RSA. У заголовку
вендорських механізмів уже присутні **Вершина** і **Скеля** — нові українські алгоритми; коли ЦСК
на них перейдуть, з нашого боку роботи не буде.

### 3.4. Обсяг робіт із нашого боку

1. **Друга SHARED-ціль** у `CMake/uapki_full_static.cmake` за зразком `cm-pkcs12-provider`.
   Джерела ширші: `cm-pkcs11/src` + `src/storage` + увесь `common/cryptoki` + більший список
   `common/pkix` (додаються `certreq-builder.cpp`, `dstu-ns.cpp`, `extnreq-helper.cpp`). `curl`
   не потрібен. Головний технічний ризик — `LNK2005` на спільних об'єктниках: спільні джерела
   треба брати **лінкуванням статичних цілей**, а не другою компіляцією (та сама граблина, що
   вже була з `cm-pkcs12`).
2. **Другий RCDATA-ресурс** і розгортання поруч із першим. Головна DLL виросте орієнтовно на
   ~1 МБ на архітектуру.
3. **Хелпер `UAPKIConnectHelper`** — навчити двом провайдерам: дефолтна ін'єкція `cmProviders`
   зараз додає рівно `cm-pkcs12`; `EnsureProviderDeployed` розгортає один ресурс;
   `WarnIfProvidersNotLoaded` звіряє одну очікувану кількість. Механіка допису арх-суфікса вже
   ітерує масив `allowedProviders`, тобто ця частина готова.
4. **Діагностика через `STORAGES`** — фактично новий обов'язковий крок після `INIT` (§3.6).

### 3.5. Чого ми не контролюємо

**Вендорський PKCS#11-модуль ми не постачаємо.** Його ставить клієнт разом із ПЗ носія.
Вантажиться модуль за **голим іменем** (лоадер PKCS#11 не додає каталог, на відміну від
`CmLoader`), тобто через стандартний пошук DLL Windows — або повним шляхом, якщо вписати його в
`name`. Наслідки:

- **Розрядність має збігатися з процесом 1С.** 32-бітний клієнт не завантажить 64-бітний модуль;
  наш арх-суфікс рятує лише нашу DLL, не вендорську.
- Кириличні шляхи вже безпечні: завантаження йде через `dl_load_library_utf8` (наш PR #26,
  прийнятий в upstream).

### 3.6. Три «тихі» точки збою

Це найважливіше для якості поставки. Провал на будь-якому з трьох рівнів **не повертає помилки**:

| Рівень | Що може піти не так | Як помітити |
|---|---|---|
| 1 | Наш `cm-pkcs11_<arch>.dll` не завантажився | `result.countCmProviders` у відповіді `INIT` менше очікуваного |
| 2 | Вендорський модуль не знайдено / не тієї розрядності | `CmCryptoki::init` **завжди** повертає `RET_OK` — не видно ніяк |
| 3 | Модуль піднявся, але носій не вставлено | теж не видно з `INIT` |

Єдиний чесний індикатор рівнів 2–3 — виклик **`STORAGES`** одразу після `INIT`: порожній перелік
або `RET_CM_LIBRARY_NOT_LOADED` означає, що щось не так. Це треба закласти в діагностику з
першого дня, інакше повториться історія з мовчазним `countCmProviders:0`.

Додатковий нюанс: **перелік модулів фіксується на `INIT`** (слоти пере-скануються на кожен
`STORAGES`, а модулі — ні). Стратегія: передавати одразу всі відомі імена модулів; ті, що не
завантажились, провайдер мовчки пропускає.

### 3.7. Тестування — слабке місце напряму

Upstream **не має жодного тесту** на PKCS#11. SoftHSM v2 розпізнається провайдером, а
`cm_key_sign` уміє RSA/ECDSA, а не тільки ДСТУ — тобто на SoftHSM можна прогнати всю механіку
(перелік носіїв → логін → ключі → вибір → підпис) без заліза. Але **українську криптографію
SoftHSM не вміє**, і жодного реального носія не емулює. Отже:

- **L-p-рівень на SoftHSM** дасть покриття плюмбінгу й регресійний захист збірки;
- **реальне підтвердження** можливе лише з фізичним носієм у руках.

Планувати напрям, розраховуючи закрити його самим лише SoftHSM, не можна.

## 4. Напрям B — прогалина ІІТ (`cm-almaz1c`)

Настанова UAPKI в прикладах конфігурації перелічує три провайдери: `cm-pkcs11`, `cm-pkcs12` і
**`cm-almaz1c`**. Останнього **немає у відкритому репозиторії** — це закритий провайдер під носії
ІІТ.

Водночас `cm-pkcs11` явно розпізнає моделі `E.key_Almaz-1C` і `NCM_Gryada301` — тобто
Спецінформсистеми передбачили роботу з носіями ІІТ і через звичайний PKCS#11. Звідси **відкрите
питання, яке потребує перевірки на живому носії:**

- носії ІІТ покриваються через `cm-pkcs11` + PKCS#11-модуль ІІТ — тоді окремий провайдер не
  потрібен;
- або `cm-almaz1c` існує саме тому, що PKCS#11-шлях для них неповний — тоді треба звертатись до
  Спецінформсистем по бінарник, і це вже питання ліцензії й поставки чужого закритого модуля.

До відповіді на це питання **не можна обіцяти підтримку носіїв ІІТ**. Це найважливіший ризик
покриття ринку в усьому документі: ІІТ — один із найпоширеніших ЦСК в Україні.

## 5. Напрям C — зовнішнє джерело підпису (`BUILD_CMS_2PASS`)

### 5.1. Механіка

Метод, доданий у v2.0.16, розриває підпис на два проходи:

1. **Прохід 1 (`step1`)** — UAPKI будує структуру `signedAttributes` і повертає її байти, а за
   запитом (`digestAlgo`) — ще й геш цих байтів у `digestBytes`. **Приватний ключ не потрібен.**
2. **Ззовні** — геш підписує будь-хто: хмарний ЦСК через свій API, Дія.Підпис, віддалений HSM,
   інший процес, інша машина.
3. **Прохід 2 (`step2`)** — повертаємо в UAPKI `bytes` (підписані атрибути), `signBytes`,
   `signAlgo`, `certId` — і ядро складає готовий PKCS#7. Підтримувані формати: `CMS`,
   `CAdES-BES`, `CAdES-T`, `CAdES-XL`, `CAdES-A`.

Для CSR є симетричний `BUILD_CSR_2PASS`.

### 5.2. Чому це важливо саме нам

**Гіпотеза (звірена з кодом, але не перевірена запуском): з боку C++ роботи нуль.**
`build-cms-2pass.cpp` **жодного разу не звертається до `CmProviders::openedStorage()`** — на
відміну від `sign.cpp`, який без відкритого сховища не працює. Йому потрібні лише кеш
сертифікатів і кеш CRL. Отже:

- `OPEN` / `SELECT_KEY` не потрібні взагалі — сертифікат підписувача достатньо покласти в кеш
  (`ADD_CERT` або `certCache` в `INIT`);
- метод уже доступний з 1С через наявний `ВызватьUAPKI`;
- уся оркестрація (HTTP до хмарного ЦСК, очікування підтвердження в застосунку, тайм-аути)
  лягає на бік 1С, де їй і місце.

Тобто **хмарний КЕП — це не третій провайдер, а інша вісь** (§1.1): UAPKI лишається складальником
контейнера, а джерело підпису стає зовнішнім і взаємозамінним.

### 5.3. Що тут ще не досліджено

Свідомо не досліджували, бо це вимагає доступу до конкретного хмарного сервісу:

- API конкретних хмарних ЦСК і Дія.Підпис — умови інтеграції, реєстрація, формат запиту підпису;
- чи всі вони приймають на підпис **саме геш** `signedAttributes` (а не готовий документ) — це
  визначальна умова сумісності з 2PASS;
- відповідність алгоритму гешу очікуванням сервісу;
- UX очікування: підпис у хмарі асинхронний (підтвердження в застосунку), а наш фасад
  UAPKI сьогодні синхронний.

Ці питання — вхід у майбутній план, а не в цей документ.

## 6. Архітектурні розвилки, які треба вирішити перед реалізацією

### 6.1. Модель постачання `cm-pkcs11`

У релізі v2.0.16 є **офіційний підписаний бінарник**: `cm-pkcs11.dll` (319 576 байт, x64),
Authenticode-підпис валідний, підписувач — `S.I.T TOV` (Спецінформсистеми). Експортує рівно ті
9 CM-символів. Але `dumpbin /DEPENDENTS` показує залежності від **`uapkif.dll` і `uapkic.dll`** —
це shared-збірка, не самодостатня.

| Варіант | За | Проти |
|---|---|---|
| **A1. Власна самодостатня збірка** `cm-pkcs11_x64/_x86.dll` зі статичними `uapkic`/`uapkif` усередині, RCDATA-ресурс | Повна узгодженість із наявною архітектурою; арх-суфікс; жодних зайвих DLL у процесі 1С; ми контролюємо збірку | Бінарник непідписаний (антивіруси, політики клієнтів); ми беремо на себе супровід збірки |
| **A2. Офіційний підписаний бінарник** + `uapkic.dll` + `uapkif.dll` поруч | Валідний підпис виробника; нуль роботи зі збіркою | Ламає самодостатність; **дві копії крипто-ядра в одному процесі** `1cv8.exe` (статичне наше + їхні DLL) — рівно те, від чого застерігав автор бібліотеки; імена без арх-суфікса → колізія x86/x64 у плоскому ZIP; 1С усе одно не розпакує зайві DLL із ZIP |
| **A3. Гібрид** — A1 зараз, а питання підпису винести окремо (запитати в upstream самодостатній підписаний варіант або підписувати самим) | Не блокує роботу; лишає шлях до підписаного бінарника | Рішення відкладене, а не прийняте |

**Схиляюсь до A1 як бази з A3 як подальшим кроком.** A2 виглядає привабливо через підпис, але
дві копії ядра в адресному просторі 1С — це клас проблем, який ми вже свідомо уникали.
Остаточне рішення — на етапі планування.

### 6.2. Де живе оркестрація 2PASS

| Варіант | За | Проти |
|---|---|---|
| **B1. Цілком на боці 1С** — компонента лишається незмінною, 1С сама робить обидва проходи і HTTP-виклик до хмари | Нуль C++-ризику; максимальна гнучкість під різні хмарні сервіси; узгоджено з принципом «одна точка входу» | Складність (ретраї, тайм-аути, асинхронність) лягає на прикладного розробника; повторюється в кожній конфігурації |
| **B2. Метод компоненти**, що інкапсулює обидва проходи + HTTP | Простий виклик для 1С | Ми вшиваємо в C++ протокол конкретного хмарного сервісу, якого ще не знаємо; суперечить «драйвер-незалежності» ядра |

**Схиляюсь до B1**, принаймні доки не буде хоча б двох реальних хмарних інтеграцій, з яких видно
спільну частину. Передчасне узагальнення тут коштує дорого.

## 7. Межі обсягу (YAGNI)

Свідомо **поза** цим наміром:

- реалізація підтримки конкретного хмарного ЦСК або Дія.Підпис — окремий проєкт після §5.3;
- асинхронний фасад UAPKI (наразі `AddinUAPKIConnect` синхронний; хмарні сценарії можуть цього
  зажадати — але тільки коли з'явиться конкретний сценарій);
- генерація ключів і випуск сертифікатів із 1С (`CREATE_KEY` + `GET_CSR` на носії) — можливість
  є, потреби поки немає;
- підтримка PKCS#11 на не-Windows платформах;
- будь-яка робота з `cm-almaz1c`, доки не з'ясовано §4.

## 8. Відкриті питання і тригери повернення

### 8.1. Питання, без відповідей на які план писати не варто

1. **Який носій реально у клієнтів?** Від відповіді залежить, чи достатньо `cm-pkcs11`, чи
   впирається все в прогалину ІІТ (§4).
2. **Який сценарій — робоче місце касира з токеном чи серверний підпис через HSM?** Це різні
   пріоритети: у першому критичні вибір носія й робота з PIN, у другому — батч і продуктивність.
3. **Чи буде доступ до фізичного носія для тестування?** Без нього напрям A закінчиться на «на
   SoftHSM працює», що не є рівнем готовності, прийнятним для цього проєкту (§3.7).
4. **Чи потрібен підписаний бінарник провайдера** у клієнтських середовищах (§6.1).

### 8.2. Тригери повернення до теми

Повертаємось до цього документа й пишемо план, коли настане хоча б одне:

- з'явився клієнт із апаратним носієм і конкретною вимогою;
- з'явився доступ до фізичного токена для тестування;
- вийшов наступний реліз UAPKI, де `cm-pkcs11` вже обкатаний (варто дивитись changelog на
  предмет фіксів у токенних сценаріях — у v2.0.16 такі ще були);
- з'явилась потреба в хмарному КЕП — тоді входимо через §5, а не через §3, і це значно дешевше.
