## 1. Навіщо

Розширення 1С `SMP_SimplyConnect_SMBru` переводить ПРРО на нашу компоненту `AddinUAPKIConnect`.
На рев'ю їхньої гілки знайдено дефект, якого юніт-тести не ловлять за побудовою: форма операції
робила `VERIFY` над JSON-відповіддю `/fs/cmd`, а ДПС на команди відповідає звичайним JSON (виправлено
у них комітом `5135885ac`). Клас «стик модулів і протоколу» ловиться лише наскрізним прогоном —
а на бойовий ДПС наскрізні тести ганяти не можна.

Звідси потреба: **імітація фіскального сервера ДПС зі станом**, у форматі відповідей ДПС і з
керованими збоями. Найцінніші для споживача — два штатні режими обриву (після реєстрації й до
реєстрації): на них перевіряється журнал невідправлених номерів ПРРО. Це не побічна опція.

### 1.1. Чому окремий exe, а не розширення `uapki_fiscal_emulator`

`uapki_fiscal_emulator` — крипто-оракул тестової обробки 1С (`/doc`, `/verify`, `/reference`; відмова
= `422` + підписана квитанція). Його семантика задокументована (`docs/integration-1c/uapki.md` §9.1)
і використовується. Імітація ДПС має **протилежний** контракт відмови (`400` + текст) — два
контракти в одному процесі читались би як один. Логіку стану до того ж треба перевіряти без HTTP і
без крипто, у гейті. Тому: окремий exe + спільні модулі (підхід 1 з трьох розглянутих). Відкинуто:
«розширити на місці» — файл на 1115 рядків подвоюється, стан не тестується окремо; «новий exe з
копією крипто-коду» — критерій `VERIFY` жив би у двох копіях. Цей критерій щойно пережив дефект
документації (плоска розкладка замість вкладеної; виправлено в `docs/integration-1c/uapki.md` §4.5
комітом `3ed88da`) — друга копія коду стала б наступним місцем такого розходження.

## 3. Архітектура

| Одиниця | Файл | Що робить | Від чого залежить |
|---|---|---|---|
| `FiscalServerState` | `tests/support/FiscalServerState.{h,cpp}` | стан ПРРО, змін, нумерації, збережених документів, підсумки змін; рішення «прийняти / відхилити з кодом» | лише STL + pugixml; **без HTTP і крипто** |
| `FaultPlan` | `tests/support/FaultPlan.{h,cpp}` | одноразові збої з фільтром цілі, постійні налаштування | лише STL |
| `UapkiOracle` | `tests/support/UapkiOracle.{h,cpp}` | крипто: `Init`, `Verify` (з розгортанням вмісту), `Sign` | `uapki_bundle` (статичне ядро UAPKI) |
| `MiniHttpServer` | `tests/support/MiniHttpServer.{h,cpp}` (наявний) | HTTP/1.1 на loopback + нові диспозиції відповіді (§7) | Winsock |
| `prro_fs_emulator` | `tests/prro_fs_emulator.cpp` | маршрути, JSON/XML-форматування, CLI, `--self-test` | усе вище |
| `uapki_fiscal_emulator` | `tests/uapki_fiscal_emulator.cpp` (наявний) | **без зміни поведінки**; крипто переїжджає в `UapkiOracle` | `UapkiOracle`, `MiniHttpServer` |

Потік запиту `/fs/doc`: `MiniHttpServer` → обробник → `FaultPlan` (чи є збій для цілі) →
`UapkiOracle::Verify` → розбір заголовка документа → `FiscalServerState` (рішення) → квитанція →
`UapkiOracle::Sign` → відповідь або диспозиція обриву.

Конкурентність: `MiniHttpServer` обслуговує кожне з'єднання окремим потоком. UAPKI — один глобальний
стан на процес, тож `UapkiOracle` серіалізує `process()` власним м'ютексом (як зараз `g_uapkiMtx`,
`uapki_fiscal_emulator.cpp:232`). `FiscalServerState` і `FaultPlan` — під спільним м'ютексом
обробника: реєстрація документа й витрата збою атомарні відносно інших запитів.

pugixml у тестову ціль підключається так само, як у компоненті: джерелом
`extern/pugixml/src/pugixml.cpp` (`CMake/components.cmake:248`).

### 3.1. CLI

## 4. Модель стану (`FiscalServerState`)

### 4.1. Реєстрація ПРРО — явна

ПРРО з'являються лише з команди керування `reset` (§8.1): перелік фіскальних номерів, за бажанням —
стартовий `nextLocalNum` (за замовчуванням `1`). Фіскальний номер ПРРО — лише цифри (у `Objects` він
`long`, [Опис] 1057). На невідомий `CASHREGISTERNUM` у `/fs/doc` — код `1 TransactionsRegistrarAbsent`,
як у ДПС. Автореєстрації немає: вона сховала б помилку фікстури [погоджено споживачем].

### 4.2. Стан ПРРО

Поля — ті, що віддає `TransactionsRegistrarState` ([Опис] ~1135-1177):

| Поле | Зміст |
|---|---|
| `ShiftState` | `0` закрита / `1` відкрита; після `reset` — `0` |
| `ShiftId` | ідентифікатор поточної/останньої зміни (окремий лічильник сервера) |
| `OpenShiftFiscalNum` | фіскальний номер документа відкриття |
| `ZRepPresent` | у поточній/останній зміні зареєстровано Z-звіт |
| `Testing` | `TESTING` документа відкриття |
| `Name` | `CASHIER` документа відкриття; нема — стала `Тестовий касир` |
| `FirstLocalNum` | локальний номер документа відкриття (`0` — зміну не відкрито) |
| `NextLocalNum` | очікуваний наступний локальний номер |
| `LastFiscalNum` | останній фіскальний номер у відкритій зміні (`null` — не відкрито) |

Для `Shifts` зберігається історія змін: `ShiftId`, `Opened`/`Closed` (час сервера), `OpenName`,
`CloseName`, `OpenShiftFiscalNum`, `CloseShiftFiscalNum`, `ZRepFiscalNum`, `Testing`.

### 4.3. Нумерація

- **Локальна** — на кожен ПРРО, наскрізна незалежно від класу документа (чек, Z-звіт) [Опис] ~165-173.
- **Фіскальна** — один лічильник на сервер, наскрізний незалежно від ПРРО й класу [Опис] ~175-179.
  Стартове значення — стала `100000001` [припущення: формат реального номера для споживача
  неважливий, він читає `ORDERTAXNUM` як рядок]. Кожен **прийнятий** документ (чек, Z-звіт,
  службові `DOCTYPE 100`/`101`) отримує наступний фіскальний номер.
- **Номер займає лише прийнятий документ.** Відхилений нічого не просуває.

### 4.4. Рішення по `/fs/doc` — порядок перевірок

1. невідомий ПРРО → `1 TransactionsRegistrarAbsent`;
2. `ORDERNUM ≠ NextLocalNum` → `7 CheckLocalNumberInvalid`, текст містить
   `Номер документа повинен дорівнювати N`, **число N — останнє в тексті** [споживач: їхній парсер
   бере число одразу після фрази; фрази в Описі немає — практика споживача];
3. `DOCTYPE 100` (відкриття) при відкритій зміні → `4 ShiftAlreadyOpened`;
4. будь-який інший документ при закритій зміні → `5 ShiftNotOpened`;
5. `DOCTYPE 101` (закриття) без Z-звіту в зміні → `6 LastDocumentMustBeZRep`;
   `ZREP` при вже зареєстрованому в цій зміні → `8 ZRepAlreadyRegistered`.

**Порядок 2 ↔ 3/4 — [припущення]**: Опис його не задає, виміру протилежного в споживача немає; номер
перевіряється раніше за стан, бо від цього залежить їхній сценарій 5 [погоджено споживачем як
припущення імітації].

Коди — з переліку [Опис] ~755-875 (у скілі `prro-fiscal` §3 той самий перелік).

### 4.5. Реєстрація — що змінюється

| Документ | Ефект |
|---|---|
| `CHECK`, `DOCTYPE 100` | `ShiftState=1`, новий `ShiftId`, `FirstLocalNum`, `OpenShiftFiscalNum`, `Testing`, `Name`, `Opened`; підсумки зміни обнуляються; `ZRepPresent=false` |
| `CHECK`, `DOCTYPE 0` | додається до підсумків (§4.7) |
| `ZREP` | `ZRepPresent=true`, `ZRepFiscalNum` |
| `CHECK`, `DOCTYPE 101` | `ShiftState=0`, `Closed`, `CloseName`, `CloseShiftFiscalNum` |

Після кожного прийнятого: `NextLocalNum++`, `LastFiscalNum` = виданий, документ зберігається (§4.6).
`CHECK` з `DOCTYPE 1..3`, `102`, `103` приймаються за нумерацією й станом, але в підсумки не
потрапляють (§12).

### 4.6. Збережені документи

Ключі: (ПРРО, локальний номер) і фіскальний номер. Зберігаються: клас (`CHECK`/`ZREP`),
`DOCTYPE`/`DOCSUBTYPE`, **побайтовий оригінал XML** (розгорнутий із CMS), фіскальний номер,
`ShiftId`, час реєстрації. Цього досить для `CheckExt`/`ZRepExt` (§6.6).

### 4.7. Підсумки зміни (`LastShiftTotals.Totals`)

Споживач **будує з них Z-звіт** [споживач: `СМП_ДокументыПРРОСервер` `ОсноваZОтчета :997`,
`ЗаписатьИтогиZОтчетаПоНаправлению :1152`], тож рахуються чесно з вмісту прийнятих чеків.

| `DOCSUBTYPE` чека `DOCTYPE 0` | Куди |
|---|---|
| `0` CheckGoods | `Real` |
| `1` CheckReturn | `Ret` |
| `2` ServiceDeposit, `3` AdditionalDeposit | `ServiceInput += CHECKTOTAL/SUM` |
| `4` ServiceIssue | `ServiceOutput += CHECKTOTAL/SUM` |
| `5` CheckStorno | **не враховується** — названа межа (§12) |

Для `Real`/`Ret`: `Sum += CHECKTOTAL/SUM`, `OrdersCount++`, `RndSum`/`NoRndSum` з `CHECKTOTAL`, якщо є;
`PayForm[]` — агрегація `CHECKPAY/ROW` за `PAYFORMCD` (`PayFormCode`; `PayFormName` з першого рядка;
`Sum`); `Tax[]` — агрегація `CHECKTAX/ROW` за ключем (`TYPE`, `LETTER`, `PRC`, `SIGN`): `Name` з
першого рядка, суми `TURNOVER`, `TURNOVERDISCOUNT`, `SOURCESUM`, `SUM`.

- `SIGN` і `TURNOVERDISCOUNT` у зразках ДПС відсутні: `check01(Два податки).xml` і
  `check01(Засоби оплат).xml` мають у `CHECKTAX` лише `TYPE/NAME/LETTER/PRC/SOURCESUM/SUM/TURNOVER`.
  **[припущення]:** відсутній `SIGN` = `false`; відсутній `TURNOVERDISCOUNT` = значення `TURNOVER` того
  ж рядка. `TurnoverDiscount` у відповіді — **завжди** [споживач: читається прямо; в Описі ~1703].
- Гроші — цілими копійками (`int64`), не `double`; у JSON — число з двома знаками після крапки.
- Кирилиця (`PAYFORMNM`, `NAME`) перекодовується з кодування, оголошеного в XML-декларації (ДПС
  вимагає `windows-1251`), у UTF-8 для JSON.

**Форма `Totals` — завжди повна** [споживач: `СМП_ПечатьПРРО` `ManagerModule.bsl :264-355` звертається
до `Real`, `Ret`, `ServiceInput`, `ServiceOutput` прямо; усередині `Real`/`Ret` — до `Sum`,
`OrdersCount` прямо; `PayForm`, `Tax` порівнюються з `Неопределено`]: `Real` і `Ret` — завжди об'єкти
(нулі, якщо чеків не було); `PayForm`/`Tax` — завжди масиви (можуть бути порожні);
`ServiceInput`/`ServiceOutput` — числа. `Pwn*`, `TotalCurrency*` — нулі; `Cash`, `Currency` — `null`
[споживач: не читаються].

## 5. Загальні правила відповіді

- **`Date`** — у **кожній** відповіді, включно з відмовами й власними відповідями транспорту
  (`411`/`413` з `MiniHttpServer`), формат RFC 1123 за Гринвічем, час = годинник сервера (§8.3)
  [споживач: вимір на бойовому ДПС; в Описі немає].
- **Розмір тіла поза 10…512000 байтів** на `/fs/doc` і `/fs/cmd` → `416` [споживач: вимір порожнім
  POST на бойовому ДПС; Опис ~879-901 визначає `416` як «Недопустимий розмір повідомлення»]. Рішення
  ухвалює обробник: стеля самого транспорту — 8 МіБ (`MiniHttpServer.cpp:24`), вище неї лишається
  `413` транспорту.
- **Відмова** (основний режим) → `400`, тіло `text/plain; charset=utf-8`:
  `Код помилки: <n> <СимвольнийКод>\r\n<опис>` [Опис ~899-901]. Альтернативний керований формат —
  §8.3.
- **`GET /ping`** — від кореня хоста (не з-під `/fs`), тіло **`prro_fs_emulator alive`**. Детектор
  споживача перевіряє саме тіло [погоджено споживачем]: на тому ж порту `8099` може відповідати й
  старий `uapki_fiscal_emulator`, і без перевірки тіла тести вирішили б «оракул є» й падали б на
  `/fs/doc` з `404` замість іменованого SKIP.
- Невідомий шлях → `404`. (Опис ~879-901 для некоректного URL дає `403`; продукт на цю різницю не
  калібрується — названо в §13.)
- **Годинник сервера** = системний час машини + `dateSkewSeconds` (§8.3). `Date` — за Гринвічем;
  `Timestamp`, `Opened`, `Closed` — ISO 8601 з місцевим зсувом (як приклад в Описі
  `"2018-10-17T01:23:00+03:00"`); `ORDERDATE`/`ORDERTIME` квитанції — місцевий час.
- **Типи вмісту:** CMS (квитанції) — `application/octet-stream`; JSON (`/fs/cmd`, `/control`) —
  `application/json; charset=utf-8`; текст відмови — `text/plain; charset=utf-8`.

## 6. Ендпоінти ДПС

### 6.1. `POST /fs/doc`

1. Розмір (§5).
2. `UapkiOracle::Verify` (STRUCT, §9). Тіло не CMS або критерій не виконано → `9
   DocumentValidationError` [припущення: Опис і скіл `prro-fiscal` §3 відносять до коду 9 і
   структурні порушення підпису].
3. Розбір заголовка через pugixml: корінь `CHECK` (заголовок `CHECKHEAD`) або `ZREP` (`ZREPHEAD`);
   поля `UID`, `DOCTYPE`, `DOCSUBTYPE`, `ORDERNUM`, `CASHREGISTERNUM`, `CASHIER`, `TESTING`. Не
   розбирається → `9`.
4. Рішення `FiscalServerState` (§4.4).
5. Прийнято → `200`, `application/octet-stream`, тіло = CMS квитанції (§6.2).

### 6.2. Квитанція

XML у `windows-1251` за зразком `Приклади/Приклади/ticket01.xml`: `UID` (документа), `ORDERDATE`
(`ddmmyyyy`) і `ORDERTIME` (`hhmmss`) — годинник сервера, `ORDERNUM`, `ORDERTAXNUM`,
`OFFLINESESSIONID` і `OFFLINESEED` (сталі; у зразку позначені обов'язковими), `ERRORCODE 0`,
`ERRORTEXT` порожній, `VER 1`. Підпис — `UapkiOracle::Sign` (§9).

### 6.3. `POST /fs/cmd` — тіло

Приймаються обидва види тіла: CMS (`Verify` STRUCT → розгорнутий JSON) або звичайний JSON.

**Підпис обов'язковий** для `Objects` ([Опис] 1005), `TransactionsRegistrarState` (1109), `ZRepExt`
(1291), `Shifts` (1333), `LastShiftTotals` (1447): непідписане тіло або підпис, що не пройшов
критерій, → `400` з кодом `9 DocumentValidationError` [код — припущення; продукт підписує всі ці
команди й на код не калібрується — погоджено споживачем, їхній варіант (б)]. `ServerState` (951) і
`CheckExt` (1215) — будь-яке тіло.

Невідома команда або непідтримуваний `Type` → `400`, `11 InvalidQueryParameter`.

### 6.4. `POST /fs/cmd` — відповідь

Завжди `200` + звичайний JSON без підпису (або `204`, де вказано). Загальні поля: `UID` (з запиту)
і `Timestamp` (ISO 8601 зі зсувом, годинник сервера) [Опис ~905-935].

| Команда | Відповідь | Що читає продукт [споживач] |
|---|---|---|
| `ServerState` | `Timestamp`, `UID` | `Timestamp` — лише для тексту (`СМП_ОтветыПРРОСервер :413`) |

### 6.6. `CheckExt` / `ZRepExt`

| `Type` [Опис ~633-689] | `Data` (base64) |

## 7. Розширення `MiniHttpServer`

Сумісні з наявним користувачем (`uapki_fiscal_emulator`): за замовчуванням поведінка не змінюється.

1. **Додаткові заголовки відповіді**: `Response::headers` (перелік пар) — для `Location` (`302`) тощо.
2. **Спільні заголовки для кожної відповіді**: `Server::SetCommonHeaders(std::function<...>)` —
   викликається і для відповідей обробника, і для власних `411`/`413` транспорту
   (`MiniHttpServer.cpp:230-244`). Так `Date` потрапляє в **кожну** відповідь (§5).
3. **Диспозиція відповіді** `Response::disposition`: `Send` (дефолт) | `Abort` (закрити без відповіді:
   `SO_LINGER {1,0}` + `closesocket` → RST, як у мережевому збої) | `HoldThenAbort` (`holdSeconds`
   тиші, потім RST). Утримання — очікування на умовній змінній, яку будить `Stop()`: зупинка сервера
   не чекає `holdSeconds`.

`Connection: close` і модель «потік на з'єднання» (`MiniHttpServer.cpp:160`) лишаються.

## 8. Керування й збої

Усе керування — **від кореня, поза `/fs`**: це не поверхня ДПС, продукт туди не ходить. Тіло — JSON;
відповіді — JSON: `200 {"ok":true}`, `400 {"ok":false,"error":"…"}`, `409` (§8.2).

### 8.1. Скидання й стан

- `POST /control` `{"action":"reset","registrars":[{"numFiscal":"4000000001","nextLocalNum":1}]}` —
  очищає стан, історію змін, документи, **усі** взведені збої й постійні налаштування; реєструє ПРРО.
- `GET /control/state` — JSON: стан кожного ПРРО (§4.2), збережені документи (без тіла: ключі, клас,
  тип, фіскальний номер), взведені збої, постійні налаштування. Для тестів це **доказ стану** на боці
  оракула: обриви до й після реєстрації ззовні нерозрізненні.

### 8.2. Одноразовий збій

`POST /control` `{"action":"fault","target":"doc"|"cmd"|"cmd:<Команда>","mode":"…", …}`.

- Спрацьовує на **наступному запиті, що відповідає `target`**, і витрачається. Фільтр цілі
  обов'язковий: продукт перед `/fs/doc` ходить на `/fs/cmd`, і збій «на наступний будь-який запит»
  з'їла б команда. `cmd:<Команда>` має перевагу над `cmd`; на один запит витрачається **рівно один**
  збій — якщо взведено обидва, `cmd` лишається на наступний запит.
- Щоб зіставити запит із ціллю `cmd:<Команда>`, ім'я команди береться з тіла — для підписаного тіла
  після розгортання CMS. Тому «до реєстрації» нижче означає «**стан не змінено**», а не «тіло не
  розбиралось». Для цілей `doc` і `cmd` тіло до спрацювання збою не розбирається.
- Взведення при вже взведеному збої для **тієї самої** цілі → `409`. Черги немає: тихий перезапис
  ламав би тести непомітно.

| `mode` | Поведінка | Де в обробці |
|---|---|---|
| `delay` `{seconds}` | пауза, потім звичайна обробка | до всього |
| `status` `{code, body?, location?}` | одразу відповідь із кодом (204/5xx/302/…), без обробки й реєстрації; для `302` `Location` за замовчуванням `http://127.0.0.1:<port>/moved` | до всього |
| `dropBeforeRegister` `{holdSeconds?}` | тіло прочитано, **стан не змінено** (номер не зайнято, документ не збережено), обрив | після читання тіла (для `cmd:<Команда>` — після розгортання) |
| `dropAfterRegister` `{holdSeconds?}` | документ **повністю** зареєстровано (номер зайнято, фіскальний номер видано, документ збережено для `CheckExt`), квитанцію сформовано й **не відправлено**, обрив; для `cmd`-цілі — команду виконано, відповідь не відправлено | після рішення стану |

Обрив — диспозиція `Abort`; з `holdSeconds` — `HoldThenAbort` («мовчати довше за таймаут»: для
`/fs/doc` продукту — більше 60 с, `/fs/cmd` — 20 с [споживач, §3.3 їхньої спеки]).

### 8.3. Постійні налаштування

`POST /control` `{"action":"set", …}`, діють до наступного `reset`:

- `dateSkewSeconds` — **зсув годинника сервера**: `Date`, `Timestamp`, `ORDERDATE`/`ORDERTIME`,
  `Opened`/`Closed`. Постійний, а не одноразовий: попередження в продукті має виникати незалежно від
  того, з якого запиту операції він бере `Date`; одноразовий прив'язав би тест до порядку запитів.
- `rejectFormat`: `"text"` (дефолт: `400` + текст, §5) | `"ticket"` (`200` + CMS квитанції з
  `ERRORCODE <n>`, `ERRORTEXT <опис>`, без `ORDERTAXNUM`). Опис допускає обидва формати відмови
  (~189-199 проти ~879-901), бойовий не виміряно; вимір внесено в чек-лист рівня 4 споживача (їхній
  `docs/prro-uapki-runtime-checklist.md` §3.11) [споживач].
- `resultCodeFormat`: `"name"` (дефолт, §6.6) | `"number"` — форма `ResultCode` у `CheckExt`/`ZRepExt`.
  Невідоме значення → `400`. Реалізація — один хелпер `ResultCodeJson`, яким користуються всі три
  місця, що виставляють `ResultCode` (`tests/support/PrroFsService.cpp`).
  > Змінено 2026-09-24 на прохання споживача: типова форма стала рядковою (див. примітку §6.6);
  > числова лишена перемикачем — бойовий ДПС не виміряно.

### 8.4. Сценарії споживача без окремого збою

Розбіжність лічильників (їхній сценарій 5) створюється **чесно**: `reset` з `nextLocalNum`, що
відрізняється від лічильника каси. Відповідь «повинен дорівнювати N» виникає зі стану, а не з
підробленої відповіді.

## 9. Крипто (`UapkiOracle`)

**Винесення, не переписування.** З `tests/uapki_fiscal_emulator.cpp` без зміни логіки переїжджають:
`callUapki` під м'ютексом (`:246`), writable-копія `certs/`/`crls/` у `%TEMP%` з прибиранням
(`prepareWorkDir :313`, `removeWorkDir :304`; каталог уже унікальний на процес —
`uapki_oracle_<pid>`, `:323`), bootstrap `INIT → OPEN → KEYS → SELECT_KEY` (`cryptoBootstrap :355`),
`verifyCms` (`:432`), `signData` (`:489`), base64-хелпери.

Інтерфейс: `bool Init(const OracleConfig&)`; `VerifyOutcome Verify(const std::string& der)` — з
розгорнутим вмістом; `std::string Sign(const std::string& bytes)` → DER або порожньо;
`void Shutdown()`.

**Критерій прийняття — без змін**: одночасно `errorCode==0`,
`signatureInfos[0].status=="TOTAL-VALID"`, `signatureInfos[0].validSignatures`,
`signatureInfos[0].validDigests` — **вкладені** шляхи, як у коді (`uapki_fiscal_emulator.cpp:455-479`).
Режим `STRUCT`, офлайн.

**Профіль підпису сервера — той самий, що зараз** (`signData`): CAdES-BES, enveloping,
`includeCert:true`, `includeTime:true` (лише атрибут signingTime, без TSP), `includeContentTS:false`,
`signAlgo 1.2.804.2.1.1.1.1.3.1.1`. Ним підписуються квитанції й `Data` у `CheckExt`/`ZRepExt` тип 2.
Сертифікат `test-diia.p12` прострочений, тож у 1С перевірка — STRUCT з `ignoreCertStatus` (узгоджено
зі споживачем).

**Доказ незмінності старого емулятора:** вивід `uapki_fiscal_emulator --self-test` до й після
винесення порівнюється порядково (рядки `ok:`/`FAIL:`/`skip:`), плюс ручний `POST /doc`. Будь-яка
відмінність — дефект винесення, а не «покращення».

**Одночасний запуск обох емуляторів** можливий: окремі процеси, окремі екземпляри UAPKI, окремі
`uapki_oracle_<pid>`; порт другого зсувається автоматично, `/ping` за тілом каже, хто відповідає.

## 13. Застереження для споживача (переносяться в §9.2)

- `STRUCT` не перевіряє ланцюга, строку дії сертифіката, OCSP/CRL. `TOTAL-VALID` від імітації =
  «підпис і вміст не підмінено», а **не** «ДПС прийме». Чинність сертифіката міряє арбітр ІІТ
  (`docs/architecture/uapki.md` §8.4), не імітація.
- Обробку помилок **не калібрувати** на імітації там, де вона розходиться з Описом або не виміряна:
  коди для непідписаної команди й зіпсованого підпису, `404` замість `403` на невідомий шлях, порядок
  перевірок (§4.4), формат відмови (`rejectFormat`), стала частина тексту коду 7.
- Квитанції й `Data` тип 2 підписані **простроченим** тестовим ключем — перевірка в 1С лише STRUCT з
  `ignoreCertStatus`.
- Лише `http` на `127.0.0.1`; TLS до бойового `:8643` імітація не перевіряє.
