# Шарування БПО-фасадів: спільна база, шар еквайрингу, виправлення LabelPrinter

*Дата: 2026-09-01. Статус: дизайн затверджено, імплементації ще немає.*

Контракт «Подключаемое оборудование» — `docs/architecture/bpo-contract.md`.
Драйвери — `docs/architecture/{ecrprivatjson,label_printer}.md`, прикладний бік —
`docs/integration-1c/`.

---

## 1. Дві проблеми, які розв'язуються одним рефакторингом

### 1.1. Семантика еквайрингу приварена до одного протоколу

`AddinEcrBpoBase` тримає `EcrPrivatJsonDriver` **конкретним полем**. Тобто вся семантика
еквайрингу — оплата, повернення, скасування, підсумки дня, асинхронна група — знає про
ПриватБанк. Коли з'явиться BPOS1 чи POSAPI, її довелося б копіювати цілком.

Додатково зашито те, що зашивати не можна: прапорці `PartialCancellation`, `CashWithdrawal`,
`ConsumerPresentedQR` захардкожені у фасаді як `false`. Уміння часткового скасування — це
властивість **протоколу й термінала**, а не фасаду.

**Дві ортогональні осі, і головна пастка — не помітити цього:**

| Вісь | Що визначає | Значення |
|---|---|---|
| **Ревізія** | розкладку параметрів методів БПО | 3004 (сімка), 4000 (дев'ятка/десятки) |
| **Протокол** | як говорити з терміналом | Privat JSON, далі BPOS1, POSAPI |

Якщо змішати їх в одному класі, кожен новий протокол коштує повного дубля обох ревізій.

### 1.2. LabelPrinter не підхоплюється підсистемою БПО

`LabelPrinter` задокументований як такий, що «реалізує стандартний контракт БПО». Це **не так**:
драйвер реєструє системні методи довгими іменами за документом ІТС
(`ПодключитьОборудование`, `ПараметрыОборудования`, `ТестированиеОборудования`), а конфігурація
кличе короткі (`Подключить`, `ПолучитьПараметры`, `ТестУстройства`) і додатково
`УстановитьПараметр`, якого в драйвері немає взагалі.

З десяти імен, які кличе конфігурація, збігаються **три**: `ПолучитьРевизиюИнтерфейса`,
`ПолучитьОписание`, `ПолучитьОшибку`. Наслідок: через штатну підсистему БПО драйвер не
підхоплюється — параметри підключення до нього не доходять у принципі.

Прямий друк через `ПечатьЭтикеток` на створеному вручну об'єкті цим не зачеплено й працює.

**Чому дефект не спіймали тести:** `label_native_host` кличе наші ж імена, тому завжди зелений.
Тест перевіряв, що драйвер відповідає сам собі, а не контракту.

## 2. Встановлені факти (про LabelPrinter)

Усе нижче звірено читанням коду **обох** конфігурацій (УНФ ru і BAS УНФ ua), не з документа ІТС.
Це принципово: документ ІТС відстає від бібліотеки й описує старіший контракт (див.
`bpo-contract.md` §5).

### 2.1. Функціональні методи ВЖЕ правильні

| Редакція | Виклик |
|---|---|
| ru | `ИнициализацияПринтераАсинх(ИДУстройства)` (:2906), `ПечатьЭтикетокАсинх(ИДУстройства, ДанныеДляВыгрузки, СтатусПакета)` (:2937) |
| ua | `ИнициализацияПринтера(ИДУстройства)` (:2778), `ПечатьЭтикеток(ИДУстройства, ДанныеДляВыгрузки, СтатусПакета)` (:2844) |

Імена й арності збігаються з нашою реалізацією. `СтатусПакета` набуває значень
`first` / `regular` / `last`.

### 2.2. Гілок за ревізією для друку етикеток НЕМАЄ

В околі викликів друку (рядки 2870-2960 ru-модуля) жодної згадки `РевизияИнтерфейса`.
**Наслідок для дизайну:** на відміну від еквайрингу, фасади на сімейства сигнатур тут
**не потрібні** — достатньо одного класу.

### 2.3. Методу можливостей для принтера етикеток не існує

Розгалуження за `ТипыОборудования.ПринтерЭтикеток` у драйверних модулях обох редакцій —
**жодного**. Аналога `ПараметрыТерминала` (який в еквайрингу віддає прапорці) для цього типу
обладнання немає. Тобто весь контракт = системна половина + два функціональні методи.

### 2.4. `EquipmentType` на вході — `ПринтерЭтикеток`

Ім'я значення переліку `Enums/ТипыПодключаемогоОборудования`, звірено в обох конфігураціях.
НЕ англійський рядок `LabelPrinter` з таблиці ІТС. Та сама пастка, що з
`ЭквайринговыйТерминал` (`bpo-contract.md` §4.1).

### 2.5. `УстановитьИнформациюПриложения` не кличеться ніде

Пошук по всіх `.bsl` обох конфігурацій — нуль збігів. Метод можна прибрати.

## 3. Дизайн

Три шари замість двох:

```
BpoFacadeBase              контракт БПО; тип обладнання не знає
 ├─ AcquiringFacadeBase    семантика еквайрингу поверх IAcquiringDriver; протокол не знає
 │   ├─ AcquiringBpo3004   ТІЛЬКИ розкладка сімки + ревізія 3004
 │   └─ AcquiringBpo4000   ТІЛЬКИ розкладка дев'ятки/десяток + ревізія 4000
 │        ├─ ECRPrivatBPO3004 / ECRPrivatBPO4000   ~15 рядків кожен
 │        └─ ECRCommXBPO3004  / ECRCommXBPO4000    коли з'явиться
 └─ AddinLabelPrinter      принтер етикеток
```

### 3.1. Спільна база `BpoFacadeBase`

Системна половина контракту однакова для **всіх** типів обладнання, тож її місце — не в
драйвері. Виносимо з `AddinEcrBpoBase` чисто контрактну частину у новий базовий клас;
`AddinEcrBpoBase` і `AddinLabelPrinter` стають його нащадками.

**У базі (готове, реалізації не потребує — переїжджає з `AddinEcrBpoBase`):**

- `ПолучитьРевизиюИнтерфейса` — віддає `InterfaceRevision()` нащадка;
- `ПолучитьНомерВерсии`, `ПолучитьОписание`, `ПолучитьПараметры`;
- `УстановитьПараметр` з накопиченням у мапу параметрів;
- `Подключить` (`ИДУстройства` в OUT) / `Отключить` / `ТестУстройства`;
- `ПолучитьОшибку` + числова таксономія `CodeToInt`;
- `ПолучитьДополнительныеДействия` / `ВыполнитьДополнительноеДействие`;
- толерантні `VariantToString` / `VariantToDouble`.

**Віртуальні гачки для нащадка:**

| Гачок | Призначення |
|---|---|
| `InterfaceRevision()` | число ревізії |
| `BuildDriverDescription()` | XML паспорта: `EquipmentType`, прапорці, лог |
| `BuildSettingsXml()` | XML форми налаштувань (`Settings/Page/Group/Parameter`) |
| `BuildActionsXml()` | XML додаткових дій (порожній набір допустимий) |
| `AcceptEquipmentType(v)` | толерантна перевірка типу обладнання |
| `OpenDevice()` / `CloseDevice()` | фактичне підключення з накопичених параметрів |
| `ProbeDevice(out)` | тіло `ТестУстройства` |
| `RunAction(name)` | виконання додаткової дії |

**Що НЕ переїжджає в базу** — усе, що специфічне для типу обладнання: методи можливостей,
платіжні операції, асинхронне розширення. Їхнє місце — §3.2.

**Ризик і чим покритий:** рефакторинг чіпає щойно зроблений і робочий еквайринг. Покритий
54 перевірками `ecr_native_host` — вони мають лишитись зеленими **без правок у тесті**, і це
критерій успіху. Знадобилось правити тест — значить зламано зовнішню поведінку.

### 3.2. Шар еквайрингу: `AcquiringFacadeBase` + `IAcquiringDriver`

**`AcquiringFacadeBase`** тримає семантику еквайрингу й **не знає протоколу**: працює виключно
через `IAcquiringDriver&`. У ньому — `ПараметрыТерминала` (рендерить можливості, які задекларував
драйвер) і `ПечатьКвитанцийНаТерминале`, `ИтогиДняПоКартам`, `АварийнаяОтменаОперации`,
асинхронне розширення (`НачатьОплату`/`НачатьВозврат`/`СостояниеОперации`/
`РезультатОперацииJSON`/`СтатусТерминала`/`ПрерватьОперацию`), логіка `VoidAsRefund` і спільні
хелпери заповнення OUT-полів із `ResultEnvelope`.

**`IAcquiringDriver`** — межа, за якою ховається протокол:

| Група | Склад |
|---|---|
| З'єднання | `Open(параметри)`, `Close()`, `IsConnected()` |
| Операції | `Purchase(сума)`, `Refund(сума, rrn)`, `Void(сума, rrn)`, `DayTotals()`, `Audit()`, `EmergencyVoid()` — усі → `ResultEnvelope` |
| Асинхронні | `StartPurchase`, `StartRefund`, `OperationState`, `TryGetOperationResult`, `LastStatus`, `CancelOperation` |
| Ідентичність | `Vendor()`, `Model()`, `Probe()` для `ТестУстройства` |
| Опис | `SettingsXml()` — форма налаштувань цього протоколу |
| **Можливості** | `Capabilities()` — що термінал реально вміє |

Операції, яких протокол не має, за замовчуванням віддають `UNSUPPORTED` — чесна відмова
лишається поведінкою за замовчуванням, а не обов'язком кожного драйвера.

**`Capabilities()` прибирає зашитість.** Замість захардкожених `false` у фасаді драйвер
декларує: часткове скасування, видача готівки, QR, електронні сертифікати, список операцій,
друк сліпа на терміналі. Фасад із цього рендерить `ПараметрыТерминала` і вирішує, де відмовляти.
Термінал, що вміє часткове скасування, вмикає його **одним рядком у своєму драйвері**.

`SettingsXml()` теж у драйвера: в BPOS1 набір параметрів підключення буде свій, і фасад не має
про це знати.

**Ревізійні шари** (`AcquiringBpo3004`, `AcquiringBpo4000`) містять **рівно** розкладку
параметрів платіжних методів і число ревізії. Жодної семантики.

**Конкретний фасад** перевизначає лише `MakeDriver()` і реєструється макросом
`REGISTER_COMPONENT`. Композиція через віртуальні методи, не шаблони — це відповідає стилю
репозиторію й читається без напруги.

**Ціна нового протоколу:** реалізувати `IAcquiringDriver` + два класи по ~15 рядків. Ні
контракт, ні семантика не дублюються.

> **Чесне застереження.** `IAcquiringDriver` проєктується на ОДНОМУ відомому протоколі, тож
> ризик, що для BPOS1 інтерфейс виявиться не зовсім тим, реальний. Приймаємо свідомо й не
> вгадуємо наперед: коли з'явиться друга реалізація, інтерфейс уточниться за фактом — саме тоді
> буде видно справжні спільні місця. Це дешевше, ніж закладати абстракції під неіснуючі вимоги.

### 3.3. Зміни в `AddinLabelPrinter`

**Перейменування** (стара назва → нова):

| Було | Стало |
|---|---|
| `ПодключитьОборудование(DeviceID[OUT], EquipmentType, ConnectionParameters)` | `Подключить(ИДУстройства[OUT])` — параметри вже накопичені |
| `ОтключитьОборудование(DeviceID)` | `Отключить(ИДУстройства)` |
| `ПараметрыОборудования(EquipmentType, TableParameters[OUT])` | `ПолучитьПараметры(ПараметрыДрайвера[OUT])` |
| `ТестированиеОборудования(EquipmentType, ConnectionParameters, Description[OUT], Demo[OUT])` | `ТестУстройства(РезультатТеста[OUT], АктивированДемоРежим[OUT])` |

**Додається:** `УстановитьПараметр`, `ПолучитьНомерВерсии`,
`ПолучитьДополнительныеДействия`, `ВыполнитьДополнительноеДействие`.

**Прибирається:** старі довгі імена і `УстановитьИнформациюПриложения` (§2.5).

⚠️ **Споживач у старих імен ВСЕ-ТАКИ Є — наша власна тестова обробка.**
`ExtDataProcessors/.../Форма/Ext/Form/Module.bsl`, область `ПринтерЭтикеток`: `ПодключитьОборудование`
(:1258) і `ОтключитьОборудование` (:1318). Її треба переписати під новий контракт разом із кодом.

**І це окремий клас ризику, який варто знати:** 1С **не перевіряє імена методів нативної
компоненти на етапі компіляції**. Ні збірка `.epf`, ні `/CheckModules -ExtendedModulesCheck` цього
не спіймають — обробка збереться зеленою, а кнопка мовчки впаде під час виконання. Тобто BSL-код,
що кличе компоненту, під статичним контролем **не стоїть узагалі**, і кожне перейменування методу
треба вручну відстежувати по всіх викликах.

**Не змінюється:** `ИнициализацияПринтера`, `ПечатьЭтикеток` (§2.1), увесь ZPL-стек —
генератор, растр, штрихкоди, `LabelXml`.

**Реєстр пристроїв згортається до одного.** Контракт накопичує параметри на об'єкті **до**
`Подключить`, тож один об'єкт фізично не може обслуговувати два принтери: параметри другого
затерли б перший. Мапа `DeviceID → канал` замінюється єдиним каналом, як в еквайринговому
фасаді.

**Ім'я класу лишається `LabelPrinter`** — запис довідника драйверів у розширенні вже
розрахований на нього.

### 3.4. Ревізія LabelPrinter — `3004`

Гейтів, специфічних для принтера, немає (§2.2), тож число майже вільне. `3004` обрано, бо:

- збігається з базовим фасадом еквайрингу — одне число на обидва драйвери;
- нижче за `4000`, з якого 1С починає кликати `УстановитьЛокализацию`. Ми його не реалізуємо,
  виняток конфігурація мовчки ковтає — зайвий шум без користі.

`LocalizationSupported` у паспорті лишається `false`.

### 3.4б. `ТестУстройства` для LabelPrinter — реально відкрити транспорт

Зараз `ТестированиеОборудования` у принтера **нічого не перевіряє фізично**: розбирає XML
параметрів і каже «коректні». Для адміністратора, який тисне «Тест устройства» у формі
налаштувань, це безкорисно — неправильні IP чи ім'я черги він побачить лише при першому друку.

Складність у тому, що `LabelPrinterDriver::Connect(profile)` транспорт **не відкриває** — Open
лінива, при першому `Send`. Тобто саме підключення нічого не доводить.

**Рішення:** `ProbeDevice` фактично відкриває транспорт і одразу закриває. TCP — конект на
`host:port`; spooler — `OpenPrinter` на черзі. Доводить досяжність і **нічого не друкує**.
Потребує нового публічного методу драйвера (`ResultEnvelope Probe(deviceId)`), який форсує
відкриття й закриття.

Свідомо **не** шлемо ініт-пакет: він міняє стан принтера (темність, швидкість, розмір), а
адміністратор, який тисне «тест», на переналаштування обладнання не підписувався.

`АктивированДемоРежим` — завжди `Ложь`: демо-режиму драйвер не має.

### 3.5. Додаткові дії LabelPrinter

Для принтера — порожній набір `<Actions/>`. Кандидат на майбутнє (не в цьому обсязі):
друк тестової етикетки з форми налаштувань.

## 4. Тестування

`label_native_host` переводиться на новий контракт за зразком `ecr_native_host`:

- ревізія віддається рівно `3004`;
- `УстановитьПараметр(EquipmentType, "ПринтерЭтикеток")` приймається, чужий тип відхиляється;
- **числове значення параметра** (`Port`, `DotsPerMm`) приймається — саме на цьому горів
  еквайринговий фасад: `Number`-параметр приходить не рядком, і пряме приведення кидає;
- `Подключить` повертає `ИДУстройства` в OUT;
- `ИнициализацияПринтера` + `ПечатьЭтикеток` проти `LabelEmulator` друкують очікуваний ZPL;
- `ПолучитьОшибку` після навмисної помилки дає код і опис.

Смоук БПО-фасаду в `label_printer_selftest` оновлюється під нові імена.

**Критерій успіху рефакторингу:** `ecr_native_host` лишається зеленим **без правок**.

## 5. Що лишається неперевіреним

**Еквайрингові фасади теж ще не бачили живої 1С.** `ECRPrivatBPO3004` і `ECRPrivatBPO4000`
покриті 54 перевірками через реальний ABI проти емулятора, але через **штатну підсистему БПО**
не запускались жодного разу: на боці розширення тривало рев'ю, і `ТестУстройства` на дев-базі
ще попереду. Тобто рефакторинг §3.1-3.3 стоїть на тесті, а не на живому підтвердженні — це
прийнятно (тест ганяє той самий ABI), але знати про це треба.


**Живий прогін через штатну підсистему БПО на реальному принтері.** Усе в §2 звірено по коду
обох конфігурацій, але сам факт, що драйвер підхоплюється формою налаштувань, приймає параметри
й друкує, не спостерігався жодного разу — ні до виправлення, ні (поки) після.

Перевіряється так само, як планувався еквайринг: запис довідника драйверів з
`ИдентификаторОбъекта = "LabelPrinter"` і тим самим макетом `СМП_КомпонентаSimplyAddinConnect`
(бандл спільний на всі класи компоненти), далі форма налаштувань обладнання → «Тест устройства»
→ друк.

## 6. Порядок робіт

Кожен крок закінчується зеленим гейтом — інакше наступний не починається.

1. **Виділити `BpoFacadeBase`** з `AddinEcrBpoBase`, лишивши еквайринг працездатним.
   `ecr_native_host` (54 перевірки) має пройти **без правок у тесті**.
2. **Виділити `IAcquiringDriver`** і адаптер над `EcrPrivatJsonDriver`; перевести семантику
   в `AcquiringFacadeBase`. Прапорці можливостей переїжджають із фасаду в драйвер
   (`Capabilities()`), а `ПараметрыТерминала` починає рендерити їх, а не константи.
   Знову `ecr_native_host` без правок.
3. **Розділити ревізійні шари** `AcquiringBpo3004`/`AcquiringBpo4000`; `ECRPrivatBPO3004`/
   `ECRPrivatBPO4000` стають тонкими класами з `MakeDriver()`.
4. **Перевести `AddinLabelPrinter`** на `BpoFacadeBase`: короткі імена, `УстановитьПараметр`,
   згортання реєстру пристроїв до одного.
5. **Оновити тести:** `label_native_host` на новий контракт, смоук у `label_printer_selftest`.
5-біс. **Переписати область `ПринтерЭтикеток` у тестовій обробці** під новий контракт
   (`УстановитьПараметр` × N → `Подключить`), поля форми лишаються джерелом значень; додати
   кнопку «Тест устройства». Пропустити цей крок не можна: статичний контроль BSL виклики
   компоненти не перевіряє (див. §3.3), тож зламане виявиться лише руками в 1С.
6. **Оновити документацію:** `docs/architecture/bpo-contract.md` (шарування фасадів),
   `label_printer.md` в обох теках — зняти дефект-нотіс.
7. **Свіжий ZIP** → компаньйон додає запис довідника → живий прогін на реальному принтері.

Кроки 1-3 не змінюють зовнішньої поведінки жодного класу — це чистий рефакторинг під
незмінним тестом. Кроки 4-5 змінюють контракт LabelPrinter, і саме там тест оновлюється.
