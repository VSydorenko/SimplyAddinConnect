# Еталонні підписи ЦЗО (тестові приклади КЕП)

**Це вхідні тестові дані, а НЕ артефакти тестового прогону. Не видаляти.**

> ⚠️ Ця теку вже одного разу описали як «порожнє дерево каталогів, створене харнесом під час
> прогону» — і мало не прибрали як сміття. Файлів тут 16, усі потрібні.

Офіційні тестові приклади кваліфікованого електронного підпису з
[czo.gov.ua/testexamples](https://czo.gov.ua/testexamples) (Центральний засвідчувальний орган),
опубліковані на виконання наказу Мінцифри від 28.12.2023 № Н 191. Завантажено 2026-09-01.

## Навіщо

Це **єдиний доступний у репозиторії матеріал із підписом за новим алгоритмом**
(ДСТУ 4145 + Купина ДСТУ 7564). До нього гілка `VERIFY` для купинних підписів не перевірялась
ніколи. Еталони ДПС у `prro_docs` для цього непридатні — вони старої схеми (ГОСТ 34311),
перевірено читанням OID.

**Обмеження: приватних ключів тут немає.** На всій сторінці ЦЗО (436 посилань) розширення лише
`xml`, `cer`, `pdf`, `p7s`, `txt`, `asice`, `asics` — жодного `.p12`/`.pfx`/`.jks`/`.dat`.
Тобто цей набір закриває **перевірку** чужого підпису й не закриває **створення** свого.
Щоб підписати Купиною, потрібен реальний КЕП нового зразка від КНЕДП.

## Склад

```
dstu-7564/   ДСТУ 4145 + Купина-256   (digest 1.2.804.2.1.1.1.1.2.2.1, sign 1.2.804.2.1.1.1.1.3.6.1.1)
dstu-4145/   ДСТУ 4145 + ГОСТ 34311   (контрольна група)
    DSTU_sign.cer, DSTU_encryption.cer
    enveloped/{CAdES-BES,CAdES-T}/test.txt.p7s
    detached/{CAdES-BES,CAdES-T}/test.txt + test.txt.p7s
```

`test.txt` — оригінал для detached-перевірки, 6 байт, `Test\r\n` (**саме з CRLF**; для detached
підпису байти мають збігатися точно). Однаковий в обох групах — це нормально, один файл
підписано двома алгоритмами.

Контрольна група потрібна не «про запас»: без неї провал на купинному зразку неоднозначний —
незрозуміло, чи стек не тягне Купину, чи не тягне формат прикладів ЦЗО взагалі.

## Три пастки

1. **Кодування різне.** Сертифікати `dstu-7564/*.cer` віддаються у **Base64** (`MII…`),
   `dstu-4145/*.cer` — сирим **DER**. `openssl x509 -inform DER` на перших падає, поки не
   пропустити через `base64 -d`. JSON-API UAPKI хоче Base64 — перші йдуть як є, другі треба
   закодувати; головне не закодувати перші вдруге.
2. **Терміни дії розходяться.** Купинний сертифікат чинний (24.04.2026 → 24.04.2027), старий
   **прострочений** (03.03.2024 → 03.03.2026). Однаковий сценарій на обох групах дасть хибний
   висновок «Купина працює, стара схема ні», хоча причина суто в терміні дії. Старій групі
   потрібен `offline` + `ignoreCertStatus` або `VERIFY` у режимі `STRUCT`.
3. **Алгоритм сертифіката НЕ визначає алгоритм підпису.** Ключ ДСТУ 4145 дозволяє підписувати
   і ГОСТом, і Купиною; живий `ticket.p7s` ДПС має сертифікат старого зразка й підпис Купиною.
   Дивитись треба в `SignerInfo`, а не в сертифікат.

## Чого цей набір НЕ покриває

Приклади ЦЗО підписують абстрактний `test.txt`, а не документ у **форматі ПРРО** (enveloping з
XML-чеком, з обов'язковим вкладеним сертифікатом підписувача й забороненими CRL/OCSP/
content-timestamp). Тобто вони перевіряють «чи вміємо ми Купину взагалі», але не «чи вміємо ми
Купину у формі, якою її подає ДПС». Матеріал з обома властивостями — квитанція фіскального
сервера; придатний для репозиторію варіант — квитанція на **тестовий** чек
(`<TESTING>true</TESTING>`), без `OFFLINESEED` і реального фіскального номера.
